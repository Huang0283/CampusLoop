\chapter{Key Architectural and Technical Decisions}
\label{ch:decisions}

This chapter analyzes twelve foundational engineering decisions that shaped CampusLoop's implementation at baseline \texttt{main@ecc22d2}. Each decision is examined in terms of the engineering problem encountered, the implemented design, the concrete alternatives considered, and the resulting trade-offs in complexity, security, and maintainability. Table~\ref{tab:decisions-summary} provides an overview of all twelve decisions across four thematic dimensions.

\section{Data Architecture, Contracts, and Session Security}
\label{sec:dec-core}

\subsection{D1. Single Authoritative PostgreSQL Store over Polyglot Persistence}

\textbf{Problem.} Second-hand trading couples inventory availability (\texttt{products}), negotiation (\texttt{offers}), reservations (\texttt{orders}), scheduling (\texttt{meetups}), and moderation (\texttt{account\_\allowbreak decisions}). Splitting these entities across independent service databases would turn offer acceptance and account disabling into distributed sagas vulnerable to partial failure.

\textbf{Chosen design and alternatives.} CampusLoop centralizes all 27 ORM tables in PostgreSQL~16 \cite{postgresExplicitLocking} while relegating Redis strictly to ephemeral rate limits and pub/sub fanout \cite{redisDocs} and MinIO strictly to immutable binary blobs \cite{minioDocs}. The alternative of assigning chat to a document database and matching jobs to a dedicated message broker was rejected because it would introduce dual-write inconsistency between database commits and downstream notifications.

\textbf{Trade-offs.} Centralizing transactional writes concentrates load on one primary database instance, which is well within campus-scale traffic while guaranteeing atomic multi-table commits, unified backups, and deterministic relational constraints.

\subsection{D2. OpenAPI-Generated TypeScript SDK over Handwritten API Clients}

\textbf{Problem.} Rapid parallel iteration across frontend pages and FastAPI endpoints frequently causes silent payload mismatches, missing optional fields, or stale URL paths.

\textbf{Chosen design and alternatives.} FastAPI automatically emits an OpenAPI~3.1 schema \cite{fastapiDocs,openapi31} from Pydantic~V2 request/response models \cite{pydanticDocs}, and the build pipeline generates \texttt{frontend/src/sdk/generated/sdk.gen.ts} with full TypeScript operation signatures. The alternatives---handwritten \texttt{fetch} wrappers or untyped JSON helpers---would remove the code-generation step but push schema mismatches from compile time to runtime failures.

\textbf{Trade-offs.} Developers must regenerate the SDK whenever route contracts change and wrap generated functions in \texttt{sdk/index.ts} for cross-cutting concerns (refresh retry, scoped \texttt{401}/\texttt{423} cleanup, and idempotency keys). In return, contract drift is caught immediately by TypeScript compilation.

\subsection{D3. In-Memory Access Tokens with Rotating HttpOnly Refresh Cookies}

\textbf{Problem.} Single-page applications must persist login state across page reloads without exposing long-lived credentials to cross-site scripting (XSS) exfiltration or cross-site request forgery (CSRF).

\textbf{Chosen design and alternatives.} Access tokens (HS256 JWTs capped at 900 seconds \cite{rfc7519}) live solely in JavaScript memory, whereas rotating refresh tokens travel in an \texttt{HttpOnly}, \texttt{SameSite=Lax} cookie (prefixed \texttt{\_\_Host-} with \texttt{Secure} in production) \cite{rfc6265,owaspSession}. Cookie-based renewal endpoints additionally verify an exact \texttt{Origin} allowlist and the custom \texttt{X-CampusLoop-Browser} header, and refresh-token reuse revokes the entire \texttt{AuthSessionFamily}. Two alternatives were rejected: storing refresh tokens in \texttt{localStorage} (which allows any injected script to steal persistent credentials) and omitting browser persistence altogether (which degrades usability by forcing re-login on every reload).

\textbf{Trade-offs.} Browser credential flows require explicit CORS credential rules and careful handling of expired-token precedence (\texttt{401} before \texttt{423}), but substantially tighten the browser security boundary.

\section{Concurrency, Scheduling, and Storage Integrity}
\label{sec:dec-concurrency}

\subsection{D4. Layered Row-Lock Ordering with Partial Unique Indexes}

\textbf{Problem.} Two buyers can submit concurrent acceptance or booking requests for the same single-unit listing, while an administrator may concurrently disable a participant's account. Meanwhile, a listing whose earlier order was cancelled or disputed must remain eligible for a future trade.

\textbf{Chosen design and alternatives.} CampusLoop enforces a fixed five-tier PostgreSQL row-lock order (\texttt{auth/user} $\to$ \texttt{product} $\to$ \texttt{offer} $\to$ \texttt{order} $\to$ \texttt{meetup}) \cite{postgresExplicitLocking} backed by Migration~\texttt{0003} partial unique indexes on \texttt{orders(product\_id)} where \texttt{status NOT IN ('CANCELLED', 'DISPUTED')} \cite{postgresPartialIndex}, alongside unique \texttt{orders.offer\_id} and \texttt{idempotency\_records}. Alternative designs---checking availability solely in application code without row locks, or imposing an unconditional unique index on \texttt{orders.product\_id}---either allow double-booking race conditions or permanently block relisting after cancellation.

\textbf{Trade-offs.} Every new mutating endpoint must respect the global lock hierarchy to prevent deadlocks, and developers must keep migration DDL synchronized with ORM definitions; however, single-winner reservation is guaranteed even under multi-worker concurrency.

\subsection{D5. Optimistic Meetup Versioning and Post-Completion Immutability}

\textbf{Problem.} Buyer and seller concurrently negotiate offline handover times and locations. Without concurrency detection, one participant could accidentally confirm an outdated location just after the other edited it, or edit a meetup after the peer already confirmed completion.

\textbf{Chosen design and alternatives.} Every \texttt{Meetup} row stores an integer \texttt{version} checked via \texttt{expectedVersion} on updates and confirmations (\texttt{409 MEETUP\_VERSION\_CONFLICT} on mismatch). Editing a meetup increments \texttt{version} and resets both meetup confirmation flags, while \texttt{main@ecc22d2} strictly blocks meetup edits (\texttt{409 ORDER\_STATE\_CONFLICT}) once either party has confirmed trade completion. A last-write-wins alternative would simplify client forms but expose students to silent handover mismatches.

\textbf{Trade-offs.} The UI must handle \texttt{409} conflicts by reloading the latest meetup version before resubmission, trading minor extra client state management for trustworthy offline coordination.

\subsection{D6. Server-Side Image Re-Encoding and Dual-Bucket Media Isolation}

\textbf{Problem.} Allowing raw user uploads directly into a single public bucket exposes students to EXIF GPS metadata leakage, polyglot image files, decompression bombs, and unauthenticated scraping of private chat or appeal evidence.

\textbf{Chosen design and alternatives.} All uploads pass through \texttt{services/storage.py}, which enforces a 5~MiB ceiling and $25\times 10^6$ pixel limit, catches corrupted stream/CRC errors (\texttt{415}), strips metadata by re-encoding to RGB JPEG via Pillow, routes public product photos to \texttt{campusloop-public} and sensitive files to \texttt{campusloop-private}, and tracks per-user ownership and purpose in \texttt{uploaded\_objects}. The alternative of direct browser-to-S3 presigned uploads would reduce API bandwidth but bypass server-side decoding, EXIF stripping, and atomic ownership registration.

\textbf{Trade-offs.} Routing uploads through FastAPI consumes modest API CPU and memory per image, which is an acceptable cost at campus scale for guaranteed metadata sanitization and strict access control over private evidence.

\section{Asynchronous Processing, Interaction Design, and Governance}
\label{sec:dec-workflow}

\subsection{D7. PostgreSQL \texttt{SKIP LOCKED} Outbox over an External Message Broker}

\textbf{Problem.} Recomputing wanted-post matches synchronously inside \texttt{createProduct} or \texttt{updateProduct} would couple write latency to advisory ranking, whereas publishing directly to an external queue (such as RabbitMQ or Kafka) introduces dual-write drift when SQL transactions roll back.

\textbf{Chosen design and alternatives.} SQLAlchemy session hooks (\texttt{before\_flush}, \texttt{after\_flush\_postexec}, \texttt{after\_rollback}) write deduplicated \texttt{matching\_jobs} rows inside the same PostgreSQL transaction as the business write, incrementing \texttt{matching\_revision}. Standalone workers claim jobs via \texttt{SELECT ... FOR UPDATE SKIP LOCKED} \cite{postgresExplicitLocking}, automatically releasing locks on process crash without separate lease expiry sweeps. Introducing an external broker was rejected because it adds operational footprint, broker persistence configuration, and reconciliation complexity unwarranted at campus throughput.

\textbf{Trade-offs.} Polling PostgreSQL adds sub-second dispatch latency and modest query load compared with push brokers, while delivering exact transactional consistency and simple single-database recovery.

\subsection{D8. Single Peer-Pair Chat Session with Switchable Listing Context}

\textbf{Problem.} On a university campus, the same buyer frequently inquires about multiple textbooks or dorm items listed by the same graduating student. Opening a separate conversation thread per listing fragments history and forces redundant greetings.

\textbf{Chosen design and alternatives.} CampusLoop maintains one persistent \texttt{ChatSession} per peer pair and updates its active \texttt{product\_id} (and optional \texttt{wanted\_id}) context whenever a user enters chat from another listing, while each \texttt{Offer} binds immutably to the specific \texttt{product\_id} being negotiated. Creating separate threads per product was rejected to keep student inboxes compact and preserve interpersonal continuity.

\textbf{Trade-offs.} The UI and API must clearly surface the active listing banner and per-offer product identity inside each thread so participants never confuse which item an offer references.

\subsection{D9. Separation of Report Triage from Sanctions and Independent Review}

\textbf{Problem.} Coupling user-report resolution directly to automated account bans risks disproportionate enforcement on unverified complaints, while allowing an administrator to review appeals against their own sanction undermines procedural fairness.

\textbf{Chosen design and alternatives.} Resolving or overriding a report (\texttt{governance.py}) never executes account or product penalties; sanctions require explicit audited commands (\texttt{moderation.py} and \texttt{admin\_console.py}) carrying structured facts, policy basis, and evidence. Disabling an account atomically revokes sessions and runs \texttt{protect\_disabled\_orders}, while appeal review requires a second independent administrator (\texttt{decision.actor\_id != actor.id}, with an audited dev-only single-admin fallback). Auto-enforcement on report resolution or risk-score threshold crossings was explicitly rejected.

\textbf{Trade-offs.} Moderators perform an additional explicit step when escalating a confirmed report to a sanction, and production deployments require at least two active administrator accounts to resolve appeals; in return, every enforcement action has a complete, auditable human decision trail.

\section{Advisory Boundaries and Operational Discipline}
\label{sec:dec-advisory}

\subsection{D10. Bounded Advisory RPC with Contract Validation and Local Fallback}

\textbf{Problem.} Search, matching, pricing, trust, and risk services involve external HTTP calls or local inference processes that may stall, reject oversized payloads (\texttt{413}), return malformed fields, or be offline during maintenance.

\textbf{Chosen design and alternatives.} All advisory calls are wrapped in \texttt{ai\_adapters.py} and \texttt{catalog\_semantic.py} with hard timeouts (\texttt{1.5 s} for frozen M7/M8 RPC, \texttt{3.0 s} for optional BGE scoring), strict schema/version validation, deterministic fallback to in-process keyword scoring or \texttt{UNAVAILABLE} envelopes, and mandatory live PostgreSQL visibility rechecks before returning listings. Three alternatives were rejected: trusting remote responses verbatim (risks leaking deleted/blocked items), failing the entire user request on advisory outage (breaks core marketplace browsing), and silently substituting baselines without setting \texttt{degraded = true} (misleads users and evaluators).

\textbf{Trade-offs.} Maintaining local validation mirrors and live recheck queries introduces modest runtime overhead, but guarantees that advisory failures never compromise core trading availability or privacy boundaries.

\subsection{D11. Explicit Null Telemetry and Separation of Asking Prices from L3 Labels}

\textbf{Problem.} Some risk signals (payment failure counts and shared-device clusters) are not collected in an offline-meetup campus platform, and active listing asking prices are abundant whereas verified completed-transaction labels (L3) are scarce.

\textbf{Chosen design and alternatives.} Uncollected risk inputs are passed explicitly as \texttt{null} and surfaced in \texttt{missingInputs}, and M8 price responses always set \texttt{degraded = true} with \texttt{NO\_ELIGIBLE\_\allowbreak L3\_LABELS}. Live 90-day asking-price quartiles (\texttt{listing\_price\_\allowbreak reference.py}) are computed and labeled separately from M8 rule advice and never fed into evaluation metrics as transaction ground truth. Substituting zeroes for uncollected signals or treating asking prices as completed-sale labels was rejected because both distort statistical interpretation and overstate model readiness.

\textbf{Trade-offs.} Users see explicit ``low confidence'' and ``asking-price reference'' notices rather than seemingly authoritative point predictions, preserving scientific honesty and aligning with the project's \texttt{NO-GO} model graduation gate.

\subsection{D12. Environment Isolation and Public-Only Local Translation}

\textbf{Problem.} Running write-heavy acceptance tests against the daily database risks corrupting real accounts and uploaded media, while sending user text indiscriminately to a translation model risks leaking private chats or moderation records.

\textbf{Chosen design and alternatives.} CampusLoop separates persistent daily startup (\texttt{scripts/start-local.ps1}, retaining daily PostgreSQL and MinIO volumes) from isolated test/audit environments using dedicated databases and Redis DB14/DB15, while keeping daily and test environments aligned to the same application revision. The optional local \texttt{HY-MT1.5-1.8B} translation server enforces \texttt{ALLOWED\_ORIGINS}, JSON-only requests, span masking, per-item failure isolation, and strict restriction to public catalog display text. Sharing one database across daily and destructive test runs, or proxying private chat/appeal text through translation, was rejected due to data-loss and privacy hazards.

\textbf{Trade-offs.} Maintainers manage separate environment configurations and explicit database switches during verification runs, gaining reproducible audits, intact daily data, and strict privacy isolation.
