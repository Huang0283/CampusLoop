# AI1-04 匹配触发、幂等、版本与降级

版本：m7-p1-v1.1，2026-09-23。状态：架构候选；需 M4/M5/M6/M9 评审，尚未实现持久化链路。

## 1. 事件边界

业务事务提交商品/求购变化时同时写 outbox；投递器至少一次发送事件，消费者以幂等处理。M6 拥有商品、求购和通知业务事实；M7 计算匹配与解释；M9 负责调度、恢复、资源与监控；M4 负责通知展示。智能失败不能回滚发布或交易。

```mermaid
flowchart LR
  A[商品或求购事务] --> B[同事务写 Outbox]
  B --> C[匹配任务]
  C --> D[读取权威事实并过滤]
  D --> E[规则评分]
  E --> F[原子版本检查]
  F --> G[保存结果及通知待发送记录]
  G --> H[发送前再次校验与去重]
  H --> I[页面或站内通知]
```

| 触发 | 影响范围与动作 |
| --- | --- |
| 新建/编辑有效求购 | 重算该求购；旧结果标 stale；旧任务不能覆盖新版本 |
| 关闭/删除/到期求购 | 撤销其有效结果和未发送通知；到期有定时扫描，不只依赖用户请求 |
| 商品上架/重新上架 | 对可能相关的有效求购计算；缩小范围不能漏掉无类别限制的求购 |
| 改价/成色/地点/描述/类别 | 失效旧资格，重算受影响求购；集合取旧、新条件可能影响的并集 |
| 商品已售/预约/隐藏/下架/删除 | 优先撤销结果与未发送通知，禁止等待语义重算后才失效 |
| 权限或校区范围变更 | 撤销不可见结果，读取/发送时再次校验 |
| 算法切换 | 增加 policyGeneration，重算；回滚也增加 generation，不能以版本名大小判断新旧 |

## 2. 持久键与状态

| 对象 | 候选键 | 不变量 |
| --- | --- | --- |
| 事件 | eventId；entityType/entityId/entityVersion | eventId 唯一；相同 ID 不同内容作为冲突告警，不当合法重试 |
| 全量匹配任务 | wantedId+wantedVersion+catalogVersion+policyGeneration | 唯一键插入/原子领取；相同输入不创建第二份有效结果 |
| 局部任务 | 上述键+受影响商品版本集合的规范化哈希 | 不允许局部结果直接替换全量结果；合并后重新排序 |
| 策略 | ruleVersion、tokenizerVersion、modelVersion、indexVersion、policyGeneration | generation 单调递增，模型未启用时 modelVersion=null |
| 结果集 | resultSetId、runId、inputVersions、generatedAt、state | 每条求购只有一个当前结果集指针；历史只读 |
| 匹配对 | wantedId+productId | 同结果集不重复；保存输入版本与资格状态 |
| 通知 | recipientId+wantedId+productId+eligibilityEpoch | 连续满足资格的同一周期只生成一条站内通知 |

任务状态：pending→running→succeeded；失败进入 failed（可重试）或进入待人工处理队列；输入过时进入 superseded。running 需租约与心跳，进程崩溃租约到期后允许重新领取。重试只新增 attempt，不改变逻辑任务键。

catalogVersion 需要 M6/M9 提供可比较的商品目录快照/修订号；单个商品版本不能冒充全库版本。若目前只能获取局部版本，先实现局部任务并清楚标明语义，不能编造一个目录版本宣称一致性。

## 3. 原子提交与乱序

计算使用固定 asOf 与输入版本。提交时在事务中确认求购版本、所读商品版本、catalogVersion（全量任务）、当前 policyGeneration 和权限仍适用；再以条件更新替换当前结果指针。任何前提变化则标 superseded，重新读取和入队，不写旧结果。

例如商品 v3 改为已售后收到 v2 的上架事件：读取权威 v3 并撤销匹配，不能重放 v2 事实；v1 求购计算慢于 v2 修改：v1 提交必须失败；算法 generation=2 的任务不能覆盖 generation=3。不能只在任务开始检查一次版本。

若结果库与业务库分离，跨库原子检查不能默认成立。Phase 2 必须选定同库事务、经业务端校验的条件写接口或可证明的等效协议；消费者最终复核仍必要。

## 4. 通知与恢复

eligibilityEpoch 在一对求购/商品从“不合格→合格”时原子增加，同周期重复计算或分数变化不增加。初次合格记第一个周期。仅因数据暂不可用不应制造不合格迁移或新周期；应记 unknown 等待恢复。重新合格是否可再通知及冷却期由 M4/M6/M7 冻结。

保存结果和 notification_outbox 在同一事务完成；发送前再次查业务状态、权限、有效期和通知政策。站内通知以唯一键写入，由 M6 负责。外部推送若采用第三方供应商，还需其幂等键支持；只靠“发送后打标”无法保证进程崩溃时不重复，不承诺外部恰好一次投递。

通知阈值、频率上限、冷却、重试次数和延迟预算尚未有项目实测依据。候选开发配置可默认 notificationsEnabled=false；该配置不代表通知联调完成。重复通知数要求为 0 的正式验收应在确定的站内通知边界内执行。

## 5. 降级契约

| 状态 | 搜索 | 匹配 | 页面行为 |
| --- | --- | --- | --- |
| 正常基线/模型未配置 | keyword | rule | 正常显示当前方法，degraded=false |
| 已配置模型超时或报错 | 相同筛选下回到 keyword | 相同硬约束下回到 rule | degraded=true，说明已使用规则结果 |
| 索引未就绪或版本不匹配 | 不使用旧向量，回到 keyword | 回到 rule | 标明原因，不假称语义结果 |
| 规则也不可用 | unavailable | unavailable，不发通知 | 暂不可用与重试入口，不能伪装空列表 |
| 合法但无候选 | 成功空结果 | 成功空匹配 | 建议用户修改条件，不自动放宽 |
| 关键字段不足 | 隔离坏记录并诊断 | needs_info | 不计入合格数，不发推荐通知 |
| 身份/权限不可确认 | 拒绝或 unavailable | 拒绝或 unavailable | 不通过降级绕过鉴权 |
| 输入版本已变更 | 重新读取、重算 | stale/pending | 不把旧价格和理由作为当前事实 |

M3 文档写“匹配不可用转关键词结果”，M8 能力矩阵写“转规则匹配”。建议匹配页采用本表 rule 且保留全部求购约束；可提供独立的“去市场搜索”入口，但必须区分其结果。该差异登记 H-04，需联合确认。

M9 应分配总超时、模型预算、回退预留、并发上限和熔断恢复条件。数据库不可用时不保证关键词仍可用。日志只记录事件/任务 ID、版本、耗时和错误码，避免完整个人查询和商品描述。

## 6. 故障验收步骤（待 Phase 3 执行）

| ID | 注入 | 应验证 |
| --- | --- | --- |
| LC-01 | 同 eventId 重发 3 次，并发领取任务 | 一个逻辑任务，一份当前结果，一条站内通知 |
| LC-02 | v3 已售先到，v2 上架后到 | 无有效推荐，无新通知 |
| LC-03 | 计算期间修改求购预算 | 旧任务 superseded，新预算重新过滤 |
| LC-04 | 结果事务失败后重试 | 不出现仅通知存在或重复结果 |
| LC-05 | 写入通知后消费者确认前崩溃 | 重投后唯一键阻止第二条站内通知 |
| LC-06 | 到期/权限撤销发生在计算后、发送前 | 发送复核阻止失效通知 |
| LC-07 | 模型超时，规则正常 | 在预留预算内返回规则结果，硬约束不变 |
| LC-08 | generation=2 慢任务晚于 generation=3 | 当前指针仍指向 generation=3 |
| LC-09 | 任务进程在 running 状态崩溃 | 租约过期可恢复，无永久卡住 |
| LC-10 | 数据暂不可用后恢复，同一匹配仍合格 | epoch 不增，无重复通知 |
