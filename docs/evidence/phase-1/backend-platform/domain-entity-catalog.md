## 2. 术语与事实来源

- **Owner** 指规则负责人；资源所有者指具体用户。M6 定义业务，M9 维护最终模型、迁移和存储结构。
- 一个用户可在不同交易中扮演买方或卖方；同一订单买卖双方必须不同。
- **事实来源**是服务端校验后持久化的业务记录。聊天文字、浏览器缓存、按钮状态、AI 分数都不能直接作为成交事实。
- **业务版本**用来识别正在操作的内容；商品版本、订单版本、约定内容版本与确认轮次是不同概念，不共用一个计数器。确认轮次在改约定或争议解除后递增，防止旧确认重放。
- 以下“信息项”是概念清单，不是数据库字段或 API 命名承诺；具体类型、长度、枚举在 Phase 2 共同冻结。

## 3. 九类核心实体

| 实体 / 关联需求 | 规则 Owner / 资源所有者 | 参与者与可见性 | 核心信息候选 | 生命周期 | 权威事实来源 |

| 求购 Wanted；MARKET-006 | M6；发布者 | 游客可读公开有效求购；发布者编辑/关闭；潜在卖家可联系；个性化匹配只对本人 | 标题、分类、描述、预算上下限、最低成色、地点、截止时间、发布者、业务版本 | OPEN→CLOSED / EXPIRED / DELETED；修改使旧匹配过期 | 本人合法操作、服务端时间；匹配命中不表示交易完成 |

## 4. 必要支撑关系

| 概念 | Owner / 参与者 | 关系与生命周期 | 约束 / 可见性 / 来源 |
|---|---|---|---|
| 用户与登录会话 | M5；本人及授权管理员 | 用户关联各资源；登录态可撤销 | M6 消费 M5 的身份/禁用结论，不另建账号体系；公开资料排除邮箱、令牌和私聊 |
| 图片与附件 | M6 定义关联规则，M9 管理存储；上传者 | 先验证上传，再关联商品/消息/举报；未关联文件可清理 | 商品展示图与私聊/举报证据分开；文件归属和内容校验后才引用；数量/格式待 M3/M9 冻结 |
| 收藏 Favorite | M6；收藏人 | 用户与商品的关系；收藏/取消 | 同一用户同一商品至多一条有效关系；商品售出/下架后显示状态，不以收藏恢复可交易性 |
| 会话 ChatSession | M6；会话双方 | 基于一个商品或一个求购上下文创建；保存消息历史 | 相同上下文和同一对参与者复用会话；求购可有多位不同卖家，不以求购人一项去重 |
| 订单事件 OrderEvent | M6；订单双方及必要审核者 | 一笔订单对应多条事件；只追加 | 保存操作者、动作、前后状态、版本、原因、时间及关联请求；事件与状态同事务落地 |
| 业务投递记录 | M6 定义可靠性，M9 设计持久化 | 业务提交→待投递→重试/已投递 | 候选采用事务内待投递记录；可变投递进度与不可变业务事件分离；不把 Redis 当事实源 |

概念关系：一个商品可以收到多笔报价，历史上可关联多笔已取消订单，但任一时刻至多一笔未取消订单占用它；一个被接受报价至多对应一笔订单。报价保存商品业务版本及条款快照；接受前必须仍与当前商品版本一致。订单具有一份“当前约定”及多份不可变历史版本；每方的约定确认和完成确认必须关联具体内容版本和确认轮次。每个订单最多两条评价，分别来自双方；治理隐藏评价不会释放其唯一性，不能因此再次评价。

求购会话如要成交，候选要求先关联该卖家的一件有效商品，再进入同一报价/订单流程，避免产生无商品订单。该入口由 M3/M4/M6 评审，未确认前不承诺实现。

## 5. 数据可见性与删除边界

1. 公开读仅包含已允许展示的商品/求购内容和脱敏用户摘要；查询隐藏或删除资源不能泄露私聊、约定、邮箱、证据或内部风险分数。
2. 商品“下架”是生命周期变化；“隐藏”和“删除”是展示维度变化。删除在售商品时同时下架，删除已售商品时保留 SOLD 事实；已占用商品禁止删除。删除后的发布无法恢复，但历史交易证据仍按授权保留。
3. 交易中商品禁止删除或改成交事实；逻辑删除后保留订单快照及必要审计，不级联清除消息、订单事件或评价证据。
4. 举报私有对象由 API 按目标与处理上下文授权，再提供短时访问；普通管理员角色不自动获得任意私聊读取权。
5. 订单的确认时间、约定地点等不是公开主页字段。通知仅含跳转所需安全摘要。
6. 公开商品图片撤回后的链接缓存/访问策略、审计保留期限由 M5/M9 确认；不能声称仅靠逻辑删除即可撤销已公开文件。

## 6. 给 M9 的模型评审输入

- 将商品生命周期与治理隐藏分离；补充下架与逻辑删除语义。现有 ER 的四个商品枚举不够表达所有动作。
- 求购 `MATCHED` 候选只作为展示/结果关系，不因 AI 命中终止求购；补充删除语义，待共同确认。
- 报价需要可识别发起者/接收者；买方卖方角色不能代替当前报价的行动权限。
- 消息需要服务端去重约束及不会因乱序提交漏消息的补拉顺序；仅 BIGINT 自增不等于提交顺序。
- 当前约定 1:1 可以保留，但必须另保历史版本以及按版本、轮次关联的确认；订单版本不能代替约定版本，旧轮次不能用于争议恢复后的新确认。
- 订单事件“不可删除”与级联删除候选冲突；建议逻辑删除、保留引用，具体 DDL 由 M9 在 Phase 2 评审。
- 举报 Owner 需按“业务目标/交易规则”和“治理授权/审核”拆清，通知规则由 M6 负责、存储由 M9 支持。
