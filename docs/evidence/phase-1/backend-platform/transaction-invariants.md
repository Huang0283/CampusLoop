| 编号 | 规则 | 关联需求 | 违反时处理 / 检查点 |
|---|---|---|---|
| INV-01 | 同一交易买方与卖方不同；只有资源所有者能管理自己的发布 | MARKET-004 / AUTH-003 | 自购、伪造参与者、第三方修改均拒绝；无业务写入 |
| INV-02 | 一件商品至多被一笔未取消订单占用；一份被接受报价至多产生一笔订单 | TRADE-003 | 并发竞争失败不能留下第二个订单或接受事实；已完成商品不能重售 |
| INV-03 | 接受报价、保存成交快照、建单、占用商品和业务事件整体成功或整体失败 | TRADE-003/004 | 中途异常全部回滚；只允许提交后通知 |
| INV-04 | 报价由当前接收者处理，发起者只能撤回；接受时必须尚未到期且商品仍可交易 | TRADE-002 | 不允许自己接受、过期接受、聊天文字直接成交；还价必须明确双方角色 |
| INV-05 | 约定确认与完成确认分别关联用户、当前约定版本和确认轮次；两个有效确认必须来自两个不同参与者 | TRADE-005/006 | 一人确认两次不等于两方确认；不同版本或轮次不能拼接 |
| INV-06 | 修改约定生成新版本，使双方旧约定确认及旧完成确认不再有效，保留历史 | TRADE-005 | 旧版动作拒绝；不得覆盖原时间地点或删除审计；候选禁止开始完成确认后改约定 |
| INV-07 | 订单完成必须同时具备当前有效约定的双方预约确认和双方独立完成确认，且当前没有争议/取消 | TRADE-006 | 单方完成不推进终态；超时、管理员裁决、模型分数均不能代替双方确认 |
| INV-08 | 订单完成与商品生命周期 SOLD 原子一致；成交金额来自被接受报价的快照 | TRADE-003/006 | 隐藏/逻辑删除不改变 SOLD 和成交历史；改价/价格建议不改变已建订单；不声称收到真实付款 |
| INV-09 | 评价者必须是已完成订单参与者，被评价者必须是另一方，每单每方至多一次 | TRADE-007 | 未完成/取消/争议订单、第三方、自己评价自己和第二条评价均拒绝 |
| INV-10 | 举报必须指向存在且举报人有权引用的目标；举报提交不等于受理、判责或订单争议 | ADMIN-001 / TRADE-008 | 猜测私聊 ID、他人订单/证据、无权限附件引用均拒绝；不自动封禁或完成 |
| INV-11 | 私聊、约定、举报证据只在必要且授权的上下文可见 | AUTH-002/003 / ADMIN-001 | 列表、详情、补拉、附件、通知跳转均需独立授权；角色为 admin 不等于全库可读 |
| INV-12 | 重复请求可以复用结果，但不能重复创建业务事实；不可变事件只追加 | TRADE-004/009 | 重复消息/订单/完成事件/评价/通知不增加计数；终态不被重试恢复 |
| INV-13 | 取消或争议不计入已完成交易；普通取消不能覆盖已出现的完成确认 | TRADE-008 / AI-004 | 一方声称已交付后，另一方不得普通取消并立即重新出售；转人工争议路径 |
| INV-14 | 智能输出仅为版本化建议，不修改售价、订单状态或治理决定 | AI-001～004 / QUALITY-001 | 过期结果不可覆盖新对象；AI 故障保留基础业务，降级状态明确 |
| INV-15 | WebSocket/Redis 不持有唯一交易事实；成功发送表示消息已持久化 | TRADE-001 / QUALITY-001 | 断线由授权 HTTP 历史补拉恢复；不能先确认成功后丢弃未存消息 |
| INV-16 | 接受报价前，报价绑定的商品业务版本必须仍是当前版本；失效报价不因重新上架而复活 | MARKET-001 / TRADE-002/003 | 商品改价、隐藏、下架、占用再释放后，需重新报价；已建订单快照保持不变 |

## 3. 双方确认的精确含义

设当前约定内容版本为 v、确认轮次为 r，参与者为买方 B、卖方 S。只有同时满足以下条件才能完成：

- 订单处于 BOOKED，或经评审保留的等价可完成状态；不是 DISPUTED、CANCELLED 或其他未预约状态。
- B≠S；B 与 S 都已在轮次 r 确认当前约定 v。
- B 与 S 都以自己的有效身份提交了针对 v、r 的完成确认；这些确认尚未因改约定或争议处理失效。
- 商品仍被该订单占用；在同一事务写入订单 COMPLETED、商品 SOLD 和相应事件。

第一个完成确认只记录该方的事实，并显示“等待对方确认”。第二个确认在事务内重新读取并检查全部条件。不能仅以两个不带版本的布尔值判断，也不能由请求传入 buyerId/sellerId 来代替认证用户。

重复确认由同一个用户、同一版本、同一轮次、同一动作识别。争议解除会递增轮次，即使时间地点未变，旧确认也不能恢复有效。重放旧幂等请求只返回原轮次历史结果及当前状态，不写入新轮次；新的确认需新动作键。双方仍需独立确认，管理员不能代确认。

争议解除后的原约定可能已过期：仅在状态机定义的、有治理审计的恢复上下文中，允许双方在新轮次核对原约定；普通新预约仍要求未来时间。这样可恢复已面交交易的确认而不伪造未来见面。

## 4. 权限边界

| 操作 | 允许角色及条件 | 必须拒绝 |
|---|---|---|
| 浏览商品/求购 | 游客和登录用户读取允许公开内容 | 以公开详情接口返回隐藏数据、私聊、约定、内部风险或证据 |
| 编辑/上下架/删除发布 | 本人且生命周期允许；治理另走专用动作 | 第三方、交易中破坏快照、已售重新上架 |
| 会话、发消息、历史补拉 | 当前有效参与者；系统事件由服务端产生 | 无令牌/失效会话、猜测会话 ID、客户端冒充 SYSTEM/ORDER_EVENT |
| 接受/拒绝/还价 | 当前报价接收者；未过期且状态允许 | 自己接受、第三方、固定只允许卖家导致买方无法接受卖方还价 |
| 撤回报价 | 当前报价发起者；未过期且待处理 | 对方撤回、撤回已接受报价以删除订单 |
| 确认约定/完成 | 订单买卖双方各操作自己；当前有效版本 | 第三方、管理员代确认、不同版本拼接、取消/争议状态 |
| 评价 | 已完成且未评的参与者评价另一方 | 未完成/取消/争议状态、第三方、自评、第二条评价 |
| 举报用户/商品 | 已登录、目标可识别且有权访问 | 伪造目标、读取不属于自己的私有附件 |
| 举报订单/消息 | 已登录且是相应订单/会话参与者 | 非参与者通过任意 ID 引用私有内容 |
| 查看证据/处理举报 | 举报人仅本人提交；审核者需 M5 授权并有关联案件 | 无关管理员、被举报人或其他参与者批量读取原始证据 |
| 通知读取/标已读 | 当前通知接收者 | 他人标已读、通知跳转绕过目标资源授权 |

账号禁用、会话撤销和 WebSocket 长连接期间重新授权由 M5 定义身份能力，M6 在每次业务动作及私有读取时使用有效结论；不把已建立连接当作永久授权。

## 5. 可逐步走查的场景（预期，尚未运行服务）

测试数据仅用虚构账号：A 卖家、B 买家、C 第三方/另一买家、D 审核者。每组场景使用独立初始记录。

| 场景 | 前置与动作 | 预期结果 / 对应规则 |
|---|---|---|
| M6-S01 正常闭环 | A 发布→B 发报价→A 接受→双方确认约定 v1→B 完成→A 完成→双方各评价 | 单方完成时订单未完成；双方完成后商品售出；恰好一笔订单、每人一条评价；INV-01～09 |
| M6-S02 越权与自购 | C 修改 A 的商品；A 向自己商品发起交易 | 两者拒绝；商品、订单无变化；INV-01 |
| M6-S03 单方重复确认 | 双方已确认约定；B 对同一约定连续完成确认两次，A 未确认完成 | 只保留 B 一次有效完成确认，订单不完成；INV-05/07/12 |
| M6-S04 旧约定 | 双方已确认 v1；尚无完成确认时 A 改为 v2；B 用 v1 确认完成 | v1 成为历史，双方旧确认失效；B 的旧版动作被拒绝；INV-05/06 |
| M6-S05 非法评价 | 对未完成、已取消、争议中订单分别评价；C 评价别人的完成单 | 全部拒绝；不新增评价或评分；INV-09 |
| M6-S06 重复评价 | B 已对完成订单评价，再提交不同内容 | 拒绝第二条；同幂等请求重试只返回原记录；INV-09/12 |
| M6-S07 争议不能代成交 | D 受理订单争议后试图直接将订单置为 COMPLETED | 拒绝；必须解除争议后双方重新合法确认，或人工取消并审计；INV-07/13 |
| M6-S08 举报证据权限 | B 举报会话内消息；C/无关联审核权限的 D 尝试读证据 | B 可见本人提交；C 与未获授权 D 拒绝；授权后 D 仅在案件上下文访问并留审计；INV-10/11 |
| M6-S09 取消与释放 | 无完成确认的预约订单由 B 合法取消；A 检查商品 | 订单取消、商品下架、历史保留；重新上架经独立校验；INV-02/13，策略待 Q04 |
| M6-S10 完成中取消 | B 已完成确认，A 尝试普通取消/修改约定 | 拒绝；显示通过举报/争议处理的路径；INV-06/13，策略待 Q04 |
| M6-S11 报价角色/过期 | A 向 B 还价；B 接受；另用过期报价执行接受 | B 可以合法接受 A 的还价；过期接受拒绝，不新增订单；INV-04 |
| M6-S12 断线恢复 | 消息已提交但 ACK 丢失；客户端用同标识重试后补拉 | 同一条持久化消息，补拉不遗漏，重复显示合并；INV-12/15 |
| M6-S13 争议恢复后重放旧确认 | B 在 v1/r1 已确认完成；进入争议后解除为 r2；B 重放 r1 请求，再由双方按 r2 核对原约定并确认完成 | 旧请求不新增 r2 确认；必须双方重新确认；若原时间已过去，只有审计指定的恢复上下文允许核对历史约定；INV-05/07/12 |
| M6-S14 改价与重新上架 | B 对商品版本 p1 报价；A 改价或下架再上架使版本变化；尝试接受旧报价 | 旧报价拒绝；双方重新报价后可交易；已接受报价的原订单快照不变；INV-04/08/16 |
| M6-S15 已售商品逻辑删除 | 订单完成后 A 删除发布，B 查看自己的交易记录 | 商品展示为 DELETED，但生命周期仍 SOLD；成交快照与评价资格不丢失，原商品不能重新上架；INV-08/09/12 |
| M6-S16 预约/完成确认竞争 | v1/r1 下已预约；两方使用相同旧订单版本同时确认完成 | 第一个请求记录本人确认后不改变 v/r；第二个在锁内重新校验并可成功；不能仅因对方确认引起的订单版本递增而拒绝；INV-05/07 |

更多并发交错见 [BP1-07 风险表](transaction-concurrency-risks.md)。这些是 Phase 1 文档走查用例，真实 API、数据库和双账号 E2E 待 Phase 3 实测。
