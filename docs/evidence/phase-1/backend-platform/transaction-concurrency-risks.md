# BP1-07 事务、幂等与并发风险（M6 提交评审版）

> 主责：M6；版本：0.2；日期：2026-09-27；状态：设计候选，供 Phase 1 PR 评审，尚无实现/压测证明。
> 同时提供 BP1-11 小组高风险清单的 M6 输入；不替代 M5/M9 的风险项或 M10 独立验收。

## 1. 设计依据

[实体字典](domain-entity-catalog.md)、[五类状态机](state-machines.md)、[不变量](transaction-invariants.md)、[M9 ER](er-candidate.md)、[M9 架构](system-context.md)、[M4 实时通信](../../../frontend/m4/05-realtime-architecture.md)。

- **事务**：一组相关数据要么全部提交，要么全部回滚。
- **幂等**：同一个操作重试，不重复产生消息、订单、确认、评价等事实。
- **并发控制**：多方同时操作时，以服务端当前事实决定唯一合法结果，不能只靠按钮禁用。
- PostgreSQL 是最终事实来源；Redis 可辅助缓存、限流和通知，但其丢失不能解除商品占用或允许越权。
- 本文给逻辑约束与查询需求；M9 在 Phase 2 决定具体模型、锁、索引和迁移。

## 2. 事务边界候选

| 业务动作 | 必须在同一事务内完成 | 提交后进行 | 回滚时不能留下 |
|---|---|---|---|
| 接受报价 | 锁定并复核商品/报价；校验接收者及期限；接受报价；保存成交快照并建单；占用商品；事件和待投递记录；幂等结果 | 系统消息/通知的派生投递、WebSocket 推送 | 孤立订单、已接受但无订单报价、无订单占用、虚假成功通知 |
| 还价 | 原报价标 COUNTERED；新报价及前序关系；事件、幂等结果 | 推送新报价 | 旧报价结束却无新报价、多个重复后继 |
| 修改约定 | 锁订单并核当前版本/完成确认；保存不可变新版本；更新当前指针；旧确认失效事件；订单回待确认 | 提醒双方重新确认 | 覆盖旧版本、部分确认遗留、新约定与旧订单状态混用 |
| 确认约定/完成 | 校验用户与当前版本；记录该方一次确认；重算双方条件；必要时更新订单/商品；追加事件与幂等结果 | 向双方推送状态、安全通知 | 单方直接完成、重复完成事件、订单已完成而商品仍在售 |
| 取消/争议处理 | 授权与状态复核；原因及审计；订单状态；确认失效；合法取消时释放商品 | 处理结果通知 | 争议中商品被重新卖出、取消记录丢失、未审计决定 |
| 提交评价 | 锁/复核订单完成和参与者；唯一评价；事件、幂等结果 | 更新可重建评分聚合 | 两条同方评价；聚合更新失败导致真实评价丢失 |
| 发送消息 | 验证会话参与者；去重；分配安全顺序；持久化消息及待投递记录 | 返回持久化 ACK，再推送；断线走历史补拉 | 收到成功 ACK 却无持久化消息 |
| 提交举报 | 校验目标及证据归属；举报记录与私有对象引用、事件、幂等结果 | 安全受理通知 | 无授权证据引用、半条举报、公开原始证据 |

对象存储上传不能与数据库假装同一 ACID 事务。候选流程为上传暂存→校验所有者与内容→事务关联→定期清理未关联对象；关联失败保留可重试标识，不能把私有证据改放公共桶兜底。

## 3. 幂等请求与自然唯一性

1. 写操作候选使用“认证用户 + 操作类型 + 资源 + 幂等键”作为作用域，同时保存规范化请求摘要。键格式、传递位置和保留时间在 Phase 2 与 M4/M9 冻结。
2. 同键同摘要：若已成功，返回原动作对应的同一资源/结果；仍需检查当前调用者有权读取，附当前状态或要求刷新，不能将历史结果当当前状态。处理中返回明确重试语义。
3. 同键不同摘要：明确冲突，不能悄悄把一笔请求改成另一笔。
4. 幂等结果与业务成功同事务提交；响应丢失可重放。事务已回滚的瞬时失败允许同键按相同内容重试，不能留下永远“处理中”的孤立记录。
5. 幂等记录过期也不能失去核心保护：订单、消息、评价、确认仍由业务唯一约束和状态前置防重复。
6. 重复确认可返回已有确认；重复提交不同评价拒绝第二条；这些语义要分别说明，不能统一用“重复就报错”处理。

| 逻辑唯一性需求 | 保护的事实 | M9 评审重点 |
|---|---|---|
| 一个商品至多一个未取消订单 | 商品只被一次有效交易占用，完成后不能重售 | 已有部分唯一索引候选可沿用，但订单状态扩展时复查；争议必须占用 |
| 一个来源报价至多一笔订单 | 同报价重试不再建单 | 来源报价引用及唯一性；不能仅依赖商品占用 |
| 订单 + 用户 + 约定版本 + 确认类型 + 确认轮次 | 区分预约与完成，避免一方算两方；争议恢复后允许真正的新确认 | 改约定/解除争议同事务递增轮次；旧请求只重放旧结果，不能写入新轮次 |
| 订单 + 评价者 | 每方最多一次评价 | 同时校验评价者/对象是订单双方 |
| 会话 + 发送者 + 客户端消息标识 | WS、HTTP、重试共用去重 | 同标识不同正文拒绝；系统消息独立服务端标识 |
| 上下文 + 规范化的参与者对 | 重复联系复用同一双人会话 | 求购不同卖家不能错误合并到同一会话 |
| 用户 + 商品收藏关系 | 不重复收藏 | 收藏/取消自然幂等；不改变商品状态 |
| 接收者 + 来源事件 + 通知类型 | 重复投递不重复通知 | 事件 ID 全局/命名空间唯一；授权与私有内容不进入正文 |
| 订单 + 事件逻辑标识/业务版本 | 不重复成功事件 | 投递状态与不可变事实分开维护 |

## 4. 锁、版本和消息游标候选

- 锁粒度为具体商品/订单/会话，不锁全站。涉及同一商品的事务统一先锁商品，再按固定顺序锁报价、订单、当前约定；不允许先锁订单再回头争抢商品。纯订单动作也须遵守全局顺序，M9 统一设计。
- 接受报价、取消、改约定、完成确认、受理争议都须在持有相关锁时重新读取状态；版本检查与修改不能拆成两个无保护步骤。
- 不同动作使用不同版本前置：报价接受检查商品绑定版本；改约定检查约定内容版本及状态；取消检查订单版本；预约/完成确认以约定版本和确认轮次为准，在锁内重算双方确认。不能仅因另一方的合法确认使订单版本增加就拒绝第二方确认。
- 商品任何业务变更递增商品版本，接受报价在增加占用版本之前核对原绑定版本；失效旧报价不会因商品再次在售恢复有效。治理隐藏/解除同样使旧报价失效，避免隐藏期间的条款变化被忽略。
- 并发同版修改只允许一个成功，失败方拿新版本重新确认，不做无提示的“最后写入覆盖”。死锁/序列化失败只做有限次可幂等重试，不无限等待。
- 完成与取消并发：若取消先合法提交，完成动作失败；若第一方完成先提交，普通取消失败；只有双方均完成才最终售出。
- `createdAt` 只能作展示，不足以作为稳定补拉游标；同秒消息、客户端时钟和数据库并发提交都可能乱序。
- M9 的 BIGINT 自增候选存在“编号较小的事务晚提交”风险。候选采用会话行串行分配、持锁至提交的会话内序号作为补拉进度；回滚的编号可跳过，但不能出现已越过游标后才提交的消息。替代方案必须证明不会漏读。
- 服务端消息 ID、客户端幂等 ID、推送事件 ID、补拉游标不是同一个概念；客户端合并应带会话/发送者作用域。传输可以重复，业务事实必须唯一。

### 并发交错走查（纸面推演，不是数据库实测）

| 场景 | T1 顺序 | T2 顺序 | 串行结果 |
|---|---|---|---|
| R01 两笔报价竞争 | 接收者锁商品→复核 p1/报价→建单占用→提交 | 等待同商品锁→读取已占用及新版本→拒绝 | 一笔有效订单；T2 不先写 ACCEPTED |
| R04 双方同时完成 | 锁商品/订单→核 v1/r1→记录 B 确认→提交 | 等锁→核 v1/r1 未变→记录 A 确认→同时完成订单和商品→提交 | 两方各一条确认，完成事件一次；忽略仅由 T1 确认导致的无害订单版本差异 |
| R06 改约定先发生 | 锁商品/订单/约定→v2/r2，旧确认失效→提交 | 等锁→发现请求 v1/r1 已旧→拒绝 | 必须对 v2/r2 重新确认；若 T2 完成确认先提交，T1 改约定被保护规则拒绝 |
| R07 取消先发生 | 锁商品/订单→无完成确认→取消并释放→提交 | 等锁→发现已取消→拒绝完成 | 不产生“已取消又完成”；若完成确认先提交，普通取消被拒绝 |
| R11 消息顺序 | 锁会话→分配序号 n 并写消息→提交后释放锁 | 等同会话锁→分配 n+1→提交 | n+1 不可能先提交而把尚未提交的 n 永久跳过；T1 回滚则 n 可复用或形成安全空洞 |
| R19 旧确认重放 | 治理恢复事务使 r1 失效、当前轮次改 r2→提交 | 同键重放只返回 r1 历史；新键带 r1 因过时拒绝 | r2 的双方确认仍为空，任何管理员操作都未替代用户确认 |

锁和约束的具体数据库实现仍交 M9；以上推演检验方案能否给出确定结果，Phase 3 必须用真实并发和故障注入复核。

## 6. 不可变事件与故障恢复

候选事件最小信息：事件身份、对象、操作者/系统来源、动作、前后状态、业务/约定版本、原因、服务端时间、关联请求。私聊全文、令牌和原始举报证据不复制到普通日志。

- 业务状态与事件同事务；失败事务不留下“成功事件”。校验失败如需安全审计，应明确标为拒绝记录。
- 业务事件只追加；更正用新事件解释，不 UPDATE/DELETE 历史，也不靠级联删除绕过。
- 待投递进度可更新；重复投递由消费者业务键去重。不宣称网络实现“恰好一次”，只保证最终业务事实不重复。
- 崩溃后：未提交事务回滚；已提交但无响应按幂等查回；已提交但未推送按持久化待投递记录补送；客户端按授权查询恢复事实。
- MinIO 故障时附件功能明确失败/重试；不伪造上传成功。数据库本身不可用则拒绝需持久化写入，不以缓存假装成功。
