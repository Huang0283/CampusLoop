## 本轮修复的问题

1. 日常页面曾连接临时验收库，导致原账号登录失败。先备份历史库和图片，再迁入固定 `campusloop-local` 日常项目；原 89 个账号的身份和密码散列逐一核对一致，旧密码没有重置。统一启动入口和固定持久卷，源码变化检查镜像指纹，端口冲突时停止并报错。
2. 集成后台仍使用公开举报类型。改为生成 SDK 的私有管理员举报契约，保留鉴权读取证据和 Blob URL 回收。
3. 管理员商品治理只有未接通提示，未达到 FE4-01。补齐正式 OpenAPI、生成 SDK、管理员列表/筛选/分页/详情、人工下架和解除、原因与审计、幂等回放、并发版本检查及迁移 0010。普通用户不能访问；已预订/已售出商品不能被此操作改变交易状态；卖家不能自行解除管理员下架。
4. 复核发现只换商品图片不会更新父商品时间，可能让管理员按照旧图片解除下架。真实数据库测试先复现失败，再显式更新商品版本；旧审核提交返回 `PRODUCT_STALE`，商品继续不可见。
5. M9 的独立 Worker 提交原未被四组集成。本分支合入 `task/m9-p4-worker-runtime`，冲突保留 M6 的有界重试、幂等和旧结果保护，再合入 M9 的观测钩子。运行时 Worker、心跳与队列健康正常。
6. 历史维护脚本把后来已用于日常账号的 `campusloop_ops` 当作可回退测试库。现在必须显式 `APP_ENV=test`、专用 `campusloop_test`/`campusloop_audit_*` 和 Redis 14/15；原日常库在创建测试证据前即被拒绝。
7. 浏览器验收脚本原硬编码通过数；现在读取 Playwright JSON 汇总，失败、跳过、波动或全局错误均不能算通过，并记录检出是否存在未提交改动。测试限流只在明确的隔离测试环境重置，不改变正常用户限流。
8. 市场页恢复原设计的四列桌面商品卡片、分类快捷入口、圆角与价格/地点层次，保留真实接口、筛选和状态。没有把路由切回旧 Mock。其他真实页面仍沿用现有集成实现，本轮不声称所有旧原型外观逐像素恢复。
9. 注册页解释测试邮箱：`name@example.invalid` 是演示标识，不是真实邮箱、无验证码，也不代表学籍认证。已有账号直接登录。

## 手动验收入口与重点

固定地址：`http://127.0.0.1:5174`。这些页面来自当前验收分支，尚不是 main 第四阶段正式发布。

1. `/market`：游客直接浏览、分类/排序/搜索；无需登录弹窗。点击收藏、发布或联系卖家才需要登录。登录后侧栏出现聊天、交易；个人菜单有发布、收藏和举报。
2. `/login`：原账号使用原密码；演示学生 `chen.demo@example.com`、密码 `Demo@12345`。刷新仍为本人，退出后刷新不恢复登录；不要把管理员账号当学生进行交易。
3. `/publish`、`/my-products`：上传真实图片、发布、编辑、普通上下架；原价不得低于售价；保存后刷新仍存在。
4. `/wanted`：发布未来有效期求购、查看匹配及过期/降级说明；价格建议入口 `/publish/price-advice` 只作参考。
5. `/chat`、`/transactions`：用两个独立浏览器/无痕上下文登录不同学生，联系商品卖家、聊天、报价、接受、安排未来约见、双方确认同一版本、双方完成、评价；过去时间必须被拒绝。
6. `/notifications`、`/report`：已读状态刷新保留；买卖方举报原因不同；只显示本人举报，不展示私密证据内部路径。
7. `/admin`：演示管理员 `admin.demo@example.com`、密码 `Demo@12345`。学生访问必须拒绝；管理员核查用户、商品、举报。人工处理填写原因，卖家不能绕过人工下架；已预订/已售出不能被商品治理强行上架。
