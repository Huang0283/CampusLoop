# 第三阶段手动验收反馈：约见时间与举报流程

日期：2026-10-15。分支：`fix/phase3-meetup-report`；基线：`origin/main` 的 `4c13e36`。本文件记录第三阶段累计 MVP 的缺陷修复，第四阶段前端 Issue #29、后端 Issue #30 接收回归；不代签用户验收，不关闭阶段 Issue。

## 问题与阶段边界

- 截图中订单时间线在 2026-10-15 创建约见，但约见日期为 2026-10-14。原代码仅判断开始早于结束，没有判断开始晚于当前时间。第四阶段原 Issue 没有明确这项校验，属于已有交易规则缺口，当前修复。
- 所有举报对象共用六种原因，导致卖家对订单中的买家举报时也显示“虚假商品/描述不符”。现按目标类型和当前订单中的买卖身份筛选，并用原有 `VIOLATION` 承载恶意下单、爽约等说明。
- 本人举报原先只在通知页底部显示，缺少账户菜单入口和提交后的明确引导。现将已有 `/report` 路由用于“我的举报记录”，通知页继续保留记录。

## 最小变更与交接

- 前后端统一使用北京时间 UTC+8，不依赖 Docker 主机或浏览器时区。新建、修改和新增约见确认均有服务端校验；过去、等于当前时间的开始不能新保存/新确认。未完成双方确认的过期约见提示改约。已确认、已完成的历史事实不批量修改；成功请求的幂等重试保持原语义。
- 拒绝校验在写版本、确认、事件之前执行。现有 DTO、路径、原因枚举、数据库结构不变；保存沿用 `422 VALIDATION_ERROR`，过期确认沿用 `409 ORDER_STATE_CONFLICT`，均为现有 OpenAPI 已声明的响应。不改 PR #102 的 OpenAPI/SDK、智能编排、Worker 或模型字段。
- 新举报页面只读取已有 `/reports/mine`，展示本人的原因、说明、目标、时间、处理状态，不读取证据或管理员风险。举报说明界面限制 1000 字，与 M5 已合并的 #101 数据库长度修复兼容。
- 前端变更归 M4 交易/治理回归接收，账户菜单和路由仅各一处修改；后端归 M6 基础交易回归接收。第四阶段 Issue 中记录“接收和回归”，不安排组员重复写同一个功能。

## 手动复验

运行地址：`http://localhost:5184`，API：`http://localhost:8014`。

1. 使用自己的买卖账号分别登录普通/无痕窗口，打开进行中的订单。截图订单 #6017 可从 `/transactions/6017` 进入，前提是本人为参与者。旧过期约见应出现提示、不能继续确认；点击修改，昨天及今天已过去的开始时间均不能保存，未来日期且结束晚于开始可保存新版本。
2. 在另一窗口重新读同一订单，确认新版本，双方确认后交易主线仍可继续；改单必须清除旧确认，单方确认不能直接完成。
3. 卖家点订单举报，不出现“虚假商品/商品描述不符”；买家点同一订单举报保留商品问题。用测试说明提交，成功提示中的链接可进入 `/report`。
4. 从右上角账户菜单进入“我的举报”，核对目标、原因、说明、时间和状态。刷新应保留，切换另一个账号不能看到原账号记录。`/notifications` 仍显示通知和本人举报。
