# CampusLoop 独立测试与验收组任务书

版本：1.3；日期：2026-10-27。本组任务章节由总任务书原文提取，逐字一致；仅删去其他组的具体任务，共同课程约束与执行规则保留。成员自行认领，尚未分配姓名。

## 课程交付约束

以下要求来自 `JC2001-GroupProjectDescription-and-Requirements-2026-27(1).pdf`，是本项目协作的硬约束：

- 项目计划书必须提交，但不计分；课程截止时间以 Blackboard 为准，团队不能自行猜测日期。
- 技术报告占总项目成绩的 50%。正文从 Introduction and Project Context 到 Conclusions and Future Work，要求 40 至 60 页；标题页、目录、图表目录、References 和 Appendix A 不计入正文页数。
- 技术报告按 A4、四边 2.54 cm 页边距、单栏、12 pt Arial 或 Times New Roman、1.5 倍行距排版，最终提交单个 PDF；报告不粘贴源代码，源代码放入 PoC 提交包。本内部中文协作规划使用 OceanScope 风格的宋体正文与黑体标题，不作为课程英文报告模板。
- Proof-of-Concept 软件占 30%。提交包必须包含源代码、可运行版本、依赖或支持文件以及 8 至 12 页用户手册 PDF。
- 项目演示占 20%。课程要求一次 15 分钟演示，提交 PowerPoint 和 MP4；录像必须出现演示者本人，不能只录屏或用自动化录像代替真人讲解。
- 课程安排四次 Project Updates，至少提交三次。每次更新要写已完成工作、困难及处理方法、下一步，并且内容必须反映真实进度和与导师的讨论。
- 技术报告 Appendix A 必须附 Group Workload Profile。所有成员应在没有争议时签名；如不同意贡献评价，不应签名并应按课程要求联系课程负责人。贡献百分比必须有可量化证据，不能凭感觉填写。
- 所有外部代码、图、图片、数据、模型、算法和 AI 使用都要按学校要求说明来源和使用方式；不把自动生成内容当作成员独立贡献。


## 本组具体交付

### 独立测试与验收组

本组长期分支：`team/testing`。组内认领以下独立岗位，岗位名称不等于已确定姓名；以下文件由对应岗位独占编辑。原任务要求保留在下方。

#### T1 测试数据与身份权限：独立任务、文件边界与接收标准

- 岗位分支：`work/testing/data-permissions`；PR 目标：`team/testing`。
- 独占文件范围：docs/collaboration/phase-<n>/testing/data-permissions/ 个人用例/日志/数据登记；tests/collaboration/phase-<n>/data-permissions/ 虚构数据和生成复位脚本；本人 changes/<变更ID>/test-data-permissions.md。
- 个人日志：`docs/collaboration/phase-<n>/testing/data-permissions/task-log.md`；每次写任务、软件 SHA、产物/PR、实际执行、阻塞和接收人。

1. 接收版本与真实 API 契约，登记虚构卖家 A、买家 B、竞争买家 C、非参与者 D、管理员、游客/过期或禁用场景；列商品/求购/图片/订单数据的覆盖和预期。
2. 维护本岗位 dataset-register.md 与 setup-reset.md，写字段、来源/许可、规模、版本/哈希、生成/清理命令、数据 ID 与用例映射；让 T2/T3 各用独立账号/数据命名空间，复位不覆盖别人的证据。
3. 独立执行 T02 认证/资料和权限边界：注册/登录/退出/刷新/过期、私密字段、普通学生越权管理、非参与者读取私聊/约定/举报证据、对象归属；与 T2 场景共用数据定义但分别保存日志。
4. 接收 M7/M8 已有评估资产/口径，维护独立评估登记，组织标注复核、去重/划分与复算交给 T3 执行；数据授权/样本门禁未到位记阻塞，不能伪造成交或代签。
5. 把可用数据清单与最小使用例交给 T2/T3；运行结果写明真实 API/原型，缺陷交 M10，原失败保留并在修复 SHA 复测；每日写本岗位日报。
6. 每周核对 T2/T3 提交的场景数据映射、脱敏和许可；只汇总数据目录，不修改他们的测试结果、脚本或复测结论。

验收与交接：T2 使用说明独立生成一组可用数据，T3 复核环境隔离/脚本范围；M10 Review 生成脚本。数据工作与权限测试共同构成 T1 工作量，不是只收集几个样例。

#### T2 业务功能与双账号交易：独立任务、文件边界与接收标准

- 岗位分支：`work/testing/business-journeys`；PR 目标：`team/testing`。
- 独占文件范围：docs/collaboration/phase-<n>/testing/business-journeys/ 功能用例/执行/缺陷/复测/日报；tests/collaboration/phase-<n>/business-journeys/；本人 changes/<变更ID>/test-business-journeys.md。
- 个人日志：`docs/collaboration/phase-<n>/testing/business-journeys/task-log.md`；每次写任务、软件 SHA、产物/PR、实际执行、阻塞和接收人。

1. 接收 T1 数据清单，自己生成独立业务场景；核对版本 SHA、角色、前置、资源 ID 与预期，缺输入先报阻塞，不让同一测试账号并行互相改状态。
2. 按 T01/T03–T09 的业务部分执行游客市场/筛选、商品生命周期/收藏/求购、图片上传、聊天/报价、唯一订单、约定版本、双方完成、评价、通知/举报；身份与越权专项由 T1 负责，正常角色按钮与状态由 T2 负责。
3. 为正常路径及重复/非法状态/输入失败写可执行用例，特别检查过去时间、单方完成、旧版本确认、取消订单评价、会话重试和刷新持久化；并发脚本与环境由 T3 主责，T2 提供业务不变量。
4. 完成 T10/T11 用户可见智能正常/降级的业务表现，记录解释、声明、未评估限制；模型指标/故障注入由 T3，数据门禁与标注登记由 T1，不能三人重复认领同一产物。
5. 每个缺陷交 M10；修复后重跑原失败与相邻交易，保存失败/成功对照。每个工作日汇总三岗位已 Review 的数据为 testing-summary.md，原始日志各人保管，不能替别人填执行结果。
6. 向用户组交接已通过任务、SHA/数据别名、已知限制和可执行步骤；阻塞的任务不交为可用，用户组可先体验其他通过任务。

验收与交接：T1 复核数据/角色，T3 复核状态不变量与日志；M10 修复代码。T2 维护本轮 changes/<变更ID>/testing-summary.md，T1/T3 提交自己的摘要文件，避免同时编辑共享日报。

#### T3 异机环境、异常与恢复：独立任务、文件边界与接收标准

- 岗位分支：`work/testing/environment-recovery`；PR 目标：`team/testing`。
- 独占文件范围：docs/collaboration/phase-<n>/testing/environment-recovery/ 环境/性能/恢复/复算/日报；tests/collaboration/phase-<n>/environment-recovery/；本人 changes/<变更ID>/test-environment-recovery.md。
- 个人日志：`docs/collaboration/phase-<n>/testing/environment-recovery/task-log.md`；每次写任务、软件 SHA、产物/PR、实际执行、阻塞和接收人。

1. 接收 T1 数据和 T2 核心步骤，在另一台组员电脑或全新 VM 按手册检出指定 SHA 或包，记录系统/硬件/依赖/端口/包哈希，不复用 M10 未提交文件或日常库。
2. 执行 T14/T15 安装、空审计库迁移/种子幂等、服务健康、重启保留、升级/回滚、数据库与媒体恢复范围；记录首次失败和手册缺步，交用户组改说明、M10 改技术问题。
3. 执行专用环境并发/重复/性能、消息重连、超时/断网/智能不可用等故障注入；并发唯一订单/幂等不变量由 T2 提供，T3 执行脚本并保存实际计数及原始日志。
4. 核对真实 API 契约/SDK 漂移、生产构建和可访问性/跨浏览器等技术检查；T12/T13 的自动化与异常执行在此归口，真人桌面/手机可用性由用户组主责。
5. 接收 T1 已审核数据与 M7/M8 指标命令独立复算，记录版本/划分/参数/原始输出与限制；没有合格授权数据时只复算可复现基线，保留候选 NO_GO。
6. 每日提交本人结果、阻塞和需运维事项，向 T2 提供摘要；修复后复测原环境/异常用例，向用户组提供实际启动命令与故障恢复结果，不编辑用户组手册。

验收与交接：T1 Review 数据/权限，T2 核对业务预期；M10 核对隔离和故障注入范围。另一电脑不足时显式阻塞，不能用本机换目录顶替。

“测试数据与身份权限”岗位的个人任务：

1. 编写游客、普通学生、买方、卖方、管理员、非参与方和禁用账号的权限用例。

“双账号交易与状态测试”岗位的个人任务：

3. 测试重复提交、重复消息、并发接受同一商品、非法状态转换和非参与方访问。
4. 记录商品 ID、会话 ID、报价 ID、订单 ID、约定版本、双方账号和实际结果；不得记录真实隐私。
5. 将演示主路径交给讲稿与演示岗位，但只有在第二轮复测通过后才允许进入最终演示脚本。

#### 测试数据与独立评估集

测试方向“测试数据与身份权限”岗位担任数据清单负责人，具体姓名由组员自选，不预先指定。数据准备与用例编写并行；普通功能测试不需要等真实成交数据齐全。

- 业务测试数据由测试组负责：准备虚构账号、商品、求购、聊天、报价、不同订单状态、通知和举报，覆盖正常、越权、非法输入、重复/并发、空列表、异常与恢复。优先使用现有种子或公开 API 建立可达业务状态，提供生成及复位命令、场景与用例映射、数量和预期，不直接写入无法经业务流程到达的订单事实。
- 搜索/匹配评估集沿用并审查 M7 现有查询、商品、匹配与人工标注资产；M7 提供方法、字段、指标和复现命令，测试组负责独立标注复核、去重、覆盖检查与复算。新增评估部分须与训练/调参部分按商品实体等分组隔离，防止近重复泄漏；测试组不能一边根据结果调参，一边把同一集合称为独立测试集。
- 价格评估由 M8 提供字段、规则基线、MAE/MAPE/区间覆盖率和门禁口径，测试组接收数据并独立复算。现有 12 条 L0 合成记录只能检验结构、规则和降级；真实价格候选效果仍需 M5 实际确认使用边界、M6 提供合规导出，满足至少 200 条合格 L3 成交及六类每类至少 30 条等既定门禁。仓库外脱敏快照尚未到位时，继续做规则/功能测试，候选效果保留 NOT_EVALUATED/NO_GO；不得伪造成交、降低门槛或将授权代签。
- 信誉/风险样例验证已批准规则的输入、预期、解释、权限、人工覆盖和禁止自动处罚。没有真实独立标签时，只能报告规则符合性，不能宣称风险识别准确率。
- 每份数据登记用途、真实/合成、来源/许可、字段、数量及类别、获取/生成/复位命令、训练/验证/测试划分、预期、版本、SHA-256、负责人和复核人。测试代码、虚构样例及许可允许的资产通过 PR 提交；原始真实导出、私钥、令牌和真实个人数据不得提交 Git。测试组新增数据目录与 M7/M8 现有资产分开维护，不覆盖生产种子或修改生产规则。

#### 测试数据与真人体验数据的区别

- 测试组验证功能时使用可重置、可重复的虚构数据：测试账号、商品、求购、消息、报价、订单、举报和通知都由种子/API/测试脚本创建。数据应覆盖正常值、边界值、错误值、权限拒绝、重复/并发和失败恢复；登记生成/清理方法、预期结果和用例 ID。不可用本地写死的前端 Mock 代替真实 API 测试。
- “用户组”指真实组员作为体验测试执行人，不等于拿真实用户资料做数据。组员以游客身份或专用虚构学生/管理员账号，按买家、卖家、管理员角色登录并完成任务；使用的仍是虚构商品和专用测试库。记录角色、任务、卡点、误解、完成/失败、建议和对应 SHA。禁止使用真实学生账号、真实聊天、真实举报附件或未经许可的个人数据。
- 演示数据可以丰富市场页面，但必须标记为演示数据，走真实数据库和接口；它不是用户研究数据，也不能作为 M7/M8 的真实交易评估集或效果结论。
- 若后续另行收集真实用户研究数据，须先明确同意方式、用途、最小化字段、保管/删除期限和访问人；本任务包默认只用虚构业务数据和真人操作观察，不上传真实个人资料。

#### 每日向 M10 汇报

测试组认领 T2 岗位的成员负责汇总，每个工作日向 M10 汇报一次，不规定钟点；如需换人，在 Issue 登记交接后再修改文件负责人。每人更新自己的 daily-report.md，汇总人在 Issue #129 提供简报或链接；当天没有执行测试也要说明原因。严重故障发现后及时报告，不等日报或周末。

日报写清日期/执行人、软件 SHA、环境与数据版本、实际执行用例及通过/失败/阻塞/未执行数量、缺陷 Issue 与严重度、日志证据、修复后的复测、需要 M10 协助的事项和下一步。阻塞、未执行不能算通过。M10 据此安排运维与缺陷修复，提供新验收 SHA；原执行人在新版本复测并保留原失败证据，文书和手册同步更新。

## 大改动同步规则

### 什么算大改动

下列任一项都必须触发“代码、测试、文书、手册同步”：

- 新增、删除或改变路由、页面流程、登录守卫或游客权限；
- 修改 OpenAPI、请求/响应字段、错误码、生成 SDK、数据库模型或迁移；
- 修改商品、求购、聊天、报价、订单、见面、完成、评价、举报或通知状态；
- 修改 AI 输入输出、规则、模型、降级、解释、阈值或数据集；
- 修改页面布局、按钮、表单字段、错误提示、响应式断点或权限可见性；
- 修改端口、环境变量、Docker Compose、种子、启动命令、备份恢复或 CI；
- 修复会影响用户路径、测试预期、报告数字、截图或演示脚本的缺陷。

只改错别字、注释或不影响行为的排版，可以由文件 Owner 直接提交，但仍需在 PR 中说明“无行为变化”。

### 强制闭环顺序

1. M10 在代码 PR 或 Issue 中写变更原因、影响模块、需求 ID、风险、目标分支和预期验收场景。
2. 测试组更新受影响用例及数据，每日向 M10 汇报，周内完成复测；先保存旧失败或旧预期，再补新版本执行记录。周内不能完成时明确登记阻塞，不写成通过。
3. 文书组更新需求追踪、设计/实现章节、限制和报告数字；没有变化的章节也要在 PR 中说明已核对。
4. 手册组更新操作步骤、错误处理、截图索引和页面问题复测；旧截图必须标记过期，不得静默替换。
5. 只有测试和手册在同一候选 SHA 上通过后，报告负责人才能把报告相关 PR 合并到文书分支。
6. 功能和 UI 冻结后，演示组才更新最终 PPT、讲稿、彩排和 MP4；冻结前的 PPT 只能标为草稿。
7. M10 在阶段集成分支执行最终验收，确认软件、测试、报告、手册和演示使用同一 SHA；材料集成人复核范围和提交清单，随后再阶段收口。

### 每日版本通知和实际执行顺序

M10 每次完成当日修改并推送后，在 Issue #129 或对应大改动 Issue 发布一条版本通知，内容必须可直接供其他组执行：日期、版本/完整 SHA、分支与预览地址、改动页面/API/角色/数据状态、修改前后行为、改动文件或 PR、已知限制、如何启动/复位虚构数据、本次要测的场景、预期结果、回报截止时间。未改变的模块写“本次未改”，不要只写“更新了，帮忙测”。

执行顺序固定为：

1. **M10 发布测试基线**：提供可检出的完整 SHA、运行方式、虚构账号/数据版本、受影响功能和测试清单。没有稳定 SHA 时标记为开发中，测试组不得把旧版结果记到新版本。
2. **测试组先测功能正确性**：在专用测试环境用虚构数据按下列核心矩阵执行，并按改动补充针对性用例。每条记录用例编号、角色、数据 ID、步骤、预期/实际、结果、浏览器/环境、SHA、证据。发现故障立即建 Issue，附复现信息；只有失败或阻塞也如实记录，不能先让用户体验组把功能不通当成体验问题。
3. **测试组向 M10 汇报**：每个工作日给出该 SHA 的通过/失败/阻塞/未执行数量、最高严重度、Issue 链接、复现步骤、日志/截图、请求协助和下一步。M10 修复后发布新 SHA；原执行人重测原用例及回归范围，保留初次失败记录。
4. **用户体验组再按真人操作走任务**：在测试组确认本轮主要功能可用后，至少由未实现该页面的组员按游客、买家、卖家、管理员任务完成登录/浏览/交易/治理流程。使用专用虚构账号与商品；检查入口是否找得到、提示是否看得懂、步骤是否连贯、返回/刷新是否让人困惑、失败后是否知道如何恢复。记录任务、角色、完成情况、耗时或卡点、原话摘要（不记个人敏感信息）、页面路由、视口、SHA 和截图索引。功能错误建缺陷，理解/可用性问题建体验 Issue，分别由 M10 修复或按规划处理。
5. **文书与手册按影响更新**：文书组更新需求追踪、设计/实现事实、测试结论、指标和限制；手册组更新按钮/路由/步骤/错误恢复和同 SHA 截图。未受影响的章节在 PR 中注明已核对；旧证据标记过期，不静默覆盖。
6. **复测与交付**：M10 发布修复候选 SHA；原测试执行人复测，用户体验执行人重走受影响任务，文书/手册组检查内容与界面一致。各组 PR 写明代码基线 SHA、自己的文件、验证结果、遗留问题和复核人。M10 汇总当日/本周仍未解决项和下一步。
7. **演示组最后介入最终版本**：UI 和功能冻结前只维护草稿/来源索引；冻结并完成复测后才制作最终截图、讲稿、彩排和录像。紧急改动改变演示路径时必须重新检查并重录受影响片段。

## 分支与 GitHub 协作

M10 技术任务通过技术任务 PR 进入当前阶段集成，不由材料组修改生产代码。四条 `team/*` 是长期组分支；九条 `work/<方向>/<岗位>` 是每个岗位认领后一人使用的工作分支，已由 M10 建立。岗位分支 PR 指向本组 `team/*`，组汇总 PR 指向本轮版本通知指定的集成目标；禁止直接 push main、共享组分支或他人岗位分支。

岗位分支可在每轮 PR merge 后继续复用：拉取自己的远端并 merge 本组最新分支，不 rebase/force-push 共享历史。PR 合并时不自动删除这九条仍有人使用的岗位分支；若一项工作已结束且不再复用，再创建新的短期任务分支。长期/岗位分支用 merge 方式保持祖先关系；不要对持续复用的 head 使用 squash 后继续堆提交。

文件边界、拉取/push/PR/Review/冲突处理见各组 WORKFLOW.md。一个文件只有一个编辑负责人；Review 用评论/建议而非直接改他人分支；跨组文件经对方接收后在对方 PR 修改。软件完整 SHA 与材料提交分开登记，材料合并不代表软件基线已经验证。

## 个人任务日志与贡献记录

每位成员在本岗位独占目录的 `task-log.md` 记录日期、任务、输入 SHA、产出文件、PR、实际执行、阻塞和接收人。每轮按 `docs/workflows/version-acceptance.md` 使用独立变更 ID 目录；M10 写 notice.md，T2 汇总 testing-summary.md，U2 汇总 user-summary.md，R1 写 report-impact.md，D1 写 presentation-impact.md；其他岗位只写自己的摘要。材料集成人汇总链接，不重复编辑他人记录。

最终 Group Workload Profile 只在团队共同核对后填写。贡献评价使用课程给定的 0%、±10%、±25%、±50%、±100% 选项，必须有 PR、测试、文档、演示和 Review 记录支持；其中 0% 表示贡献相等，不表示没有贡献。本文件不预填成员的贡献百分比，也不代替任何人的签名。

## 完成标准

本协作计划只有同时满足以下条件才算完成：

1. M10 的软件候选 SHA 在另一位成员电脑或全新虚拟机上按手册启动，核心旅程和失败边界可复现，保留独立执行记录。
2. 测试组维护数据清单和独立评估边界，完成独立功能、权限、异常、环境和非功能测试，每日向 M10 汇报，失败项已修复或明确阻塞。
3. 文书组完成 40 至 60 页技术报告正文及引用、贡献和证据追踪。
4. 手册组完成 8 至 12 页用户手册和管理员/部署/故障文档，非作者可按步骤运行。
5. 功能与 UI 已冻结，演示组在同一 SHA 上完成两轮彩排、15 分钟演示材料和真人出镜 MP4。
6. 软件、报告、手册、PPT、视频和 Group Workload Profile 的版本、术语、数字和限制一致。
7. 所有外部来源、AI 使用、隐私数据、许可证和未完成项已披露；材料集成人、M10 和课程要求的 Review/签收真实完成。

没有证据的项目保持“待完成”或“阻塞”，不通过口头确认关闭 Issue。

每日版本通知与完整功能/用户任务目录见 [升级验收工作流](../../../workflows/version-acceptance.md)，本组每日 Git 操作见 [WORKFLOW.md](./WORKFLOW.md)。
