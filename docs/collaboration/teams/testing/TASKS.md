# CampusLoop 独立测试与验收组任务书

版本：1.4；日期：2026-10-27。组员自行认领，本文件不分配姓名。本组任务逐字提取总任务书相同章节，只保留本组具体岗位；共同交接规则保留。

## 课程交付约束

以下要求来自 `JC2001-GroupProjectDescription-and-Requirements-2026-27(1).pdf`，是本项目协作的硬约束：

- 项目计划书必须提交，但不计分；课程截止时间以 Blackboard 为准，团队不能自行猜测日期。
- 技术报告占总项目成绩的 50%。正文从 Introduction and Project Context 到 Conclusions and Future Work，要求 40 至 60 页；标题页、目录、图表目录、References 和 Appendix A 不计入正文页数。
- 技术报告按 A4、四边 2.54 cm 页边距、单栏、12 pt Arial 或 Times New Roman、1.5 倍行距排版，最终提交单个 PDF；报告不粘贴源代码，源代码放入 PoC 提交包。本内部中文协作规划使用 OceanScope 风格的宋体正文与黑体标题，不作为课程英文报告模板。
- Proof-of-Concept 软件占 30%。提交包必须包含源代码、可运行版本、依赖或支持文件以及 8 至 12 页用户手册 PDF。
- 项目演示占 20%。课程要求一次 15 分钟演示，提交 PowerPoint 和 MP4；录像必须出现演示者本人，不能只录屏或用自动化录像代替真人讲解。
- 课程安排四次 Project Updates，至少提交三次。每次更新要写已完成工作、困难及处理方法、下一步，并且内容必须反映真实进度和与导师的讨论。
- 技术报告 Appendix A 必须附 Group Workload Profile。所有成员应在没有争议时签名；如不同意贡献评价，不应签名并应按课程要求联系课程负责人。贡献百分比必须有可量化证据，不能凭感觉填写。
- 所有外部代码、图、图片、数据、模型、算法和 AI 使用都要按学校要求说明来源和使用方式；不把自动生成内容当作成员独立贡献。

## 先看懂这些规则，再认领岗位

本版的数量是团队从现在开始执行的最低交付要求，不是课程另加的要求，也不表示仓库已存在这些产物。首次把基础包建好，以后每次大改只补受影响的用例、数据、章节和截图；不要求每天重新造 60 件商品、重写报告或再收一遍同样数据。一次发布验收仍须把完整目录核对一遍。数量达到但覆盖遗漏，仍然不合格。

- **软件版本 SHA**：所测代码的完整提交号；从 M10 通知复制。材料自己的 commit 另记，不能把两者混在一起。
- **虚构静态样例**：写在 JSON/CSV 或图片文件中的测试输入，例如“二手高数教材、售价 25 元”。只交这些文件，尚未证明系统功能正确。
- **真实接口测试**：将上述虚构样例通过被测 API 创建到专用测试库，再在页面操作并核对 API/数据库结果；数据是虚构的，接口和操作是真的。不得把商品硬编码到生产页面充数。
- **一条用例**：一次明确的前置、输入/动作、预期、实际与结论。改标题重复同一操作不能增加数量；同一用例换浏览器是两次执行，不是两个新用例。
- **岗位编号**：R1/R2、T1/T2/T3、U1/U2、D1/D2 是新岗位，不是原 M 编号。九人自行认领，本文不替组员分组。
- **交付文件**：下面列出的具体文件都由对应岗位唯一维护。需要其他人的内容时，对方先提交自己的文件，接收人汇总链接；不同时改一个共享文件。
- **状态**：通过、失败、阻塞、未执行、不适用五类分别记录。需要的功能缺失写失败/阻塞；只有范围明确排除并经 M10 登记，才能写不适用，不能为了凑通过数删用例。

目录中的 `<n>` 换成实际项目阶段，例如阶段五用 `phase-5`；`<变更ID>` 换成 M10 通知的编号，例如 `C20261027-02`。同一阶段内按变更 ID 分轮次，不创造“阶段六”。下列文件名是**要交的产物**，不是表示已经实现的命令或文件；接收前先核对存在与实际执行。

后文简写的 `changes/<变更ID>/文件名` 均位于 `docs/collaboration/phase-<n>/changes/<变更ID>/`；`testing/`、`experience/` 根目录分别是 `docs/collaboration/phase-<n>/testing/`、`docs/collaboration/phase-<n>/experience/`，不是仓库根目录。每轮日志追加变更 ID 和时间，执行 CSV 按运行一行追加，不能覆盖上轮失败/原始证据。

每个岗位都要交自己的 `task-log.md`、本轮 `delivery-checklist.md` 和非作者 Review 链接。交付清单逐个列文件、任务 ID、软件 SHA、实际结果、证据、未完成原因和接收人；缺的文件写待交，不能只发一句“已完成”。测试岗位另交 `daily-report.md`，每个工作日更新一次；严重故障立即报 M10。

## 本组具体交付

### 独立测试与验收组

长期组分支：`team/testing`。首次交付包括一套可复现虚构数据、126 条最低用例（T1 36、T2 60、T3 30），以及真实执行记录。126 是本轮团队最低覆盖计划，不是宣称都已通过；现有测试可以复用，但必须登记对应 ID、SHA 与实际结果。缺功能就记录缺陷，不能改预期掩盖。后续通知只重跑受影响用例、交易冒烟和相邻回归；发布候选完整核对。

#### T1 测试数据与账号权限

岗位分支：`work/testing/data-permissions` → PR 到 `team/testing`。先问 M10 要软件 SHA、专用审计环境地址、管理员初始化方式、数据允许写入范围；凭据私下获取，不能上传 GitHub。

##### 个人任务一：把虚构数据具体做出来

固定样例叫 `cl-functional-v1`。一个数据包包括以下数量，不能只交几张截图：

1. **8 个账号配置**：A 卖家、B 买家、C 竞争买家、D 非参与者、E 空资料/空列表学生、Z 禁用学生，共 6 个普通用户；另 R/S 两个管理员供重复/并发审核。A/B 可在别的交易互换买卖方。游客是不登录会话，过期是同一账号会话过期，都不另算账号。账号文件只存别名/测试角色；邮箱由专用测试域和运行前缀生成，密码运行时私下输入/生成，不写入样例。管理员由 M10 批准的初始化方式建立，Z 经管理接口禁用；没有能力时写阻塞，不能开后门或改生产权限。
2. **60 条商品输入**：P001–P048 为展示/搜索基础样例，6 个当前市场类别各 8 条：BOOKS 图书、DIGITAL 数码、DAILY 生活、SPORTS 运动、clothing 服饰、other 其他。P049–P060 为 12 个交易场景各留 1 件，类别各 2 条。输入只设合法待发布字段，不直接把状态写成已售。商品标题必须不同，不用“测试1”至“测试60”重复填充。
3. **商品每条写清字段和用途**：fixtureId、ownerAlias、title、description、category、condition、price、originalPrice、campusLocation、imageFixtureIds、caseIds。fixtureId/ownerAlias/imageFixtureIds/caseIds 是测试元数据，setup 要转换成真实 API 字段，不能原样发送触发 extra-forbid。图片先用当前卖家上传得到合法媒体键，再放进 images；其他卖家不能借用私有键。商品写成学生能理解的描述，如高数教材/键盘/台灯/羽毛球拍/外套/收纳盒；不使用真人联系资料。每类 8 条基础样例按 NEW/LIKE_NEW/GOOD/FAIR 各 2 条；每类价格设计 0.01、10、25、50、100、200、500、1000 元各 1 条，只作边界/筛选样例，不称市场真实价格；originalPrice 留 null 或合法且不低于售价。每类 4 条用 1 张图、4 条用 2 张图，12 件场景商品各至少 1 张图。当前契约要求 1–5 张图片，因此 60 条合法商品都带图；缺图/超量另归非法输入，不从 60 条里扣数。
4. **12 条求购输入**：W01–W12，8 条保持 OPEN，4 条创建后通过关闭接口变 CLOSED。每条给 title、description、budgetMin、budgetMax、condition、location、expireAt、ownerAlias、caseIds；8 条 OPEN 中：2 条预算边界刚好命中、2 条无匹配、2 条成色筛选、2 条地点筛选。到期时间按运行时生成未来时间，不能写死为已经过去的日期；过期状态在专项用例另测。当前求购写接口没有分类字段，类别意图写在标题/描述，不能凭空新增 category 参数。
5. **12 个图片/文件样例**：8 张自制或获许可的正常图片（4 JPEG、4 PNG），4 个故意非法的文件（伪装 jpg 的文本、截断图片、超限图片、禁止格式各 1）。每个登记用途、来源/许可、大小、MIME 与 SHA-256；大文件由生成器在本地生成，不把大二进制塞仓库。大小/数量上限从本轮 OpenAPI/服务配置读取，不擅自编一个上限。非法文件只用于拒绝测试，不当商品图片展示。
6. **24 条拒绝/边界输入**：商品 8 条（空标题、超长标题、负数价格、超精度价格、非法类别、非法成色、无图片、超限图片数量）；求购 8 条（空标题、预算为负、最小大于最大、非法成色、空地点、过去到期时间、非法日期、超长说明）；认证/交易 8 条（无效邮箱、重复邮箱、空密码、不合长度密码、空消息、超长消息、非正报价、过去见面时间）。每条给原请求、预期依据和映射用例；过去求购到期时间等是否应拒绝要先对照本轮需求/契约，若没有定义或实现不一致则标“待 M10 确认”并登记实际结果，不能把所有输入都先编成应拒绝。无图片属于已明确拒绝项。它们不计入 60 条合法商品。
7. **20 份 HTTP 模拟响应**：只供隔离组件测试，不接入生产路由。商品列表、商品详情、聊天列表、订单详情各 5 份，覆盖延迟加载、成功、空内容/不存在、服务失败、无权限。延迟由测试配置控制；详情的“空”按契约为 404，不编一个成功空对象。响应字段/错误信封取自同一 OpenAPI，标 MOCK_RESPONSE，不能拿这些证明 E2E/持久化通过。T1 只准备输入/响应，T3 执行组件/异常测试。
8. **30 条功能搜索查询**：Q01–Q30，每个商品类别 5 条，分别为精确名称、同义说法、用途描述、结构化筛选、无答案。每条给 query、filter（接口支持时）、预期可接受商品 fixtureId 或应为空、依据、caseIds；人工核对商品事实，不看候选排名倒填答案。这是构造数据上的功能检查，不是正式模型评估。
9. **24 条价格输入和 12 条信誉/风险事实样例**：价格每类 4 条，分别正常、低价/高价边界、字段不足、非法字段；单独标注预期规则/不可用/拒绝的依据。信誉/风险按“无交易、正常完成评价、有取消/举报事实、服务不可用”四组各 3 条，给脱敏虚构事实与允许输出/禁止输出。规则服务输入按当前 M8 schema 映射；只能测规则、权限与降级，不为这些合成数据填写 L3 或真实成交价标签。

**商品文件中的一条应该这样写**（仅示例结构，尚未导入，也不是已完成数据）：

```json
{
  "fixtureId": "P001", "ownerAlias": "A",
  "title": "九成新高等数学上册", "description": "测试教材，少量铅笔笔记，无缺页。",
  "category": "BOOKS", "condition": "LIKE_NEW",
  "price": 25, "originalPrice": 49, "campusLocation": "图书馆门口",
  "imageFixtureIds": ["M01"], "caseIds": ["T2-C07", "T2-C01"]
}
```

T1 为其他条目填不同的真实测试内容和对应配额；M01 只是正常图片模板别名，setup 要以 A 身份上传后替换成接口需要的真实 images 数组。不要把 M01 或 fixtureId 当数据库 ID 发送。

**一条搜索功能样例**也要带答案依据，不能只有一句查询：`Q01`，query="高等数学教材"，filters={category:"BOOKS"}，acceptableProductFixtureIds=["P001", 其他已核对同类教材]，reason="标题和描述满足教材需求且分类正确"，caseIds=["T2-C04"]。无答案样例的 acceptableProductFixtureIds 为空，并写核对过完整商品快照；同义/用途类样例记录关键词基线与候选各自预期/限制，不强迫关键词基线实现语义理解。价格/信誉样例同样必须有 expected 和依据字段，而不是只交随机数字。

所有文件里的输入只是一套样例定义。T1 负责把账号、普通商品、求购和媒体准备到专用 API；T2 负责通过真实业务操作生成会话、消息、报价、订单、评价、通知和举报，不能让 T1 手写一批“已完成订单”直接插库。60 条是商品输入数，实际成功创建/拒绝数必须另报，不能用静态文件行数冒充数据库记录数。

##### 个人任务二：生成、复位、映射与隔离

同一套样例可复用，但运行时至少支持 `permission`、`business`、`environment`、`experience`、`demo` 五种命名空间；只为本次接收人按需建立，不要求五份同时运行。不同空间的账号/商品互不共用。T1 交一份定义，T2/T3/U2 各在自己的空间导入，不算重复采集数据。相同场景第二次执行要先只复位自己的空间或用新 runId，不能重用已售商品导致下轮交易无法开始。

数据交接分两批，避免互相等待：T1 先交可导入的账号/商品/求购/媒体基础包，不需要先测完所有 36 条；T2 收到就能开始建交易场景。T1 要测试订单/聊天/举报越权时，再按 T2 已交付的合法场景配方，在 permission 空间创建前置；不会执行的部分点名请 T2 指导/运行配方，T1 仍自行执行权限判断和记录。不得让 T1 等 T2 的订单、T2 又等 T1 的全部权限通过。

`setup_data.py` 要先核对目标 API、专用库标识、媒体范围和 Redis DB14/15，再创建样例并保存 fixtureId→真实资源 ID 的本地运行清单；重复运行同一前缀不得新增重复事实。`reset_data.py` 默认先 dry-run 列出本前缀资源，只清理自己的测试数据；有关联无法安全删时，改用新前缀或由 M10 提供专用环境复位办法，不能全库清空。禁止写入 daily `campusloop-local`。`verify_data.py` 统计输入数、创建/拒绝/阻塞数、引用完整性与哈希；运行账号凭据和私密响应不提交。

##### 个人任务三：36 条账号与权限用例

每个编号分别编写步骤、预期、实际，不是只交下面的标题。每组 6 条，共 36 条：

- **T1-C01–C06 注册**：合法注册；重复邮箱；非法邮箱；空密码；密码长度边界；注册失败后重试且无重复账号。
- **T1-C07–C12 会话**：正确登录；错误密码；禁用账号拒绝；退出后受保护请求拒绝；刷新恢复本人；过期会话按提示恢复/重新登录。
- **T1-C13–C18 本人与角色**：本人资料修改持久化；不可改字段拒绝；公开资料无邮箱/令牌；普通用户访问管理员 API 拒绝；游客可公开浏览；游客收藏/发布需登录且保留返回目标。
- **T1-C19–C24 对象归属**：D 不能编辑 A 商品；D 不能编辑/关闭 B 求购；D 不能读 A/B 私聊；D 不能读 A/B 订单；D 不能读见面私密信息；A 不能购买自己的商品。
- **T1-C25–C30 举报证据**：举报人可查本人记录；无关用户不能读记录/附件；普通用户不能处理举报；管理员合法查看有审计；聊天证据须有关联授权；公开信誉不返回内部风险/私密事实。
- **T1-C31–C36 账户切换与隔离**：多标签切换账号不会串身份；刷新令牌/会话失效；未带凭据的保护接口拒绝；过期/伪造令牌拒绝；媒体私有 URL 无授权拒绝；换命名空间复位不删除他人资源。

##### 个人任务一：12 个能重走的业务场景

为 P049–P060 各写 1 个场景，动作必须按本轮服务状态机实现，不直接改订单状态：

1. **S01 咨询**：B 联系 A 的商品，建立 1 个会话，双方各发 2 条非空文本。
2. **S02 待处理报价**：B 发有效报价，A 看见待处理；同一请求重试不重复。
3. **S03 还价**：A 对 B 报价还价，双方状态一致；记录原报价与新报价 ID。
4. **S04 拒绝**：A 拒绝报价，不能再接受同一失效报价。
5. **S05 接受与唯一订单**：A 接受 B 报价，商品被占用，只有 1 个有效订单，C 不能再买同件。
6. **S06 见面约定**：双方确认同一版本的未来时间和校内公共地点，刷新后仍在。
7. **S07 单方完成**：一方确认完成后，订单不能提前算双方完成，不能提前评价。
8. **S08 双方完成评价**：另一方完成后商品已售、订单完成，买卖双方各评价 1 次，重复评价拒绝。
9. **S09 取消**：按合法前置取消，订单不允许继续完成/正常评价，商品状态按契约恢复。
10. **S10 举报与处理**：完成至少 4 份举报，分别针对 USER、PRODUCT、ORDER、CHAT_MESSAGE；由专用管理员处理后举报人查结果，无关人不能看私密证据。只有当前接口支持的审核动作才执行。
11. **S11 过去时间拒绝**：提交过去见面时间失败，原约定/订单不被写坏；未来时间可继续。
12. **S12 旧版本确认失效**：修改约定得到新版本，旧确认不能误算新版本已确认，双方需按新版本操作。

S01–S12 每项独立留前置/数据/动作配方，不要求全在一个永久快照中保持。至少实际建立 6 个会话、发送 24 条人工测试文本（每个会话双方各 2 条）、8 个收藏关系、1 笔双边完成且有 2 条评价的交易和上述 4 份举报；不足时补独立场景副本并列清 ID。报价、订单、通知数量由实际动作产生，逐项统计，不手工插入通知或订单充数。S10 的管理员操作使用 business 空间，T1 的权限专项用另一空间，不争用账号。

每个真实故障单独建 Issue，填软件 SHA、环境/数据、账号别名/对象 ID、最短复现、预期依据、实际结果和脱敏证据。M10 回复“接受并修复/需补证据/暂缓及理由”，修复 PR 用 `Refs #缺陷号`，推送新软件 SHA 和回归范围。原执行人在新 SHA 跑原用例与相邻回归，在缺陷 Issue 写结果；T2 才更新汇总状态。没有原执行人复测，M10 不能替他写“已确认”，PR 合并不自动等于缺陷关闭。

### 第四步：T2 交通过的任务 → U2 分给 U1

T2 发 `business-journeys/user-handoff.md`，逐项写 U01–U08 哪些可做、通过用例/证据、软件 SHA、experience 空间导入入口、角色别名、数据 ID、已知限制。U2 先确认能打开首页、登录专用账号、查看一件指定商品，再在 #129 回复接收结果，并分给 U1 的学生任务与自己的管理/安装任务。

U1 不必等 U06 管理页修好才能体验 U01 浏览；被阻塞的任务写明对应缺陷，其他任务继续。U1/U2 的观察与任务由真人记录，体验步骤不能用脚本替代。测试组修正错误数据由 T1 交接；软件坏了找 M10；难用问题建体验 Issue，不能丢给文书组修改一句话代替修功能。

### 第五步：用户组交问题 → M10 处置 → 原体验人确认

U1 给 U2 自己的任务/截图/反馈链接，U2 在 `changes/<变更ID>/user-summary.md` 按任务列完成/失败/阻塞、入口卡点、问题 Issue、手册和截图 PR。M10 在每条 Issue 写接受修复、后续处理或不采纳及理由；接受项修后由原体验人重走任务，后续处理给负责人/影响/再检查日期。U2 汇总处置，不替 U1 填“体验已通过”。

### 第六步：T2/U2/M10 交事实 → R1/R2 更新报告

T2 给报告的包是测试汇总、用例与原始日志链接、数据规模、已修/未修、实际指标或未评估原因；U2 给的是手册 PR、截图索引、真实任务观察/限制；M10 给的是代码/契约变更、版本和技术限制。R1 回复“收到哪些证据、要改哪些 REQ/章节、仍缺什么”；R2 据此核对图/链路/方法，R1 写测试/体验结论和总稿，两人各提交自己文件的 PR。

R1 报告中的数字请原测试岗位复核，技术说明请 M10 复核，截图请 U2 复核；这些可以在同一个 PR 留具体评论，不要求所有人同时改报告。没等到结果的段落保留待验证，其他章节可以先合草稿，不能要求所有测试通过后才允许写任何文档。最终“通过”结论必须对应实际证据。

### 第七步：前三组交稳定资料 → D2/D1 最终演示

R1 交最终报告/需求/结论和限制，T2 交已复测主链路/边界/降级的操作配方，U2 交同版本截图/手册/demo 数据计划。D2 回复缺少的场景或数据 ID，D1 核所有数字/截图来源。M10 在 #129 明确“冻结软件 SHA、允许最终演示的范围、仍有限制”；没冻结只能写草稿，不能录最终版。

D2 组织第 1 轮彩排，失败建 Issue 交 M10，测试/原体验人复测，D1/D2 各修自己的 PPT/脚本，再做第 2 轮，之后录真人出镜 MP4。紧急 UI/代码变更影响哪个环节，就补测和重录那个环节；不把旧图静默塞进新版本。

### 第八步：各组 PR → 接收 Review → M10 收口

个人 `work/*` PR 到本组 `team/*`，同组另一人按任务书核对实际文件/数量/内容；跨组接收人只评论或给接收记录，不能直接推别人分支。组联络人汇总自己的组 PR，目标按本轮 notice 写明（当前阶段集成或已收口后的 main），写软件 SHA、材料 commit、结果和缺口。阶段材料可以引用已合并到另一个组分支的原文件链接，不能互相复制后双份维护。

M10 检查核心流程和技术边界，各组确认自己的材料已更新；有失败/阻塞继续开放，不因为到了周末或 PR 合并就关闭 #129。课程提交由指定人实际操作 Blackboard，D1/D2 登记文件/回执；GitHub PR 不能代替学校提交、成员签名或独立验收。

### 大改动后每个岗位具体补什么

- T1：接口字段/权限变了，更新对应 JSON/模拟响应/非法输入/36 条权限例中相关项，跑生成/核对，交 T2 数据影响摘要。
- T2：按钮/状态/主流程变了，更新 S01–S12 和受影响的 60 条业务例，测完整交易冒烟，发新 user-handoff 和测试汇总。
- T3：端口/部署/模型/并发/故障变了，补对应环境/恢复/性能/模型或路由格，保留原失败与新日志；不必每改一句文案都跑 900 请求。
- U1：改了哪些学生操作/文字/布局，就重走相关任务并换对应截图/手册步骤，写旧图属于哪个版本。
- U2：更新管理/部署说明、汇总截图索引、体验处置和 demo 计划，交 R1/D2；不覆盖 U1 原图。
- R2：更新受影响链路、图和技术/智能说明；R1 更新需求追踪、测试数字、限制、总稿并重新导出受影响版本。
- D1/D2：冻结前只改草稿/来源/影响记录；冻结后变更演示路径才重测、修 PPT/讲稿、重录受影响部分。
