### T3-C04 健康与就绪接口在依赖异常时的表现
- **实现依据**：`backend/app/api/routes/system.py`。`GET /health` 恒返回 200，响应体为
  `{"code":0,"message":"ok","data":{"status":"ok"|"degraded","dependencies":{"database":…,"redis":…}}}`；
  `GET /ready` 结构相同，`degraded` 时返回 503。依赖探测范围**只有 database 与 redis**，媒体服务不在其中。
  Worker 另有 `GET /healthz`（200=健康 / 503=异常，判据为主循环心跳新鲜且队列可达）。
- **前置条件**：服务已启动，审计环境可用
- **步骤**：① 停止数据库 → 请求 `/health`、`/ready`；② 恢复后停止 Redis → 重复请求；③ 停机期间请求 worker `/healthz`；④ 停止媒体服务 → 再请求三个端点
- **预期**：
  - 停库：`/health` 返回 200 且 `status=degraded`、`dependencies.database=unavailable`；`/ready` 返回 503
  - 停 Redis：同上，`dependencies.redis=unavailable`
  - Worker：`/healthz` 在心跳中断或队列不可达时返回 503 并附原因
  - 停媒体：`/health` 与 `/ready` 仍为 `ok`。这是当前探测范围的既有事实，**记为范围限制**（媒体可用性由 C10、C27 用真实图片请求覆盖），不判为“虚假健康”，也不判为程序错误
- **证据要求**：四个场景下各端点的响应码与响应体原文；媒体未纳入探测范围的结论写入 `environment.md`
- **实际结果**：未执行

### T3-C05 界面、接口与 Worker 版本一致

- **前置条件**：同一提交部署的前端、API、Worker
- **步骤**：记录前端构建来源、`/openapi.json` 的 `info.version`、Worker 启动日志中的 version，并对照部署所用提交 SHA
- **预期**：三者能对应到同一提交；不一致时能判断出是遗留进程还是构建产物过期
- **证据要求**：三处版本原文、`git rev-parse HEAD`；若未实现统一版本号接口，如实记为范围限制

## 并发与安全（C19–C24）

### T3-C19 两买家竞争同一商品（三轮）
- **实现依据**：系统没有独立的“直接下单”接口，订单只由卖家接受报价产生：接受时报价置 `ACCEPTED`、商品置 `RESERVED`、
  同时创建 `status=PENDING_CONFIRM` 的订单（`backend/app/api/routes/transactions.py`）。成交还需后续约定与双方确认，
  **因此本用例只判定“是否只产生一条有效订单”，不断言“已成交完成”**。
- **前置条件**：每轮准备一个 `ON_SALE` 商品，两个买家各建一条有效报价，卖家可并发接受
- **步骤**：连续 3 轮，每轮同时接受两条报价，记录两次响应与最终状态；每轮使用新的商品与买家
- **预期**：每轮只有一条报价被接受并产生**一条** `PENDING_CONFIRM` 订单；另一条返回明确的冲突错误；商品为 `RESERVED`；
  订单与商品状态一致，不出现一商品多有效订单
- **证据要求**：三轮的请求与响应、最终订单数、商品状态、卖家库存一致性；按模板写入 `concurrency.md`
- **实际结果**：未执行

### T3-C20 幂等重试不产生重复记录
- **实现依据**：写接口支持 `Idempotency-Key` 请求头（报价创建/接受/还价、约定保存/确认、完成确认、评价、举报等）。
- **前置条件**：可获得成功响应的业务动作
- **步骤**：携带同一 `Idempotency-Key` 连续提交两次同一请求；再验证不带该头重复提交时的实际表现
- **预期**：带同一键的重复请求只产生一条业务记录并返回确定结果；不带键时的行为按实际契约记录（有唯一约束则返回冲突，无则为缺口）
- **证据要求**：两次响应、记录数量、最终对象状态
- **实际结果**：未执行

- **预期**：生成结果与仓库内产物一致（无未提交漂移），类型检查通过；若存在漂移，记录漂移条目与影响

### T3-C23 Cookie、CORS 与跨域请求按实际契约验证
- **实现依据**：刷新令牌走 Cookie，属性为 `HttpOnly`、`SameSite=Strict`、`Path=/`、按环境启用 `Secure`；
  访问令牌走 `Authorization: Bearer`。CORS 为白名单 `settings.cors_origin_list`，`allow_credentials=True`。
  **当前未实现独立 CSRF token**，跨站写保护依赖 `SameSite=Strict`。
- **前置条件**：可构造跨域与第三方页面发起的请求
- **步骤**：检查刷新 Cookie 的实际属性；用非白名单来源发起预检与实际请求；在第三方页面发起写操作
- **预期**：Cookie 属性与上述实现一致；非白名单来源被 CORS 拒绝；跨站写请求因 `SameSite=Strict` 不携带凭据而失败。
  未实现独立 CSRF token 记为**范围限制**，不作为失败判定
- **证据要求**：响应头原文（Cookie 属性）、预检响应、跨站请求结果
- **实际结果**：未执行

- **证据要求**：检索命令、命中结果（命中即登记缺陷，原文脱敏后再贴）
- **实际结果**：未执行
