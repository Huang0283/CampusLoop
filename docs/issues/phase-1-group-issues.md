# CampusLoop AI 第一阶段 GitHub Issues

> 阶段定义：第 1-2 周（Requirements Validation / 第一次汇报前）  
> 建议 Milestone：`Phase 1 - Requirements Validation`  
> 统一截止：第 2 周周五或第一次汇报前，以教师通知为准  
> 本阶段目标：锁定“做什么、谁负责、如何验收”，不把尚未开发的功能描述为已经完成。

## 创建前统一设置

- 建议 Labels：`phase-1`、`requirements`、`priority:P0`，再添加对应小组标签。
- Assignees：至少设置组内负责人；其他成员可同时设为 Assignee，或在正文中保留唯一任务归属。
- 每项子任务必须有负责人、产物位置和验收证据，不能只写“已讨论”。
- 阻塞超过半天，在 Issue 中留言说明阻塞项、影响范围、需要谁处理和预计恢复时间。
- 影响其他组的字段、状态、目录或接口决定，必须在当天同步到对应 Issue。
- 第一阶段所有文档均为候选版；全员评审通过后，才由 M1 标记为需求基线。

# Issue 1：项目管理与质量组

## 阶段信息

- 阶段：第 1-2 周
- 小组：项目管理与质量组
- 成员：M1、M10
- 项目负责人：M1
- 质量负责人：M10
- 截止时间：第一次汇报前
- 依赖：M2-M9 提交各组边界、负责人、风险和阶段产物

## 小组目标

把项目说明转换为可追踪、可验收、适合十人在十周内完成的需求候选基线，并建立计划、风险、变更、会议、测试和汇报管理机制。

本阶段只形成需求候选版，不宣布正式冻结；未实际完成的功能不得写成已实现。

---

## 分支与合并要求

- 小组集成分支：`phase1/management-quality`。
- 分支负责人：M1；合并复核：M10。
- M1 从最新 `main` 创建并推送小组集成分支，并把远程分支链接填写到本 Issue。
- M1、M10 的具体交付使用独立任务分支，命名为 `task/<成员编号>-<简短任务>`，例如 `task/m1-project-scope`、`task/m10-test-strategy`。
- 任务分支从 `phase1/management-quality` 创建，完成后通过 Pull Request 合并回小组集成分支。
- 禁止直接向 `main` 或小组集成分支提交；共享小组分支禁止 force-push 和变基改写历史。
- 文档涉及其他组的负责人、边界、接口或验收条件时，必须邀请对应小组负责人参加评审。
- 小组材料通过内部复核后，由 M1 从 `phase1/management-quality` 向 `main` 提交汇总 Pull Request，M10 复核文档完整性和状态表述。

# Issue 2：前端体验组

## 阶段信息

- 阶段：第 1-2 周
- 小组：前端体验组
- 成员：M2、M3、M4
- 组内负责人：M2
- 截止时间：第一次汇报前
- 依赖：M1 提供功能范围；M5/M6 提供权限、实体和状态候选；M7/M8 提供智能结果字段

## 小组目标

梳理学生端和管理端的页面范围，完成核心用户流程、信息架构和低保真原型，为下一阶段的可点击原型、组件规范和接口设计提供依据。

本阶段不要求完成正式业务页面。现有 React 路由和占位页面不能视为功能已经完成。

---

## 分支与合并要求

- 小组集成分支：`phase1/frontend-experience`。
- 分支负责人：M2；交叉评审：M3、M4；范围复核：M1；可测试性复核：M10。
- M2 从最新 `main` 创建并推送小组集成分支，并把远程分支链接填写到本 Issue。
- 个人任务分支命名为 `task/<成员编号>-<简短任务>`，例如 `task/m2-navigation-audit`、`task/m3-market-wireframes`、`task/m4-transaction-flow`。
- 任务分支从 `phase1/frontend-experience` 创建，完成后通过 Pull Request 合并回小组集成分支。
- 禁止直接向 `main` 或小组集成分支提交；共享小组分支禁止 force-push 和变基改写历史。
- 公共路由、公共组件、权限和术语变更必须由另一名前端成员评审；涉及业务状态或接口字段时必须邀请对应后端或智能功能负责人评审。
- 小组交付通过交叉评审后，由 M2 从 `phase1/frontend-experience` 向 `main` 提交汇总 Pull Request。

## 本阶段不做

- 不训练或承诺复杂模型，不把 Isolation Forest 纳入 MVP。
- 不抓取许可不明的数据，不使用个人敏感信息进行实验。
- 不把相似度解释为成交概率，不把挂牌价直接视为真实成交价。
- 不允许智能服务成为商品发布、浏览、聊天或交易的硬依赖。
- 不为汇报美观而生成虚假的模型指标、样本规模或对比结果。
