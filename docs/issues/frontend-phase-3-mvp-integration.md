# FE-P3 MVP 真实接口联调

## 阶段信息

- 周次：第 5-6 周；截止：第三次汇报前。
- 成员：M2、M3、M4；组内负责人：M2。
- 集成分支：`phase3/frontend-mvp`。
- 任务分支：`task/m2-p3-auth-integration`、`task/m3-p3-market-integration`、`task/m4-p3-transaction-integration`；PR 目标：`phase3/frontend-mvp`。
- 证据目录：`docs/evidence/phase-3/frontend/`。
- 输入门禁：FE-P2 原型/映射冻结；BP-P2 契约和环境可用；M10 场景已编号。
- 输出去向：MQ-P3 双账号验收、FE-P4 智能/后台集成。

## 阶段完成结果

将 Phase 2 原型中的 MVP Mock 替换为真实 HTTP/WebSocket 接口，完成账号、商品和交易闭环。成功必须来自服务端响应和持久化结果；前端不得直接修改订单事实。

## 接入前置条件

- M2 仅在 M5 的认证接口通过契约测试并提供测试账号/错误样例后标记真实联调开始。
- M3 仅在 M6 的商品/求购接口和 M9 的上传环境可复现后标记真实联调开始。
- M4 仅在 M6 的聊天 API/WebSocket、交易状态机和测试数据可用后标记真实联调开始。
- 上游未就绪时可继续完成 Mock UI，但任务状态必须为“待联调”，不得计入本 Issue 关闭条件。
- M10 只在服务端证据、前端接入和持久化结果同时存在时判定场景通过。

## 联调纪律

- [ ] 接口与契约不一致时登记差异并由 M5/M6 决定，不在前端长期兼容猜测字段。
- [ ] Mock 仅允许在明确开发开关下存在，页面标识且不计入验收。
- [ ] 每次状态变更后重新读取或采用服务端权威响应，不自行推进订单状态。
- [ ] 上传、聊天和交易失败必须保留用户可恢复路径。
- [ ] 日志、提示和截图不得包含令牌、邮箱、私聊全文或举报证据。
