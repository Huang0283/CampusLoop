# FE-P3 MVP 真实接口联调

## 阶段信息

- 周次：第 5-6 周；截止：第三次汇报前。
- 成员：M2、M3、M4；组内负责人：M2。
- 证据目录：`docs/evidence/phase-3/frontend/`。
- 输入门禁：FE-P2 原型/映射冻结；BP-P2 契约和环境可用；M10 场景已编号。
- 输出去向：MQ-P3 双账号验收、FE-P4 智能/后台集成。

## 小组目标

将 Phase 2 原型中的 MVP Mock 替换为真实 HTTP/WebSocket 接口，完成账号、商品和交易闭环。成功必须来自服务端响应和持久化结果；前端不得直接修改订单事实。

## 联调纪律

- [ ] 接口与契约不一致时登记差异并由 M5/M6 决定，不在前端长期兼容猜测字段。
- [ ] Mock 仅允许在明确开发开关下存在，页面标识且不计入验收。
- [ ] 每次状态变更后重新读取或采用服务端权威响应，不自行推进订单状态。
- [ ] 上传、聊天和交易失败必须保留用户可恢复路径。
- [ ] 日志、提示和截图不得包含令牌、邮箱、私聊全文或举报证据。

## 小组验收标准

- [ ] 刷新页面后登录态和持久化业务数据仍正确。
- [ ] 两账号可完成发布 -> 搜索 -> 聊天 -> 报价 -> 订单 -> 约定 -> 双方完成 -> 评价。
- [ ] 未完成/取消订单无法评价；非参与者无法读取私聊或修改交易。
- [ ] WebSocket 断开后有提示，重连/补拉不产生重复消息。
- [ ] 重复点击关键提交不会产生重复订单、确认或评价。
- [ ] 每个 MVP 页面五类状态已实现或写明不适用原因。
- [ ] `npm run lint` 和 `npm run build` 通过；关键 UI 测试通过。

## 本阶段不做

- 不提前实现未进入 MVP 的高级推荐、动画或运营报表。
- 不把静态成功提示、localStorage 业务事实或控制台输出算真实联调。
