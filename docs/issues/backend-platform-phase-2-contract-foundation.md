# BP-P2 API、数据库与统一环境基线

## 阶段信息

- 周次：第 2 周；截止：第二次汇报前。
- 成员：M5、M6、M9；业务主责：M6；平台主责：M9。
- 证据目录：`docs/evidence/phase-2/backend-platform/`。
- 输入门禁：BP-P1 领域候选完成；需求/页面字段/智能资源需求可用。
- 输出去向：BP-P3、FE-P3、AI-P3、MQ-P2 测试基线。

## 小组目标

建立可启动的 FastAPI/PostgreSQL 基础工程、首版迁移、种子数据、API 契约和 CI。所有 MVP 接口在实现前已明确权限、事务、幂等、错误码和测试场景；接口样例不得与数据库事实或前端字段冲突。

- 项目阶段集成分支：`phase2/integration`，由 M1 从上一阶段已验收的 `main` 创建。
- 小组集成分支：`phase2/backend-foundation`。
- 分支负责人：M5；组内交叉评审：M6、M9；范围复核：M1；可测试性复核：M10。
- M5 从最新 `phase2/integration` 创建并推送 `phase2/backend-foundation`，在本 Issue 中记录远程分支链接。

## 文件所有权与合并顺序

- M5 只维护认证契约输入和 `auth-contract.md`、`auth-security-design.md`；不得在个人 PR 中直接改写 `openapi/campusloop.v1.yaml`。
- M6 是 `openapi/campusloop.v1.yaml` 的唯一维护人，先合入 M5 Review 通过的认证字段，再合入业务接口、状态和错误结构；只有 M6 在 canonical OpenAPI 合并后执行 `npm run sdk:generate`。
- `frontend/src/sdk/generated/` 是生成产物，M6 负责生成并登记提交号；M2/M3/M4 只能消费和验证，不得手工改写。
- M9 独占模型、迁移、索引、种子、Compose 和 CI 运行文件；M5/M6 通过迁移需求文档提出变更，由 M9 在同一小组分支落盘。
- 合并顺序固定为 M5 -> M6 -> M9；每一步合并后下一位负责人先同步 `phase2/backend-foundation` 再提交 PR。

## 本阶段小闭环

本周由后端与平台组完成“领域规则、接口/持久化、运行环境和服务端证据”的最小可验收闭环。只有本节的输入、结果、证据和交接均已记录，才允许把本 Issue 标记为本组完成。

### 输入确认

- 本阶段输入：对应 Phase 1 已关闭 Issue 的交付物、提交号和遗留清单；所有输入必须可从阶段集成提交检出。
- 本组本周工作边界：只处理本文件“个人任务”和“小组共同任务”列出的范围；未列出的新需求不得借本 Issue 关闭。
- 输入不完整时：在证据目录的 `handoff.md` 写明阻塞事项、上游 Owner、下游 Owner、当前可做内容和不能验收内容；不得用猜测字段、临时数据或口头确认代替输入。

### 本周可验收结果

- 最小结果：冻结可消费的设计基线：页面原型/组件、API/数据库/环境契约、数据评估或测试契约；Mock、样例或骨架必须明确标注，不能算真实业务完成。
- 验收动作：由非作者从阶段集成提交检出，按本 Issue 的任务 ID 找到交付文件，执行文档中的命令或场景，并分别记录成功、失败、权限/状态边界。
- 证据要求：保存成功/失败样例、版本号、差异决策、启动命令和契约测试结果，确保下一阶段不需要猜测字段或状态。 证据至少包含提交号、运行环境、命令或操作步骤、实际结果和失败时的日志/截图路径。

### 输出与下一阶段交接

- 输出位置：源码、测试和迁移保留在所属目录；阶段证据统一写入 `docs/evidence/phase-2/backend-platform/`，至少包含 `deliverables.md`、`verification.md` 和 `handoff.md`。
- 接收人和动作：下一阶段实现负责人同步 phase2/integration 的收口提交，按接收清单逐项验证契约、样例和环境。
- 接收清单必须列出：输出文件/提交号、接收人、接收动作、验收命令或场景、接收结论；任何未完成项都要写明 Owner、依赖人、影响、下一动作和明确截止时间。
