## T2：业务旅程与后台治理

岗位分支 `work/testing/business-journeys`。T2 负责主要端到端业务执行，共 84 条计划用例，并负责统一本组总结果和用户组可用流程清单。收到 T1 第一批基础数据即可开始，不必等待 T1 全部权限用例完成；权限专项需要交易/举报前置时，T1 按 T2 已确认的合法场景配方另行执行。

必须覆盖的后台联动链：

1. 举报人提交举报 → 管理员查看并处理或驳回、填写原因 → 举报人刷新后回看状态/通知 → 核对审计记录和证据权限。
2. 管理员禁用用户 → 学生端验证登录、权限和商品可见性变化 → 管理员恢复用户 → 再验证恢复结果。
3. 管理员治理商品下架 → 学生端市场及搜索确认商品变化 → 恢复商品 → 再确认展示状态。

举报处理不自动封号或下架商品；如要禁用用户或治理商品，需分别执行相应操作。若现有版本没有仲裁、公告、待审核等功能入口，记录为范围限制/缺口，不编造操作。

## 接收与缺陷处理流程

1. T1 先将数据说明、样例和导入脚本交给 T2/T3；接收人独立导入并回复数据版本、环境、成功/失败和缺少项。T1 的权限用例可以继续进行，不阻塞 T2 建业务场景。
2. T2 将业务配方交 T1，用于权限边界前置；T1 回复接受的场景 ID。各岗位使用隔离数据空间，避免覆盖彼此结果。
3. T2/T3 只把已通过、写明 SHA 的用户流程交 U1/U2；失败项用缺陷 Issue 交 M10，列复现步骤、实际/期望、证据和影响。M10 的修复 PR 合入后，原执行岗位按同一用例复测；修复合并不等于缺陷关闭。
4. T2 每轮更新汇总，交 R1/R2（真实报告结论）、U2（手册验证）、D1/D2（冻结演示流程）和 M10（修复/限制）。接收人逐项回复接受或缺少什么。
5. 非作者 Review 个人 PR；T2 汇总到 `team/testing`，组联络人再开 PR 到 `main`。不得直推 main 或回已关闭的阶段集成分支。
