# MQ-P2 需求与设计基线

## 阶段信息

- 周次：第 2 周；截止：第二次汇报前。
- 成员：M1、M10；主责：M1；质量门禁：M10。
- 证据目录：`docs/evidence/phase-2/management-quality/`。
- 输入门禁：四组 Phase 1 Issue 已关闭；候选需求、页面旅程、领域状态和智能可行性均有证据。
- 输出去向：四组 Phase 3 实现 Issue、第二次汇报和冻结后的追踪基线。

## 小组目标

需求、设计、测试和运行环境形成同一版本基线。任何 Phase 3 实现都能追溯到需求 ID、原型页面、API、数据结构和验收场景；尚未确认内容不得进入开发基线。

## 本阶段小闭环

本周由管理质量组完成“范围、追踪、阶段验收、缺陷和交接证据”的最小可验收闭环。只有本节的输入、结果、证据和交接均已记录，才允许把本 Issue 标记为本组完成。

### 输入确认

- 本阶段输入：对应 Phase 1 已关闭 Issue 的交付物、提交号和遗留清单；所有输入必须可从阶段集成提交检出。
- 本组本周工作边界：只处理本文件“个人任务”和“小组共同任务”列出的范围；未列出的新需求不得借本 Issue 关闭。
- 输入不完整时：在证据目录的 `handoff.md` 写明阻塞事项、上游 Owner、下游 Owner、当前可做内容和不能验收内容；不得用猜测字段、临时数据或口头确认代替输入。

### 本周可验收结果

- 最小结果：冻结可消费的设计基线：页面原型/组件、API/数据库/环境契约、数据评估或测试契约；Mock、样例或骨架必须明确标注，不能算真实业务完成。
- 验收动作：由非作者从阶段集成提交检出，按本 Issue 的任务 ID 找到交付文件，执行文档中的命令或场景，并分别记录成功、失败、权限/状态边界。
- 证据要求：保存成功/失败样例、版本号、差异决策、启动命令和契约测试结果，确保下一阶段不需要猜测字段或状态。 证据至少包含提交号、运行环境、命令或操作步骤、实际结果和失败时的日志/截图路径。

### 输出与下一阶段交接

- 输出位置：源码、测试和迁移保留在所属目录；阶段证据统一写入 `docs/evidence/phase-2/management-quality/`，至少包含 `deliverables.md`、`verification.md` 和 `handoff.md`。
- 接收人和动作：下一阶段实现负责人同步 phase2/integration 的收口提交，按接收清单逐项验证契约、样例和环境。
- 接收清单必须列出：输出文件/提交号、接收人、接收动作、验收命令或场景、接收结论；任何未完成项都要写明 Owner、依赖人、影响、下一动作和明确截止时间。

### 单周关闭门禁

- [ ] 本周截止前，所有个人任务均有对应交付物和成员验收结果；未完成项已登记为阻塞或经 M1 正式移出范围。
- [ ] 小组任务 PR 已经由同组成员 Review，并合并到 `phase2/management-quality`；小组汇总 PR 已提交到 `phase2/integration`。
- [ ] M10 已在阶段集成提交上执行本组验收，M1 已确认范围、遗留项和下一阶段接收清单。
- [ ] 本阶段收口前，证据、提交号和交接记录不依赖未合并分支；未达到门禁不得关闭 Issue。
## 本阶段不做

- 不以设计评审代替实际实现，不宣称 MVP 已完成。
- 不在基线外追加 Stretch；不允许未确认 API/状态直接进入开发。

## Issue 关闭条件

- [ ] 每个 MVP 需求同时关联页面/接口或服务/数据/测试场景。
- [ ] 原型、API、数据库、智能输出中的同一字段和枚举没有冲突。
- [ ] 统一环境可按文档启动，健康检查结果有记录。
- [ ] 未决项均已延期或排除，不存在“开发时再看”。
- [ ] 需求变更必须经过 M1 决策、受影响 Owner 确认、M10 更新测试。
- [ ] M10 完成基线质量检查；M1 宣布基线版本及生效提交。
- [ ] 汇总 PR 合并；Phase 3 各组明确接收输入并可开始实现。
- [ ] Phase 2 阶段收口 PR 合并到 `main` 后，由该 PR 统一关闭本阶段四个 Issue。
