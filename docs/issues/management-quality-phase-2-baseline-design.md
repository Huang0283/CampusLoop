# MQ-P2 需求与设计基线

## 阶段信息

- 周次：第 3-4 周；截止：第二次汇报前。
- 成员：M1、M10；主责：M1；质量门禁：M10。
- 集成分支：`phase2/management-quality`。
- 输入门禁：四组 Phase 1 Issue 已关闭；候选需求、页面旅程、领域状态和智能可行性均有证据。
- 输出去向：四组 Phase 3 实现 Issue、第二次汇报和冻结后的追踪基线。

## 阶段完成结果

需求、设计、测试和运行环境形成同一版本基线。任何 Phase 3 实现都能追溯到需求 ID、原型页面、API、数据结构和验收场景；尚未确认内容不得进入开发基线。

## M1 任务

- [ ] 逐项处理 Phase 1 未决项，决策为纳入、延期或排除并记录理由。
- [ ] 冻结 MVP 需求基线版本，锁定业务术语、角色和核心状态名称。
- [ ] 更新追踪表，使每个 MVP 需求关联 FE/BP/AI 设计和测试场景。
- [ ] 组织页面、API、数据库、智能结果和测试场景联合评审。
- [ ] 审查四组 Phase 3 Issue，确保任务、Owner、依赖和验收能执行。
- [ ] 建立变更控制：申请人、原因、影响、决策、回滚和通知对象。
- [ ] 建立第二次汇报材料、讲解分工、演示顺序和问题答复表。
- [ ] 记录设计基线提交号和标签候选，禁止引用未合并任务分支。

## M10 任务

- [ ] 将冻结需求转换为编号化测试场景，覆盖主路径、权限、异常和边界。
- [ ] 为认证、商品、交易、智能降级定义测试数据和测试账号需求。
- [ ] 审查 API 错误码、状态机非法转换、权限矩阵和隐私字段是否可测。
- [ ] 审查前端原型是否覆盖加载、空数据、成功、失败、无权限设计。
- [ ] 审查智能评估集是否隔离、指标是否可计算、基线是否公平。
- [ ] 定义 Phase 3 CI 必跑检查及失败责任人。
- [ ] 执行第二次汇报前文档/环境/演示检查并形成问题关闭记录。

## 联合基线表

| 基线 | Owner | 必须包含 | 通过条件 |
|---|---|---|---|
| 需求基线 | M1 | ID、规则、优先级、Owner、验收、阶段 | 无无主需求；变更可追踪 |
| 页面原型 | M2 | 路由、角色、五类状态、字段、动作 | 核心旅程无设计断点 |
| API/领域 | M6 | 请求响应、权限、状态、错误、幂等 | 前端和测试共同确认 |
| 数据/环境 | M9 | 模型、迁移、种子、启动、健康检查 | 非作者可按说明启动 |
| 智能契约 | M7 | 输入输出、基线、版本、解释、降级 | 后端/前端/测试确认 |
| 测试基线 | M10 | 场景、数据、预期、层级、Owner | 可在 Phase 3 执行 |

## 协作顺序检查

- [ ] 每个前端消费项均指向一个明确的后端/智能契约 Owner，而不是只写“等待接口”。
- [ ] 每个契约先有成功/失败样例和契约测试，再允许下游标记“已对接”。
- [ ] Phase 2 的聊天、交易和智能页面只验收可点击 Mock 与字段一致性，不要求真实消息或真实模型结果。
- [ ] M10 将 Phase 2 原型验收与 Phase 3 真实联调验收分成不同场景 ID。
- [ ] 不存在 A 等 B、B 又等 A 的循环依赖；发现循环时由 M1 指定先交付契约的一方和日期。

## 必交产物

- [ ] 带版本号的 MVP 需求与追踪基线。
- [ ] 联合设计评审记录和全部问题处置结果。
- [ ] Phase 3 测试计划、账号/数据计划和 CI 门禁。
- [ ] 变更申请、决策和影响分析模板。
- [ ] 第二次汇报材料、彩排记录、设计基线提交号。
- [ ] 四组 Phase 3 Issue 的输入确认记录。

## 验收与关闭

- [ ] 每个 MVP 需求同时关联页面/接口或服务/数据/测试场景。
- [ ] 原型、API、数据库、智能输出中的同一字段和枚举没有冲突。
- [ ] 统一环境可按文档启动，健康检查结果有记录。
- [ ] 未决项均已延期或排除，不存在“开发时再看”。
- [ ] 需求变更必须经过 M1 决策、受影响 Owner 确认、M10 更新测试。
- [ ] M10 完成基线质量检查；M1 宣布基线版本及生效提交。
- [ ] 汇总 PR 合并；Phase 3 各组明确接收输入并可开始实现。

## 本阶段不做

- 不以设计评审代替实际实现，不宣称 MVP 已完成。
- 不在基线外追加 Stretch；不允许未确认 API/状态直接进入开发。
