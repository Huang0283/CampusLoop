## 阶段信息

- 阶段：第 1-2 周
- 小组：后端与平台组
- 成员：M5、M6、M9
- 业务负责人：M6
- 平台负责人：M9
- 截止时间：第一次汇报前
- 依赖：M1 提供功能范围；M2-M4 提供用户流程；M7-M8 提供数据与任务需求

## 小组目标

明确账号、商品、求购、交易和平台基础设施的边界，完成业务实体、权限矩阵、核心状态规则、系统架构及统一运行方案初稿。

本阶段产出设计候选，不代表接口、数据库、容器或持续集成已经完成。

---

## 分支与合并要求

- 小组集成分支：`phase1/backend-platform`。
- 分支负责人：M6（业务边界）与 M9（平台方案）；组内评审：M5/M6/M9 交叉评审。
- M6 或 M9 从最新 `main` 创建并推送小组集成分支，并把远程分支链接填写到本 Issue。
- 个人任务分支命名为 `task/<成员编号>-<简短任务>`，例如 `task/m5-auth-boundary`、`task/m6-domain-model`、`task/m9-runtime-plan`。
- 任务分支从 `phase1/backend-platform` 创建，完成后通过 Pull Request 合并回小组集成分支。
- 禁止直接向 `main` 或小组集成分支提交；共享小组分支禁止 force-push 和变基改写历史。
- 数据库、状态机、权限、接口错误和运行环境变更必须标明影响范围；涉及前端或智能服务时邀请对应负责人评审。
- 小组交付通过交叉评审后，由 M6/M9 从 `phase1/backend-platform` 向 `main` 提交汇总 Pull Request。

## M5：账号、用户与权限后端负责人

### 个人任务

- [ ] 定义账号、用户资料、角色、会话和模拟校园认证的业务边界。
- [ ] 定义普通用户和管理员的权限范围。
- [ ] 建立角色权限矩阵，覆盖未登录用户、普通用户和管理员。
- [ ] 区分公开字段、本人可见字段、管理员条件可见字段和禁止返回字段。
- [ ] 梳理注册、登录、令牌刷新、退出和资料修改流程。
- [ ] 定义账号重复、密码错误、令牌失效、账号禁用和无权限访问等异常。
- [ ] 明确密码保存、令牌保存和敏感字段保护要求。
- [ ] 梳理通知、评价汇总和信誉读取的账号侧职责。
- [ ] 识别接口限流、跨站请求保护和越权访问风险。
- [ ] 列出需要保存审计记录的管理员操作。
- [ ] 与 M2 核对登录态、权限路由、个人资料和管理员页面。
- [ ] 与 M8 核对信誉展示口径和风险信息可见范围。
- [ ] 为 M10 提供账号和权限测试场景。
- [ ] 从 `phase1/backend-platform` 建立 `task/m5-auth-boundary` 等任务分支，通过小型 PR 提交账号、权限与隐私边界材料。

### 个人交付物

- [ ] 账号与用户模块边界说明
- [ ] 角色权限矩阵
- [ ] 用户字段可见性清单
- [ ] 注册登录流程图
- [ ] 认证异常场景清单
- [ ] 安全与隐私要求清单
- [ ] 管理员审计操作清单
- [ ] 账号接口能力清单

### M5 验收标准

- [ ] 每个账号操作都明确允许角色和禁止角色。
- [ ] 邮箱、令牌、私密时间和举报证据不会作为公开字段返回。
- [ ] 登录失效、账号禁用和越权访问均有明确结果。
- [ ] 管理员查看敏感内容必须关联审核场景并记录审计信息。
- [ ] 前端能够根据权限矩阵设计登录和权限页面。

## M6：市场与交易后端负责人

### 个人任务

- [ ] 盘点商品、图片、收藏、求购、匹配、会话、消息、报价、订单、见面约定、评价和举报实体。
- [ ] 明确每个实体的创建者、参与者、管理员权限和生命周期。
- [ ] 绘制从商品发布到交易完成的完整业务流程。
- [ ] 起草商品状态机，包括草稿、在售、预留、已售、下架和删除。
- [ ] 起草求购状态机，包括开放、匹配中、关闭和过期。
- [ ] 起草报价状态机，包括待处理、接受、拒绝、撤回和过期。
- [ ] 起草订单状态机，包括待确认、待预约、已安排、已完成、已取消和争议。
- [ ] 起草见面约定状态，包括待确认、双方确认、修改和取消。
- [ ] 明确双方完成确认规则，不允许单方操作直接完成交易。
- [ ] 明确只有已完成交易才能评价，且每方只能评价一次。
- [ ] 标记需要事务、并发控制、幂等键和唯一约束的写操作。
- [ ] 标记需要不可变事件记录的订单和管理操作。
- [ ] 建立接口能力清单，记录调用角色、输入、输出和错误类别。
- [ ] 与 M3 核对商品、搜索、收藏和求购流程。
- [ ] 与 M4 核对聊天、议价、订单和见面约定流程。
- [ ] 与 M7 核对新商品或新求购触发匹配的业务事件。
- [ ] 从最新 `main` 创建并推送 `phase1/backend-platform`，在本 Issue 中记录远程分支链接。
- [ ] 建立市场与交易业务任务分支，并检查业务 PR 是否说明状态、权限、事务、幂等、并发和失败结果。

### 个人交付物

- [ ] 市场与交易模块边界说明
- [ ] 核心业务实体清单
- [ ] 完整交易业务流程图
- [ ] 商品与求购状态机
- [ ] 报价与订单状态机
- [ ] 见面约定状态机
- [ ] 事务与并发风险清单
- [ ] 幂等与唯一约束清单
- [ ] 接口能力候选清单
- [ ] 业务异常场景清单

### M6 验收标准

- [ ] 每个关键状态转换都有执行角色、前置条件和失败结果。
- [ ] 前端不能绕过后端直接修改交易状态。
- [ ] 并发接受报价、重复确认和重复评价有控制方案。
- [ ] 取消、争议和失败交易不会被计入正常完成记录。
- [ ] 基础交易流程不依赖智能服务才能运行。
- [ ] M3、M4 能根据业务规则继续完善页面原型。

## M9：数据库、环境与持续集成负责人

### 个人任务

- [ ] 绘制 React、FastAPI、PostgreSQL、Redis、对象存储和 AI Worker 的系统边界。
- [ ] 明确采用模块化单体架构，不在当前阶段拆分大量微服务。
- [ ] 根据 M5、M6 的实体清单绘制 ER 草图。
- [ ] 标记主键、外键、唯一约束、敏感字段、状态字段和审计字段。
- [ ] 明确数据库结构只能通过迁移脚本修改。
- [ ] 制定迁移命名、执行、检查和回滚原则。
- [ ] 盘点本地开发所需服务、软件版本和端口。
- [ ] 设计环境变量分类，区分普通配置和敏感配置。
- [ ] 明确真实密钥不得提交到仓库。
- [ ] 给出 Docker Compose 的阶段实现方案。
- [ ] 给出持续集成检查项目，包括格式、静态检查、测试和构建。
- [ ] 制定日志、备份、恢复和健康检查的候选方案。
- [ ] 明确 PostgreSQL 为业务事实来源，Redis 只用于缓存或临时状态。
- [ ] 与 M7 确认 pgvector、向量索引和后台任务需求。
- [ ] 与 M8 确认数据处理、模型运行和结果保存需求。
- [ ] 整理统一运行环境的风险与待确认问题。
- [ ] 建立数据库与运行方案任务分支，并检查相关 PR 是否包含迁移/回滚、配置分类、密钥排除和可重复运行说明。

### 个人交付物

- [ ] 系统上下文图
- [ ] 技术架构草图
- [ ] 核心 ER 草图
- [ ] 数据库约束清单
- [ ] 数据库迁移原则
- [ ] 本地开发服务清单
- [ ] 环境变量分类表
- [ ] Docker Compose 实施计划
- [ ] 持续集成实施计划
- [ ] 日志、备份与恢复方案初稿
- [ ] 平台风险和待确认问题清单

### M9 验收标准

- [ ] 每个核心实体都有明确的数据归属。
- [ ] 数据库、缓存、对象存储和智能结果的职责不混淆。
- [ ] 任何数据库结构修改都计划通过迁移脚本完成。
- [ ] 环境方案中不存在真实密钥或个人敏感信息。
- [ ] AI、Redis 或 WebSocket 不可用时，基础交易仍可继续。
- [ ] 方案能够支持后续在新电脑上建立统一运行环境。

## 小组共同任务

- [ ] 形成系统上下文图和模块责任表，明确哪些逻辑在后端、智能服务、前端和平台层。
- [ ] 建立统一术语表：商品、求购、匹配、报价、订单、见面约定、完成确认、评价、举报、风险线索。
- [ ] 识别至少 10 个高风险业务场景，例如越权修改、重复报价、并发接受、重复完成、无交易评价和举报证据越权。
- [ ] 评估 MVP 在 AI、Redis、对象存储或 WebSocket 不可用时的最低运行能力。
- [ ] 为第一次汇报准备业务实体、系统边界和运行方案摘要。
- [ ] M5/M6/M9 完成交叉评审后，由 M6/M9 提交小组汇总 Pull Request。
- [ ] 汇总 PR 合并后，在本 Issue 中记录任务 PR、汇总 PR、合并提交和最终文件路径，并删除已完成的远程分支。

## 本阶段不做

- 不冻结完整 API URL、数据库字段或索引；这些在第 3-4 周详细设计并评审。
- 不宣称 Docker、CI、备份恢复、权限或并发控制已经实现。
- 不拆分大量微服务，不引入 Kubernetes。
- 不实现真实支付、真实身份验证、物流或跨校交易。
- 不让智能模型直接修改交易事实、商品价格或用户封禁状态。
