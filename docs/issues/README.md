# CampusLoop 分阶段 Issue 索引与闭环规范

OpenAPI 契约、生成 SDK、前后端端口以及 Phase 1 至 Phase 5 的接力门禁统一见 `docs/api/openapi-sdk-stage-closure.md`。该文档只定义跨阶段交接，不替代各阶段 Issue 的成员 Review、跨组对签、M10 测试或 M1 范围验收。

## 1. 使用范围

本目录将项目拆为四个主责组、五个连续交付阶段，共 20 个可直接创建为 GitHub Issue 的任务书。每个阶段只占一个项目周；课程若按更长周期执行，只能把该周拆成日计划，不能把一个阶段的验收拖到下一周。每份 Issue 都必须能独立回答：谁负责、依赖什么、具体做什么、交付到哪里、怎样验收、失败如何记录、下一阶段接收什么。

需求依据按以下优先级执行：

1. 教师最新要求和团队正式变更决定。
2. 根目录 `README.md` 中的产品范围、MVP/Core/Stretch 和技术边界；阶段 Issue 的周次以本文件为准。
3. 本索引定义的阶段门禁和跨组交接。
4. 各组阶段 Issue 的具体任务。

发生冲突时不得自行选择方便的版本。必须由 M1 记录变更，由受影响负责人确认，M10 更新验收场景。

## 2. 文件命名规范

- 阶段 Issue：`<group>-phase-<阶段号>-<主题>.md`。
- `<group>` 仅允许：`management-quality`、`frontend`、`backend-platform`、`intelligence`。
- 文件名只使用小写 ASCII、数字和连字符。
- 一级标题统一为：`<组缩写>-P<阶段号> 中文阶段名称`。
- Issue 编号不写入文件名，避免把 GitHub Issue 编号误认成项目阶段号。
- 前端第一阶段文件 `frontend-phase-1-experience.md` 为既有基线，保留原有任务结构；周次和统一的小闭环关闭门禁按本规范执行。

## 3. 五阶段定义

### 阶段：Phase 1

- 周次：第 1 周
- 里程碑：第一次汇报
- 全项目可验证结果：范围、成员、候选需求、页面/领域/智能可行性和五阶段计划明确
- 下一阶段入口：四组 Phase 1 Issue 关闭并合并

### 阶段：Phase 2

- 周次：第 2 周
- 里程碑：第二次汇报
- 全项目可验证结果：需求和设计基线冻结；原型、API、数据库、环境、数据与测试契约互相一致
- 下一阶段入口：设计评审通过；统一环境可启动

### 阶段：Phase 3

- 周次：第 3 周
- 里程碑：第三次汇报
- 全项目可验证结果：两个账号可从注册/登录完成发布、搜索、聊天、议价、订单、见面、双方确认、评价
- 下一阶段入口：MVP E2E 通过并形成版本标签

### 阶段：Phase 4

- 周次：第 4 周
- 里程碑：第四次汇报
- 全项目可验证结果：至少两个智能功能真实集成，有基线对比、解释和降级；第 4 周结束冻结功能
- 下一阶段入口：冻结清单和发布候选范围确认

### 阶段：Phase 5

- 周次：第 5 周
- 里程碑：第五次汇报
- 全项目可验证结果：缺陷收敛、干净部署、恢复验证、文档/演示/提交包齐全
- 下一阶段入口：最终标签和提交清单签字

### 3.1 阶段小闭环与唯一合并入口

每个 Phase 是一个在单周内可独立验收、可回滚、可演示的小闭环。四个小组 Issue 是该闭环的并行工作包，不分别直接合并到 `main`。周末仍未满足关闭门禁的任务必须登记为阻塞或正式移出范围，不能自动顺延并声称本阶段完成。

- 项目阶段集成分支统一命名为 `phase<n>/integration`，由 M1 从上一阶段已通过验收的 `main` 提交创建。
- 各小组集成分支从对应的 `phase<n>/integration` 创建；个人任务 PR 仍只合并到本组集成分支。
- 小组任务完成后，由组内负责人提交“小组汇总 PR”到 `phase<n>/integration`，不得直接提交到 `main`。
- 提供方可先把已评审的契约、schema 或最小服务通过小组汇总 PR 合入阶段集成分支；消费者同步阶段分支后再接入，避免相互等待。
- 四个小组汇总 PR 均合并后，M10 在 `phase<n>/integration` 执行阶段验收，M1 复核范围、遗留项和下一阶段交接。
- 只有 M1 提交的“阶段收口 PR”可以从 `phase<n>/integration` 合并到 `main`。该 PR 必须同时引用本阶段四个 Issue、验收证据和阶段标签。
- 阶段收口 PR 合并前，`main` 必须保持上一阶段可运行版本；合并后，`main` 必须达到本阶段定义的可验证结果。
- 下一阶段只能从阶段收口 PR 合并后的 `main` 创建，不从任一小组分支或未验收的阶段集成分支创建。

阶段内推荐顺序如下：

1. Phase 1：M1 发布范围候选 -> 前端/后端/智能组并行形成候选 -> 联合评审 -> MQ 收口。
2. Phase 2：后端/智能组先提供契约 -> 前端消费契约完成原型 -> MQ 冻结联合基线。
3. Phase 3：后端与智能基线先可调用 -> 前端真实联调 -> MQ 完成双账号 E2E。
4. Phase 4：智能组提供版本化结果 -> 后端编排落库 -> 前端展示与降级 -> MQ 冻结。
5. Phase 5：前端/后端/智能组并行加固和复现 -> MQ 完成干净部署、回归和最终交付。

## 5. 跨阶段闭环

### 上一阶段输出：Phase 1 需求候选、页面旅程、领域状态、数据可行性

- 下一阶段必须消费：Phase 2 冻结需求、原型、API/数据库、样本和测试契约
- 证据要求：Phase 2 Issue 列出所引用的 Phase 1 文件或 PR；未消费项必须说明删除理由

### 上一阶段输出：Phase 2 设计基线、统一环境、接口样例、测试场景

- 下一阶段必须消费：Phase 3 前后端实现、基线服务和端到端测试
- 证据要求：每个实现 PR 标注需求 ID、接口版本、迁移版本和验收场景

### 上一阶段输出：Phase 3 MVP 版本、缺陷清单、真实业务数据结构

- 下一阶段必须消费：Phase 4 智能集成、治理补齐和功能冻结
- 证据要求：智能功能不得绕过 Phase 3 权限、状态机和事务；集成测试必须保留降级场景

### 上一阶段输出：Phase 4 冻结版本、指标报告、遗留问题

- 下一阶段必须消费：Phase 5 只修复、优化、复验和打包
- 证据要求：Phase 5 不新增功能；例外必须有 M1 变更记录和 M10 回归范围


任何交付不得以“后续处理”结束。未完成项必须写成：`阻塞事项 / Owner / 依赖人 / 影响 / 下一动作 / 明确截止时间`。

## 6. 协作与验收逻辑

跨组协作必须按“规则/契约提供者 -> 实现提供者 -> 消费者接入 -> M10 独立验收”的顺序进行，不能让消费者为尚不存在的能力负责，也不能用消费者页面反过来证明服务已完成。

### 阶段：Phase 1

- 上游应提供：页面/领域/数据候选、状态规则、验收场景草案
- 下游可验收：文档能相互映射，流程无设计缺口
- 本阶段禁止声称：页面可交互、接口已实现、模型有效

### 阶段：Phase 2

- 上游应提供：冻结契约、成功/失败样例、可点击 Mock、服务骨架
- 下游可验收：原型按契约演示；契约测试和环境冒烟通过
- 本阶段禁止声称：真实业务联调完成

### 阶段：Phase 3

- 上游应提供：真实 API/WebSocket、迁移、基线服务、测试数据
- 下游可验收：前端接入后完成双账号真实持久化闭环
- 本阶段禁止声称：Mock、内存状态或固定响应等于完成

### 阶段：Phase 4

- 上游应提供：模型候选、任务触发、结果存储、解释和降级
- 下游可验收：同一数据上基线对比，集成/降级均可演示
- 本阶段禁止声称：指标未运行、风险自动处罚、功能未冻结

### 阶段：Phase 5

- 上游应提供：冻结版本、缺陷修复、部署包和最终文档
- 下游可验收：非作者干净部署、回归、恢复和演示
- 本阶段禁止声称：新功能或未登记范围变化

### 6.2 上游未就绪处理

1. 消费者可以使用与冻结契约一致、且明显标记的 Mock 继续开发 UI，但只能把任务标记为“待联调”，不能标记“完成”。
2. 上游必须提供阻塞单：缺少能力、当前可用替代、Owner、预计提交、受影响场景和下一检查时间。
3. 接口一旦可用，先由上游提供契约/服务测试证据，再由消费者接入；M10 只在两者都完成后执行端到端验收。
4. 阶段关闭条件要求真实联调时，未联调项必须由 M1 正式移出范围或顺延并修改下游 Issue；不能用 Mock 关闭。
5. 同一人不能既声明上游完成又替代 M10 做最终独立验收。

## 7. 全局完成定义

单个小组 Issue 只有同时满足以下条件才可标记为“组内完成”；同一阶段四个 Issue 只在阶段收口 PR 合并后统一关闭：

- [ ] 所有必做任务完成，或未完成项已按变更流程移出范围。
- [ ] 每个成员的产物进入仓库，路径可打开，内容与当前代码一致。
- [ ] 任务分支通过 PR 合并到小组集成分支，至少一名同组成员完成 Review。
- [ ] 影响其他组的接口、字段、状态、页面或指标由对应负责人确认。
- [ ] 自动化检查与本 Issue 指定验收通过，命令、环境、结果和提交号有记录。
- [ ] M10 完成独立复核；M1 完成范围与业务结果复核。
- [ ] 小组汇总 PR 已合并到 `phase<n>/integration`，Issue 收尾评论记录任务 PR、汇总 PR、阶段提交、证据路径、遗留问题和下一阶段接收人。
- [ ] `docs/evidence/phase-<n>/<group>/handoff.md` 已写明输入版本、输出路径、接收人、接收动作、验收命令、未完成项 Owner 和下一动作截止时间。
- [ ] 没有密钥、真实个人隐私、构建产物、伪造数据或无法复现的效果数字。

阶段收口还必须同时满足：

- [ ] 四个小组 Issue 均达到“组内完成”，小组汇总 PR 均已进入同一个 `phase<n>/integration`。
- [ ] M10 在该阶段集成提交上完成自动化检查、跨组场景和本阶段演示路径验收。
- [ ] M1 确认范围、变更、遗留问题和下一阶段输入，阶段结果不依赖未合并分支。
- [ ] 阶段收口 PR 合并到 `main`，创建阶段标签，并用该 PR 统一关闭四个小组 Issue。

## 9. GitHub Issue 创建要求

手动创建 Issue 时，标题使用：`[组缩写][P阶段] 阶段名称`，正文复制对应 Markdown 全文，并设置：

- Milestone：对应第几次汇报。
- Assignees：该组全体成员，组内负责人为主 Assignee。
- Labels：`group:<group>`、`phase:<n>`、`type:milestone`。
- Dependencies：正文“输入门禁”中列出的上游 Issue；Phase 1 的“启动输入/阶段协作输入”属于非阻塞协作项，不登记为硬依赖。
- Closing PR：只允许从 `phase<n>/integration` 到 `main` 的阶段收口 PR 关闭本阶段四个 Issue；个人任务 PR 和小组汇总 PR 均不直接关闭 Issue。

## 10. 分支与证据落盘规范

- 除保留不改的前端第一阶段外，每份 Issue 必须沿用该文档的成员模板：每名成员分别设置“个人任务”“个人交付物”和“成员验收标准”，并在三处使用同一任务 ID 建立对应关系。
- 个人任务必须写清动作、对象、边界、异常处理或协作对象；个人交付物必须写清代码、文档或证据名称；成员验收标准必须能由非作者按步骤判断通过或失败。仅写“完成某模块”不算合格任务。
- 每份 Issue 必须单列“分支与合并要求”，写明项目阶段集成分支、小组集成分支、每名成员的个人任务分支、PR 目标、评审人和小组汇总 PR 去向。
- Issue 正文禁止使用 Markdown 表格；统一使用分级标题、普通列表和任务复选框，保证可直接复制到 GitHub Issue 并正常勾选。
- 任务卡中未写完整目录的交付文件名，均相对于该 Issue“证据目录”字段；源码、迁移和测试代码仍提交到对应源码目录，并在交付文件中登记实际路径。
- 每份阶段 Issue 已给出唯一的小组集成分支和成员任务分支；任务 PR 的目标必须是小组集成分支，小组汇总 PR 的目标必须是 `phase<n>/integration`。
- 阶段证据统一放在 `docs/evidence/phase-<n>/<group>/`，其中 `<group>` 与文件命名中的组名一致。
- 每个阶段证据目录至少包含：`deliverables.md`（交付物及路径）、`verification.md`（命令/环境/结果/提交号）、`handoff.md`（向下一阶段交接和阻塞）。
- 代码、迁移、测试、模型和原始结果保留在所属源码目录；证据文件只登记可点击路径和结论，不复制大文件。
- 每个任务 PR 必须在阶段 Issue 中登记：成员、任务分支、PR、Reviewer、跨组确认人、验证命令、结果和最终提交。
- 阻塞记录必须包含：`阻塞事项 / 上游 Owner / 下游 Owner / 当前可做内容 / 不能验收内容 / 下一动作 / 截止时间`。
