# MQ-P1 范围、计划与质量框架

## 阶段信息

- 周次：第 1-2 周；截止：第一次汇报前。
- 成员：M1、M10；主责：M1；质量复核：M10。
- 集成分支：`phase1/management-quality`。
- 输入：项目总说明、教师要求、M2-M9 的职责/依赖/风险候选。
- 输出去向：四组 Phase 2 Issue、第一次汇报、需求追踪表。

## 阶段目标

把项目设想转换成十周内可执行的候选范围和质量机制。完成时，每个纳入功能必须有需求 ID、优先级、负责人、依赖、验收条件和计划阶段；计划功能不得写成已实现。

## M1 任务

- [ ] 建立 `AUTH-*`、`MARKET-*`、`TRADE-*`、`AI-*`、`ADMIN-*`、`QUALITY-*` 需求编号。
- [ ] 将功能逐项归入 MVP、Core、Stretch 或 Out，并记录理由。
- [ ] 确认四组、M1-M10 唯一主责、组负责人、替补和跨组评审人。
- [ ] 建立需求追踪表：需求 ID、业务规则、Owner、协作者、依赖、验收、阶段、状态、证据。
- [ ] 建立五阶段/十周计划，明确第 6 周 MVP、第 8 周冻结、第 10 周提交门禁。
- [ ] 建立会议纪要、决策、范围变更、风险和阻塞模板。
- [ ] 汇总三条核心旅程：买家、卖家、求购匹配；标出页面、服务、数据、测试 Owner。
- [ ] 组织全员范围评审，删除真实支付、真实 SSO、物流、硬件和其他越界能力。
- [ ] 编写第一次汇报提纲、讲述分工和现场问题清单。

## M10 任务

- [ ] 建立单元、接口、权限、状态机、WebSocket、AI、E2E、性能和恢复测试策略候选。
- [ ] 把核心旅程转换为 Given/When/Then 验收场景并分配场景 ID。
- [ ] 定义 P0-P3 缺陷等级、进入/退出标准及缺陷关闭证据。
- [ ] 定义任务状态 `todo/in-progress/blocked/review/done`，禁止无证据标记完成。
- [ ] 建立文档质量、PR、演示和彩排检查表。
- [ ] 检查需求是否存在无 Owner、无验收、相互冲突、不可测试或超出十周的问题。
- [ ] 建立第一阶段复核日志，逐项记录问题位置、修复人和期限。

## 跨组交接

| 提供方 | 必须提供 | 接收方 | 验收证据 |
|---|---|---|---|
| 前端组 | 页面清单、旅程、角色、状态候选 | M1/M10 | 可映射到需求和验收场景 |
| 后端组 | 实体、状态、权限、平台约束 | M1/M10 | 每个 MVP 行为有后端 Owner |
| 智能组 | 数据可用性、基线、指标、降级 | M1/M10 | 每项结论为 go/conditional/no-go |
| M1/M10 | 范围、质量门禁、阶段矩阵 | 全组 | 全员评审记录 |

## 交付物

- [ ] 项目范围与排除项、MVP/Core/Stretch 清单。
- [ ] 需求候选清单与追踪表。
- [ ] 四组职责、替补和跨组责任矩阵。
- [ ] 十周计划、五次汇报门禁和风险登记。
- [ ] 测试策略候选、核心验收场景和缺陷流程。
- [ ] 第一次汇报材料、彩排记录和行动项。

## 验收与关闭

- [ ] 每个范围内功能均有 ID、Owner、依赖、验收和阶段。
- [ ] MVP 覆盖账号、商品、搜索、聊天、议价、订单、见面、双方确认、评价、举报、通知和最低管理后台。
- [ ] Core/Stretch 不阻塞 MVP；AI 均有非 AI 降级路径。
- [ ] 四组 Phase 1 任务没有责任空白或重复主责。
- [ ] 所有风险和未决问题有 Owner 与明确期限。
- [ ] M10 确认验收场景可执行，M1 确认范围可在十周完成。
- [ ] 汇总 PR 合并并记录证据；输出由四组 Phase 2 Issue 明确接收。

## 本阶段不做

- 不冻结最终 API/数据库字段，不声称代码或环境已经完成。
- 不以截图、口头说明或 README 描述代替可追踪证据。
- 不新增总说明排除的支付、物流、真实认证和硬件能力。
