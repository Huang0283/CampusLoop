# MQ-P1 范围、计划与质量框架

## 阶段信息

- 周次：第 1-2 周；截止：第一次汇报前。
- 成员：M1、M10；主责：M1；质量复核：M10。
- 证据目录：`docs/evidence/phase-1/management-quality/`。
- 输入门禁：项目总说明、教师要求、M2-M9 的职责/依赖/风险候选均已提供。
- 输出去向：四组 Phase 2 Issue、第一次汇报、需求追踪表。

## 小组目标

把项目设想转换成十周内可执行的候选范围和质量机制。完成时，每个纳入功能必须有需求 ID、优先级、负责人、依赖、验收条件和计划阶段；计划功能不得写成已实现。

---

## 分支与合并要求

- 小组集成分支：`phase1/management-quality`。
- 分支负责人：M1；组内交叉评审：M10；范围复核：M1；可测试性复核：M10。
- M1 从最新 `main` 创建并推送 `phase1/management-quality`，在本 Issue 中记录远程分支链接。
- 远程分支链接：https://github.com/Huang0283/CampusLoop/tree/phase1/management-quality
- M1 个人任务分支：`task/m1-p1-scope`。
- M10 个人任务分支：`task/m10-p1-quality`。
- 所有个人任务分支均从 `phase1/management-quality` 创建，通过 Pull Request 合并回 `phase1/management-quality`。
- 禁止直接向 `main` 或小组集成分支提交；共享分支禁止 force-push 和变基改写历史。
- 任务 PR 必须写明任务编号、交付物路径、验证命令、验证结果、遗留问题和评审人。
- 个人任务完成并交叉评审后，由 M1 从 `phase1/management-quality` 向 `main` 提交汇总 Pull Request。

## M1：项目范围、计划与交付负责人

- 个人任务分支：`task/m1-p1-scope`。

### 个人任务

- [ ] **MQ1-01**：阅读总说明并逐项拆分账号、市场、交易、治理、智能和质量需求；给每项分配唯一 ID，写清触发者、前置条件、正常结果和禁止行为。

- [ ] **MQ1-04**：编写 M1-M10 RACI、替补关系、接口决策人和阻塞升级路径。
- [ ] **MQ1-05**：将十周拆为五个阶段，写出每周必须形成的代码、文档、测试和汇报证据。

### M1 验收标准

- [ ] **MQ1-01**：任取一个需求能回答谁使用、何时触发、成功/失败是什么。
- [ ] **MQ1-02**：MVP 单独即可形成交易闭环；Out 中包含总文档明确排除项。
- [ ] **MQ1-03**：不存在 Owner、阶段或验收列为空的纳入需求。
- [ ] **MQ1-04**：每项跨组能力只有一个最终规则 Owner，替补不改变主责。
- [ ] **MQ1-05**：第 6 周闭环、第 8 周冻结、第 10 周提交均有进入/退出门禁。

## 跨组交接

### 提供方：前端组

- 必须提供：页面清单、旅程、角色、状态候选
- 接收方：M1/M10
- 验收证据：可映射到需求和验收场景

### 提供方：后端组

- 必须提供：实体、状态、权限、平台约束
- 接收方：M1/M10
- 验收证据：每个 MVP 行为有后端 Owner

### 提供方：智能组

- 必须提供：数据可用性、基线、指标、降级
- 接收方：M1/M10
- 验收证据：每项结论为 go/conditional/no-go

### 提供方：M1/M10

- 必须提供：范围、质量门禁、阶段矩阵
- 接收方：全组
- 验收证据：全员评审记录

## Issue 关闭条件

- [ ] 每个范围内功能均有 ID、Owner、依赖、验收和阶段。
- [ ] MVP 覆盖账号、商品、搜索、聊天、议价、订单、见面、双方确认、评价、举报、通知和最低管理后台。
- [ ] Core/Stretch 不阻塞 MVP；AI 均有非 AI 降级路径。
- [ ] 四组 Phase 1 任务没有责任空白或重复主责。
- [ ] 所有风险和未决问题有 Owner 与明确期限。
- [ ] M10 确认验收场景可执行，M1 确认范围可在十周完成。
- [ ] 汇总 PR 合并并记录证据；输出由四组 Phase 2 Issue 明确接收。
