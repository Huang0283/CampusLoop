# BP-P1 领域边界与平台方案

## 阶段信息

- 周次：第 1-2 周；截止：第一次汇报前。
- 成员：M5、M6、M9；业务主责：M6；平台主责：M9。
- 集成分支：`phase1/backend-platform`。
- 输入：M1 范围候选、前端用户旅程、智能组数据/任务需求。
- 输出去向：BP-P2、FE-P2、AI-P2、MQ-P2。

## 阶段目标

明确账号、市场、交易和运行平台边界，形成可供详细设计消费的实体、权限、状态机、事务、架构和环境候选。所有内容是设计结论，不得声称接口、数据库或容器已经实现。

## M5 任务：账号、用户与权限

- [ ] 定义账号、用户资料、角色、会话、模拟校园认证和账号状态。
- [ ] 建立未登录、普通用户、管理员的权限矩阵。
- [ ] 区分公开、本人、审核场景管理员可见和禁止返回字段。
- [ ] 梳理注册、登录、刷新、退出、资料修改、账号禁用流程及错误结果。
- [ ] 明确密码、令牌、邮箱、私密时间、聊天和举报证据的保护要求。
- [ ] 列出必须审计的管理员操作和越权风险。
- [ ] 与 M2 确认登录态/权限页面，与 M8 确认信誉和风险字段可见性。

## M6 任务：市场与交易领域

- [ ] 盘点商品、图片、收藏、求购、匹配、会话、消息、报价、订单、见面约定、评价、举报和通知实体。
- [ ] 为每个实体定义创建者、参与者、管理员权限、状态和生命周期。
- [ ] 绘制发布至评价的交易流程，并定义商品、求购、报价、订单、约定状态机。
- [ ] 明确双方独立确认，同一约定版本双方确认后才完成。
- [ ] 明确仅完成订单参与者可评价、每方一次，取消/争议不进入正常评价。
- [ ] 标记事务、并发控制、幂等键、唯一约束和不可变事件要求。
- [ ] 建立接口能力候选表：调用角色、输入、输出、错误类别、事实来源。
- [ ] 与 M3/M4 核对页面旅程，与 M7 核对匹配触发事件。

## M9 任务：数据与平台

- [ ] 绘制 React、FastAPI、PostgreSQL/pgvector、Redis、MinIO、Worker 的系统边界。
- [ ] 确认模块化单体，不引入无必要微服务或 Kubernetes。
- [ ] 根据领域实体绘制 ER 草图并标记键、约束、敏感/状态/审计字段。
- [ ] 定义迁移脚本、命名、检查和回滚原则，禁止手改共享数据库。
- [ ] 盘点开发服务、版本、端口、环境变量和密钥分类。
- [ ] 制定 Docker Compose、CI、健康检查、日志、备份和恢复候选方案。
- [ ] 明确 PostgreSQL 是业务事实源，Redis/智能结果不能替代交易事实。
- [ ] 与 M7/M8 确认向量、后台任务、模型结果保存和资源需求。

## 必交产物

- [ ] 账号边界、角色权限矩阵、字段可见性和认证异常清单。
- [ ] 领域实体表、交易流程、五类状态机、事务/幂等/并发清单。
- [ ] 系统上下文图、ER 草图、数据归属和平台组件责任表。
- [ ] 迁移、环境、Compose、CI、日志、备份恢复方案候选。
- [ ] 至少 10 个高风险业务场景及预期处理。
- [ ] 前端/智能/测试跨组待确认表，每项有 Owner 和期限。

## 验收与关闭

- [ ] 每个前端 MVP 行为可映射到后端模块、实体和权限 Owner。
- [ ] 每个关键状态转换有角色、前置条件、成功结果和失败结果。
- [ ] 并发接受、重复确认、重复评价、越权修改和证据泄露有控制方案。
- [ ] AI、Redis、对象存储或 WebSocket 不可用时，基础交易的降级边界明确。
- [ ] 数据库、缓存、对象存储、Worker 的责任没有混淆。
- [ ] M5/M6 互审业务；M9 复核数据/环境；M1 复核范围；M10 确认可测试。
- [ ] 汇总 PR 合并，BP-P2 明确接收所有设计项或记录删除理由。

## 本阶段不做

- 不冻结 URL、表字段和索引，不实现正式接口或容器。
- 不允许智能模型直接修改订单事实、定价、封禁或审核结论。
- 不提交真实密钥、个人隐私或来源不明数据。
