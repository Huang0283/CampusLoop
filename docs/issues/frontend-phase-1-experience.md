# 前端第一阶段：范围、信息架构与低保真原型

## 阶段信息

- 周次：第 1 周
- 小组：前端体验组
- 成员：M2、M3、M4
- 组内负责人：M2
- 截止时间：第一次汇报前
- 阶段协作输入：先使用 M1 的范围候选启动页面旅程；M5/M6 的权限、实体和状态候选及 M7/M8 的智能结果字段可分批进入 `phase1/integration`，在联合评审前收敛，不作为前端启动前硬门禁

## 小组目标

梳理学生端和管理端的页面范围，完成核心用户流程、信息架构和低保真原型，为下一阶段的可点击原型、组件规范和接口设计提供依据。

本阶段不要求完成正式业务页面。现有 React 路由和占位页面不能视为功能已经完成。

## 分支与合并要求

- 项目阶段集成分支：`phase1/integration`，由 M1 从上一阶段已验收的 `main` 创建。
- 小组集成分支：`phase1/frontend-experience`。
- 分支负责人：M2；交叉评审：M3、M4；范围复核：M1；可测试性复核：M10。
- M2 从最新 `phase1/integration` 创建并推送小组集成分支，并把远程分支链接填写到本 Issue。
- 远程分支链接：https://github.com/Huang0283/CampusLoop/tree/phase1/frontend-experience
- 个人任务分支命名为 `task/<成员编号>-<简短任务>`，例如 `task/m2-navigation-audit`、`task/m3-market-wireframes`、`task/m4-transaction-flow`。
- 任务分支从 `phase1/frontend-experience` 创建，完成后通过 Pull Request 合并回小组集成分支。
- 禁止直接向 `main` 或小组集成分支提交；共享小组分支禁止 force-push 和变基改写历史。
- 公共路由、公共组件、权限和术语变更必须由另一名前端成员评审；涉及业务状态或接口字段时必须邀请对应后端或智能功能负责人评审。
- 小组交付通过交叉评审后，由 M2 从 `phase1/frontend-experience` 向 `phase1/integration` 提交小组汇总 Pull Request。
- 四组汇总完成并通过 M10/M1 阶段验收后，仅由 M1 从 `phase1/integration` 向 `main` 提交阶段收口 Pull Request。
- 共享文件唯一 Owner 和固定合并顺序按 `docs/issues/README.md` 第 10.1 节执行；本阶段页面草图按 M2/M3/M4 的页面范围分目录保存，公共导航和组件只由 M2 修改。

## 本阶段小闭环

本周由前端体验组完成“页面、交互、页面到契约的映射和用户可见证据”的最小可验收闭环。只有本节的输入、结果、证据和交接均已记录，才允许把本 Issue 标记为本组完成。

### 输入确认

- 本阶段输入：M1 已发布的范围候选、产品总文档和本组成员职责；跨组输入可以在本周内补交，但必须记录版本和确认人。
- 本组本周工作边界：只处理本文件“个人任务”和“小组共同任务”列出的范围；未列出的新需求不得借本 Issue 关闭。
- 输入不完整时：在证据目录的 `handoff.md` 写明阻塞事项、上游 Owner、下游 Owner、当前可做内容和不能验收内容；不得用猜测字段、临时数据或口头确认代替输入。

### 本周可验收结果

- 最小结果：形成可评审的候选方案和验收场景；本阶段只证明范围、规则或可行性，不声称真实页面、接口、持久化或模型已经实现。
- 验收动作：由非作者从阶段集成提交检出，按本 Issue 的任务 ID 找到交付文件，执行文档中的命令或场景，并分别记录成功、失败、权限/状态边界。
- 证据要求：将需求/规则/页面旅程/数据可行性与对应任务 ID 关联，并保存一份可由非作者阅读的验收记录。 证据至少包含提交号、运行环境、命令或操作步骤、实际结果和失败时的日志/截图路径。

### 输出与下一阶段交接

- 输出位置：源码、测试和迁移保留在所属目录；阶段证据统一写入 `docs/evidence/phase-1/frontend/`，至少包含 `deliverables.md`、`verification.md` 和 `handoff.md`。
- 接收人和动作：下一阶段负责人按文件路径读取候选结果，逐项确认采用、修改或删除；未采用项必须写明理由。
- 接收清单必须列出：输出文件/提交号、接收人、接收动作、验收命令或场景、接收结论；任何未完成项都要写明 Owner、依赖人、影响、下一动作和明确截止时间。
