# BP-P3 MVP 业务闭环实现

## 阶段信息

- 周次：第 5-6 周；截止：第三次汇报前。
- 成员：M5、M6、M9；业务主责：M6；平台主责：M9。
- 证据目录：`docs/evidence/phase-3/backend-platform/`。
- 输入门禁：BP-P2 契约/迁移/环境基线冻结；前端映射和 M10 场景可用。
- 输出去向：FE-P3 联调、MQ-P3 验收、BP-P4 智能与治理扩展。

## 小组目标

实现真实持久化、权限正确、事务完整且可测试的 MVP API/WebSocket。基础交易在智能服务不可用时仍能运行；所有状态改变由服务端验证和记录。

## 提供方优先顺序

1. M5/M6 先提交契约测试可通过的 API/WebSocket 和虚构测试数据。
2. M9 确认迁移、依赖和统一环境可复现，发布可供前端使用的提交号。
3. M2/M3/M4 再开始真实联调；发现契约差异退回对应后端 Owner，不由前端猜测修补。
4. M10 在后端服务证据和前端接入证据都存在后执行 E2E。后端单测不能代替页面验收，页面 Mock 也不能代替接口验收。

## 核心不变量

- [ ] 只有商品/订单参与者或授权管理员能访问受限资源。
- [ ] 一个报价最多成功接受一次；接受与订单创建在同一事务。
- [ ] 单方完成不改变订单为完成；双方必须确认同一约定版本。
- [ ] 每个参与方每订单最多评价一次；非完成订单拒绝评价。
- [ ] 订单状态事件不可由客户端伪造或覆盖。
- [ ] 举报证据私有；管理员访问有审核上下文和审计记录。

## 小组验收标准

- [ ] API/服务/数据库测试覆盖主路径、权限、非法状态、重复和回滚。
- [ ] 两账号从发布到评价的数据可通过 API 和数据库事件一致验证。
- [ ] 并发请求不创建重复订单、完成或评价。
- [ ] 服务重启后数据仍在；缓存清空不改变订单事实。
- [ ] WebSocket 断开可通过 HTTP 获取缺失消息。
- [ ] OpenAPI、迁移和运行说明与当前提交一致。

## 本阶段不做

- 不以管理员权限代替正常权限测试，不手改数据库制造演示状态。
- 不让智能、Redis 或 WebSocket 故障破坏基础交易写入和读取。
