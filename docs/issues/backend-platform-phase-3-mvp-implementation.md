# BP-P3 MVP 业务闭环实现

## 阶段信息

- 周次：第 3 周；截止：第三次汇报前。
- 成员：M5、M6、M9；业务主责：M6；平台主责：M9。
- 证据目录：`docs/evidence/phase-3/backend-platform/`。
- 输入门禁：BP-P2 契约/迁移/环境基线冻结；前端映射和 M10 场景可用。
- 输出去向：FE-P3 联调、MQ-P3 验收、BP-P4 智能与治理扩展。

## 小组目标

实现真实持久化、权限正确、事务完整且可测试的 MVP API/WebSocket。基础交易在智能服务不可用时仍能运行；所有状态改变由服务端验证和记录。

- 分支负责人：M5；组内交叉评审：M6、M9；范围复核：M1；可测试性复核：M10。

## 提供方优先顺序

1. M5/M6 先提交契约测试可通过的 API/WebSocket 和虚构测试数据。
2. M9 确认迁移、依赖和统一环境可复现，发布可供前端使用的提交号。
3. M2/M3/M4 再开始真实联调；发现契约差异退回对应后端 Owner，不由前端猜测修补。
4. M10 在后端服务证据和前端接入证据都存在后执行 E2E。后端单测不能代替页面验收，页面 Mock 也不能代替接口验收。

## 核心不变量

- [ ] 只有商品/订单参与者或授权管理员能访问受限资源。
- [ ] 一个报价最多成功接受一次；接受与订单创建在同一事务。
- [ ] 单方完成不改变订单为完成；双方必须确认同一约定版本。
- [ ] 每个参与方每订单最多评价一次；非完成订单拒绝评价。
- [ ] 订单状态事件不可由客户端伪造或覆盖。
- [ ] 举报证据私有；管理员访问有审核上下文和审计记录。

## 小组验收标准

- [ ] API/服务/数据库测试覆盖主路径、权限、非法状态、重复和回滚。
- [ ] 两账号从发布到评价的数据可通过 API 和数据库事件一致验证。
- [ ] 并发请求不创建重复订单、完成或评价。
- [ ] 服务重启后数据仍在；缓存清空不改变订单事实。
- [ ] WebSocket 断开可通过 HTTP 获取缺失消息。
- [ ] OpenAPI、迁移和运行说明与当前提交一致。

## 本阶段小闭环

本周由后端与平台组完成“领域规则、接口/持久化、运行环境和服务端证据”的最小可验收闭环。只有本节的输入、结果、证据和交接均已记录，才允许把本 Issue 标记为本组完成。

### 输入确认

- 本阶段输入：对应 Phase 2 收口提交中的冻结契约、迁移/环境、原型映射、测试数据和验收场景。
- 本组本周工作边界：只处理本文件“个人任务”和“小组共同任务”列出的范围；未列出的新需求不得借本 Issue 关闭。
- 输入不完整时：在证据目录的 `handoff.md` 写明阻塞事项、上游 Owner、下游 Owner、当前可做内容和不能验收内容；不得用猜测字段、临时数据或口头确认代替输入。

### 本周可验收结果

- 最小结果：完成本组负责的真实 MVP 片段，并能在统一环境中按场景验证；Mock、内存状态、固定响应或手工改库不计入完成。
- 验收动作：由非作者从阶段集成提交检出，按本 Issue 的任务 ID 找到交付文件，执行文档中的命令或场景，并分别记录成功、失败、权限/状态边界。
- 证据要求：记录实际提交号、启动命令、请求/页面/数据库或模型结果证据，以及成功、失败、权限和恢复路径。 证据至少包含提交号、运行环境、命令或操作步骤、实际结果和失败时的日志/截图路径。

### 输出与下一阶段交接

- 输出位置：源码、测试和迁移保留在所属目录；阶段证据统一写入 `docs/evidence/phase-3/backend-platform/`，至少包含 `deliverables.md`、`verification.md` 和 `handoff.md`。
- 接收人和动作：下一阶段只接收已通过本周门禁的真实结果；未联调项必须保留阻塞记录并由 M1 决定顺延或移出范围。
- 接收清单必须列出：输出文件/提交号、接收人、接收动作、验收命令或场景、接收结论；任何未完成项都要写明 Owner、依赖人、影响、下一动作和明确截止时间。
