# 九人协作、文书测试与最终演示闭环

## 目标

本 Issue 用于组织 M10 技术负责人之外的九名组员，完成课程技术报告、PoC 用户手册、独立测试、页面证据、最终 PPT、15 分钟真人演示和提交材料。每个阶段占一周；阶段内所有材料必须绑定同一个验收 SHA。

## 自选方向与认领方式（尚未分组）

本 Issue 不指定九名组员各自加入哪一组。所有岗位目前均待认领，由九名组员自行协商选择；建议人数仅用于平衡工作量，不是固定名额。

- 文书与技术报告方向，建议 2 人：需求与报告统稿；系统设计与技术证据。
- 独立测试与验收方向，建议 3 人：测试数据与身份权限；双账号交易与业务状态；异机部署、性能与恢复。
- 使用说明与页面截图方向，建议 2 人：学生用户手册与主流程；管理员/部署说明与页面证据。
- 最终演示与提交方向，建议 2 人：PPT、课程要求与证据来源；讲稿、双账号演示、彩排和 MP4。
- M10 陈梓弘继续负责功能/API/UI/SDK/联调/缺陷修复、可验收 SHA、阶段技术集成和最终技术验收，不参加上述九人的材料分组。

每人留言认领：姓名、成员编号、工作方向、个人岗位、交付文件、组内复核人、个人分支及预计交付日期。可协商兼岗或拆分岗位，但所有任务均须有人认领；共享文件只有一个编辑负责人。九人另行推选材料集成人，负责登记、共享索引和汇总，不预先指定人选。调整岗位需本人说明交接人和剩余任务。

详细个人任务、交付路径和验收要求见下方“详细任务文档”。

## 任务清单

### MQ-COLLAB-01 文书与技术报告

认领文书方向的组员必须提交英文报告章节、需求追踪、架构与智能方法说明。报告正文必须满足课程 40 至 60 页要求，不能把目录、References、Appendix A 计入正文。每个实现结论必须引用代码、契约、测试或明确限制。

### MQ-COLLAB-02 独立测试与验收

认领测试方向的组员必须在独立测试环境执行功能、权限、状态、异常、部署、性能和恢复测试。每条用例写明角色、数据、步骤、预期、实际、SHA、时间和证据。技术负责人修复后，原执行人必须复测；没有复测不能关闭缺陷。写入测试只使用专用审计数据库及 Redis DB14/15，不操作日常账号库或媒体卷。

测试数据清单负责人由测试方向自行认领，负责虚构业务数据、生成/复位说明、来源/许可、版本、哈希和用例映射。M7/M8 提供既有智能资产、字段、指标与方法，测试组负责独立标注复核、去重、覆盖检查与复算；测试部分须与训练/调参隔离。M8 的 L0 合成记录只能测试结构、规则与降级；真实价格效果仍依赖 M5/M6 实际授权的合格 L3 快照，未满足既有 200 条及六类每类 30 条等门禁时保留 NOT_EVALUATED/NO_GO，不能伪造成交。普通功能测试无需等真实成交数据齐全。

“异机部署、性能与恢复”岗位在另一成员电脑或全新虚拟机检出指定 SHA，依手册安装、空审计库迁移、种子、启动、健康检查和双账号交易/智能降级；不复用 M10 的依赖、环境、账号库或媒体卷。本机换目录不能代替异机验收。测试组执行并保存系统/依赖/端口/命令/失败与结果，手册组补漏步骤，M10 修技术故障，原执行人复测。缺电脑或虚拟机时登记阻塞。

测试组每个工作日向 M10 简报一次，不规定钟点；个人维护 `testing/m<编号>/daily-report.md`，自行推选的汇总人在本 Issue 给链接。内容包含 SHA、环境、数据版本、通过/失败/阻塞/未执行数量、缺陷 Issue/严重度、证据、复测、需协助事项及下一步。没测也说明原因，严重故障及时报告；M10 据此安排运维修复并提供新验收 SHA。

测试目录 `docs/collaboration/phase-<n>/testing/` 额外交付 `dataset-register.md`、`test-data-setup.md`、`independent-evaluation.md`、`environment-verification.md`。新增可提交虚构样例及生成/复位脚本放 `tests/collaboration/phase-<n>/`，与 M7/M8 既有资产分开，不改生产种子或规则，不提交原始真实导出、真实个人数据或密钥。

### MQ-COLLAB-03 使用说明与页面截图

用户手册是教别人怎样安装、启动、登录并完成交易；页面证据是指定软件版本的真实截图及操作记录，供报告和演示引用。手册组写说明并维护截图，测试组独立验证操作和异机运行，M10 修复技术问题；不能只交截图没有步骤。

认领手册方向的组员必须完成 8 至 12 页用户手册以及管理员、部署、故障文档。截图、手册和页面问题必须来自当前 SHA，覆盖桌面/移动、游客/学生/管理员、成功/失败/无权限/空状态。页面问题通过 Issue 交给 M10 修复，不能用材料 PR 改生产功能。

### MQ-COLLAB-04 最终演示与提交

认领演示方向的组员只能在功能与 UI 冻结后制作最终材料，冻结前只维护结构、来源与脚本草稿。课程演示为 15 分钟，MP4 必须出现演示者本人；先完成第一轮彩排，修复并复测，再完成第二轮。PPT、讲稿、视频、截图和软件必须绑定同一软件基线 SHA。

### MQ-COLLAB-05 每次大改动的同步闭环

M10 修改路由、API、SDK、数据库、状态、权限、UI、错误提示、AI 行为、端口、部署或 CI 时，必须在 PR 中列出受影响材料。测试组更新用例并复测，文书组更新需求/设计/实现/测试章节，手册组更新步骤/截图/故障处理；演示组在冻结前只维护草稿。所有同步 PR 链接回本 Issue。

## 验收标准

- 每个成员有独立分支、独立 PR、任务日志和组内复核记录。
- 软件、测试、报告、手册、PPT 和视频绑定同一软件基线 SHA；旧截图和旧数字明确标为过期。材料 PR 的提交 SHA 另记，不要求它与代码提交相同，最终记录发布提交或标签。
- 课程报告、用户手册、项目演示、至少三次项目更新和 Group Workload Profile 按教师文件完成。
- 失败、阻塞、未实现和 NO_GO 功能如实保留；不以自动化日志代替真人演示或成员签名。
- M10 在阶段集成分支复验，推选的材料集成人核对范围和提交清单，全部门禁满足后再关闭本 Issue。

## 分支和 PR 规则

- 文书：`docs/p<阶段>-report`。
- 测试：`docs/p<阶段>-testing`。
- 手册：`docs/p<阶段>-manuals`。
- 演示：`docs/p<阶段>-presentation`。
- M10 技术分支：`task/m10-p<阶段>-<主题>`，先进入阶段技术集成分支。
- 上述四个材料分支用于方向内集成；个人另建 `docs/p<阶段>-<方向>-m<编号>-<主题>` 分支发 PR，避免多人直接推同一分支。个人日志放在 `docs/collaboration/phase-<n>/<方向>/m<编号>/task-log.md`，共享文件由登记的唯一负责人汇总。
- 所有 PR 必须写任务 ID、文件、基线 SHA、验证命令、实际结果、遗留问题和关联 PR；不得直接改 `main`。

## 时间与提交节奏

每阶段一周：每周认领交付，周内持续测试、修复及更新材料，周末复核，不细化到每天几点做哪项。测试组每个工作日向 M10 汇报；各方向在本周交付前提交源文件、证据、个人 PR 与任务日志，大改动后同步更新。最终演示/录像放在功能/UI 冻结与验收之后，脚本按环节安排，无须逐秒排程。

三个课程文件没有具体日历截止日期：Proposal 模板只有 Deadline 栏；课程说明要求查 Blackboard Course Assessment；贡献表随 coursework 提交。材料集成人取得正式日期后登记截止时间、时区、提交入口、课程提交人和内部交付日期，未取得时标为待确认。GitHub push 不等于学校提交，课程提交后须保存 Blackboard 回执。

## 关闭条件

本 Issue 不因提交一份草稿而关闭。必须有独立测试结果、报告和手册更新、同 SHA 交接、最终演示材料、贡献记录和真实 Review。课程截止日期以 Blackboard 为准；未提供日期时保持待确认。
