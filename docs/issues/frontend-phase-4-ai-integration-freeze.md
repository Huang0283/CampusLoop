# FE-P4 智能结果、后台与冻结

## 阶段信息

- 周次：第 4 周；截止：第四次汇报及功能冻结前。
- 成员：M2、M3、M4；组内负责人：M2。
- 证据目录：`docs/evidence/phase-4/frontend/`。
- 输入门禁：FE-P3/MQ-P3 通过；M7/M8 结果契约和 M5/M6 接口提交可测。
- 输出去向：MQ-P4 集成验收、FE-P5 稳定化。

## 小组目标

在不破坏 MVP 的前提下接入智能搜索、供需匹配、价格建议及已纳入范围的信誉/风险展示，补齐最低管理后台和五类状态，并按冻结清单锁定页面范围。

## 分支与合并要求

- 项目阶段集成分支：`phase4/integration`，由 M1 从上一阶段已验收的 `main` 创建。
- 小组集成分支：`phase4/frontend-integration`。
- 分支负责人：M2；组内交叉评审：M3、M4；范围复核：M1；可测试性复核：M10。
- M2 从最新 `phase4/integration` 创建并推送 `phase4/frontend-integration`，在本 Issue 中记录远程分支链接。
- 远程分支链接：https://github.com/Huang0283/CampusLoop/tree/phase4/frontend-integration
- M2 个人任务分支：`task/m2-p4-admin-freeze`。
- M3 个人任务分支：`task/m3-p4-ai-results`。
- M4 个人任务分支：`task/m4-p4-governance-regression`。
- 所有个人任务分支均从 `phase4/frontend-integration` 创建，通过 Pull Request 合并回 `phase4/frontend-integration`。
- 禁止直接向 `main` 或小组集成分支提交；共享分支禁止 force-push 和变基改写历史。
- 任务 PR 必须写明任务编号、交付物路径、验证命令、验证结果、遗留问题和评审人。
- 个人任务完成并交叉评审后，由 M2 从 `phase4/frontend-integration` 向 `phase4/integration` 提交小组汇总 Pull Request。
- 四组汇总完成并通过 M10/M1 阶段验收后，仅由 M1 从 `phase4/integration` 向 `main` 提交阶段收口 Pull Request。

## 文件所有权与合并顺序

- M2 独占管理后台壳层、异步状态组件、全局错误边界和冻结登记；M3/M4 不直接修改公共组件。
- M3 只维护搜索、供需匹配和价格建议页面；M4 只维护交易、通知和治理页面；智能字段必须来自同一生成 SDK 和已确认的 AI 契约。
- 后端 M6 负责 OpenAPI 与 SDK 生成，前端只消费版本化结果；任何字段差异先由 M7/M8 确认，再由 M6 修改契约，最后由 M3/M4 接入。
- 合并顺序固定为 M2 -> M3 -> M4；后一 PR 必须从最新 `phase4/frontend-integration` 同步后再提交。

## 接入顺序

1. M7/M8 提供版本化结果、解释、降级样例和真实评估证据。
2. M5/M6 提供带权限的业务 API、任务状态和结果持久化。
3. M3/M2 只调用业务 API 展示，不直接读取模型文件或绕过后端权限。
4. M10 同时验证正常与降级路径；M1 决定是否进入冻结范围。

## 本阶段小闭环

本周由前端体验组完成“页面、交互、页面到契约的映射和用户可见证据”的最小可验收闭环。只有本节的输入、结果、证据和交接均已记录，才允许把本 Issue 标记为本组完成。

### 输入确认

- 本阶段输入：Phase 3 MVP 收口提交、真实业务事件/数据、智能结果契约和未关闭缺陷清单。
- 本组本周工作边界：只处理本文件“个人任务”和“小组共同任务”列出的范围；未列出的新需求不得借本 Issue 关闭。
- 输入不完整时：在证据目录的 `handoff.md` 写明阻塞事项、上游 Owner、下游 Owner、当前可做内容和不能验收内容；不得用猜测字段、临时数据或口头确认代替输入。

### 本周可验收结果

- 最小结果：完成已批准的智能集成、治理补齐或前端展示，并同时保留基线、解释、权限和不可用降级；本周末功能冻结。
- 验收动作：由非作者从阶段集成提交检出，按本 Issue 的任务 ID 找到交付文件，执行文档中的命令或场景，并分别记录成功、失败、权限/状态边界。
- 证据要求：固定数据/代码/参数版本，保存逐样本和汇总指标、集成路径、降级路径、人工边界和冻结提交号。 证据至少包含提交号、运行环境、命令或操作步骤、实际结果和失败时的日志/截图路径。

### 输出与下一阶段交接

- 输出位置：源码、测试和迁移保留在所属目录；阶段证据统一写入 `docs/evidence/phase-4/frontend/`，至少包含 `deliverables.md`、`verification.md` 和 `handoff.md`。
- 接收人和动作：Phase 5 只接收冻结清单中的修复、优化、复验和打包任务；任何新功能必须先走范围变更。
- 接收清单必须列出：输出文件/提交号、接收人、接收动作、验收命令或场景、接收结论；任何未完成项都要写明 Owner、依赖人、影响、下一动作和明确截止时间。

- [ ] 小组任务 PR 已经由同组成员 Review，并合并到 `phase4/frontend-integration`；小组汇总 PR 已提交到 `phase4/integration`。
- [ ] M10 已在阶段集成提交上执行本组验收，M1 已确认范围、遗留项和下一阶段接收清单。
