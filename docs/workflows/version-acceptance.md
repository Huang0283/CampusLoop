# CampusLoop 每次升级后的测试、用户体验与材料更新工作流

版本：1.4；更新日期：2026-10-27。协作总任务为 [Issue #129](https://github.com/Huang0283/CampusLoop/issues/129)。本文件规定以后每轮升级的做法，不声明任何一轮已通过。

## 1. 谁做什么，做到哪里才算交付

M10 陈梓弘继续负责代码、功能、API、SDK、UI、部署故障修复和候选版本集成；M1 管理与 M10 技术工作当前由同一人承担，质量记录不能因此冒充另一人的独立复核。其他九人自行选择岗位，建议文书 2 人、测试 3 人、用户体验与手册 2 人、最终演示 2 人。人数可协商，本文不分配姓名。每人认领一个主要岗位，登记组内复核人；一个文件只有一个编辑负责人，跨组修改先由负责人接收。

四组交付职责如下：

- 文书组把已验证的软件事实写进英文技术报告。不能只写背景介绍，必须维护需求追踪、设计与实现说明、测试与评估、限制、引用和贡献来源。详细岗位任务见[九人协作任务书](../management/nine-member-collaboration-plan.md)。
- 测试组回答“功能结果对不对”，维护测试数据、完整用例、执行日志、缺陷、复测及异机安装记录。自动化结果是输入，真人独立执行另存，不能把 M10 自测算作自己的执行。
- 用户体验与手册组（简称用户组）回答“普通用户能否理解并完成任务”。真实组员登录和使用系统，记录任务是否完成、卡在哪里，再更新用户/管理员/部署手册和截图；不是只交截图，也不是要求寻找真实交易用户。
- 演示组维护课程要求、来源索引和脚本草稿，功能/UI 冻结且测试与用户任务通过后，才制作最终 PPT、彩排和真人出镜录像。

测试组每个工作日向 M10 汇报一次，不限定钟点；严重问题立即报。其他组在收到变更通知后回复接收及受影响文件，本周交付前提交 PR；不能完成时写阻塞、责任人和下一次反馈日期。每个原定项目阶段仍是一周；每天的版本通知是周内增量验收，不另起一个阶段，也不虚构课程截止日期。

## 2. 分支：保留什么，谁建什么

`main` 是正式稳定主干，长期保留。四个材料组各有一条跨阶段复用的长期组分支：

- `team/reporting`：英文技术报告、需求追踪、设计实现章节、引用与贡献索引。
- `team/testing`：用例、虚构数据、执行日志、缺陷复测、独立评估和异机部署测试记录。
- `team/user-experience`：真人体验任务、用户/管理员/部署手册、页面截图及体验问题。
- `team/presentation`：PPT、讲稿、演示脚本、彩排记录、提交清单和媒体索引。

四条分支由 M10 从本次文档合入后的 `origin/main` 建立，九条岗位分支从对应组分支建立；组员无需建组分支或岗位分支。建立分支不代表已分配组员。组员自行推选各组材料集成人后在 #129 登记负责人、分支链接、文件负责人和复核人。长期分支采用 merge PR 合入主干，关闭自动删除该 head 的选项；合并后负责人通过任务 PR 将必要的 `origin/main` 更新同步回组分支，不改写历史。

每个岗位先认领预建的 `work/<方向>/<岗位>` 分支，一人独用并向本组 `team/*` 发 PR。每轮 merge 后继续使用时先合入本组最新提交，不自动删除 head；如另开独立临时任务，才从本组最新分支建立 `docs/<方向>-<成员>-<变更ID>`。个人任务经另一位组员 Review 后合入组分支，组汇总 PR 再进入当前阶段的 `phase<n>/integration`；阶段正式收口后进入 `main`。阶段已结束后的日常材料更新，组汇总 PR 可直接指向 `main`。每轮通知写明实际汇总目标，所有组照同一个目标操作。

材料组 PR 不携带生产功能、OpenAPI、SDK、数据库迁移或运行配置修改。测试新代码只能写在 `tests/collaboration/`，由 M10 复核；生产代码问题交缺陷 Issue，由 M10 在技术任务分支修复。组分支保持最新主干，不把其他组未验收的代码偷偷合进来。软件 SHA 与材料提交 SHA 分开记录，不能因为材料变更导致 SHA 不同就要求重做全部测试。

老分支处理：

- 正在开发或验收的 `phase5/*`、未合并 PR 对应分支、存在独有提交或下游依赖的分支先保留。`phase5/integration` 合入的内容不能误称已在 `main`。
- 老的 `docs/p<阶段>-report/testing/manuals/presentation` 若实际存在且有未合并内容，先通过 PR 迁入对应 `team/*`，登记接收提交，再停用。不存在的旧示例分支无需创建。
- 历史 `task/*`、`fix/*`、`prep/*`、`docs/*`、备份或审计分支，需要确认对应 PR 已合并、成果已进入目标主干、开放 PR/工作树/其他成员没有依赖，再删除。squash 合并时不能仅凭 `--merged` 判断成果丢失，要核对 PR 的 merge commit 与最终文件。
- 阶段分支在阶段验收和主干收口完成、证据可从主干/标签找到、无后续依赖后可以归档或删除。删除分支不会删除已经合并的历史。
- 本轮仅建立新规则并记录现有分支检查结果，不批量删除旧分支；2026-10-27 已 fetch 并检查：老的 docs/eight-member-closeout-plan、docs/nine-member-collaboration、docs/collaboration-testing-datasets 已在 main 历史中；phase5/integration 仍有未进入 main 的候选提交，且有本地 worktree 使用旧任务分支，故本轮不删除远端旧分支。文档清理见 docs/management/README.md。

测试数据岗位首次拉取示例（其他岗位看各组 WORKFLOW.md）：

```powershell
git fetch origin --prune
git switch --track origin/work/testing/data-permissions
git merge origin/team/testing
# 编辑本人任务文件后，逐项 git add <相关文件>，再 commit、push
git push origin work/testing/data-permissions
```

如果本地已存在岗位分支，用 `git switch work/testing/data-permissions` 和 `git pull --ff-only origin work/testing/data-permissions`，不要重复创建。PR 目标为 `team/testing`。不使用 reset --hard、force-push 或整目录覆盖来处理冲突。

## 3. 数据、用例与个人交付物的固定基线

具体字段、每条样例做什么、生成/复位、逐岗位文件见[总任务书](../management/nine-member-collaboration-plan.md)与[测试组任务书](../collaboration/teams/testing/TASKS.md)。本节数字是待交要求，不是运行结果，首次建立后增量维护：

- 数据：8 个账号配置、60 条商品输入（48 展示/12 场景）、12 求购、12 媒体定义、24 非法输入、20 隔离 HTTP 模拟响应、30 搜索、24 价格、12 信誉/风险功能样例。
- T1 准备数据并测 36 条权限例，T2 用真实 API 做 S01–S12 和 60 条业务例，T3 做 30 条环境/异常例；合计最低 126 条计划用例，执行次数与用例数分开。
- 基础文件的虚构输入要导入专用测试库，经真实页面/接口执行；静态 mock 响应只供组件检查，不能作为持久化/E2E通过证据。后台状态只能通过合法业务动作达到。
- U1 交 12 份任务记录和至少 18 图；U2 交 4 份管理/安装/手册复核记录和至少 10 图；真人操作使用虚构数据，缺任务就报阻塞，不虚构访谈。
- R1/R2、D1/D2 逐项文件、六张技术图、十四页 PPT 初稿、两轮彩排、最终报告/手册/视频的要求以各岗位任务书为准。
- M7/M8 真实评估的独立审核、测试前封存、来源授权与原样本/切片门槛保留；功能合成数据不冒充 L3，条件不足保留 NOT_EVALUATED/NO_GO。
- 写入只用专用审计数据库、测试媒体卷与 Redis DB14/15。日常启动沿用 scripts/start-local.ps1；UI 5174/API 8001 是本机默认，独立环境实际地址按版本通知，localhost 不能当其他组员可直连地址。

## 对接流程：谁交什么、发哪里、谁接收

### 公共约定：只需要四个联络人，不要全员互相催

四组联络人为 R1、T2、U2、D2；组内原始任务由实际岗位执行。所有通知在 [Issue #129](https://github.com/Huang0283/CampusLoop/issues/129) 以变更 ID 串起来，文件在各自岗位/组分支提交 PR，缺陷/体验问题另开 Issue 并回链。无需把文件重复复制到四个群；发可打开的 GitHub 链接，不只发本机 `C:\...` 路径或别人打不开的 localhost。

第一次交接接收人先做一次最小操作，再回复“已接收，可开始/部分可开始/缺材料”；不能只点表情。每轮通知由 M10 写本轮预计反馈日期，接收人最迟下一个团队工作日给接收/阻塞反馈，不要求当天完成整组工作；发现越权、数据丢失或核心链路不通立即报告。每周节奏仍是一周一个阶段，正式课程日期未知时保持待确认。

### 第一步：M10 发版本 → T2 分给 T1/T3

M10 在 `docs/collaboration/phase-<n>/changes/<变更ID>/notice.md` 填写软件分支/完整 SHA、UI 与 API 地址、是否已合并、专用环境/数据获取、改前改后、受影响页面/接口/权限/状态、要测的 T 编号/用户 U 任务和预期、已知限制、反馈日期、组汇总 PR 目标；在 #129 发链接并点名实际认领的 T2/R1/U2/D2。

T2 回复软件 SHA/任务范围，把数据和权限交 T1、业务交自己、环境/异常交 T3。T1/T3 在自己的日志认领用例，不能三人改一个文件。若 API 没启动、没有审计库或缺管理员，T2 列“缺什么、由谁补、哪些不能测”交 M10；其他能测的用例先继续。R1/R2/U1/U2/D1/D2 此时可改草稿，不要假写测试结论。

### 第二步：T1 交数据 → T2/T3 接收

T1 发数据 PR/版本、样例统计（8账号/60商品/12求购等）、README、命名空间、生成/复位命令、实际成功/拒绝数、映射清单和已知缺口；凭据私发，不写公开 Issue。

T2 在 business 空间按说明导入，T3 在 environment 空间复核目标和重复导入。两人各回复：实际软件 SHA、数据版本、执行命令、创建数/失败数、是否可开始。文件缺行/引用错误退回 T1；接口不支持或环境权限缺失退回 M10；不把双方都写成“等对方处理”。T1 修后重交同 PR，由原接收人重试；此前失败保留。

先接收基础数据再接收权限/交易前置：T2 不用等 T1 的 36 条全部通过才开始生成场景，T1 的订单/私聊越权用例接收 T2 的配方后补测，分别写两次交接。安装说明亦先由 U2 按统一启动脚本写可执行草稿，T3 边运行边回报缺步，U2 再修订，不要求手册已验收后才允许测试手册。

### 第三步：测试组每天交反馈 → M10 修 → 原执行人复测

T1/T3 将自己的 `daily-report.md` 和脱敏证据交 T2；T2 加本人记录，在 `changes/<变更ID>/testing-summary.md` 汇总五类计数、Issue、严重度、可交用户任务、阻塞、需 M10 帮忙和下一步，每个工作日在 #129 发一次摘要。不是让 M10 到三个分支里猜结果。

每个真实故障单独建 Issue，填软件 SHA、环境/数据、账号别名/对象 ID、最短复现、预期依据、实际结果和脱敏证据。M10 回复“接受并修复/需补证据/暂缓及理由”，修复 PR 用 `Refs #缺陷号`，推送新软件 SHA 和回归范围。原执行人在新 SHA 跑原用例与相邻回归，在缺陷 Issue 写结果；T2 才更新汇总状态。没有原执行人复测，M10 不能替他写“已确认”，PR 合并不自动等于缺陷关闭。

### 第四步：T2 交通过的任务 → U2 分给 U1

T2 发 `business-journeys/user-handoff.md`，逐项写 U01–U08 哪些可做、通过用例/证据、软件 SHA、experience 空间导入入口、角色别名、数据 ID、已知限制。U2 先确认能打开首页、登录专用账号、查看一件指定商品，再在 #129 回复接收结果，并分给 U1 的学生任务与自己的管理/安装任务。

U1 不必等 U06 管理页修好才能体验 U01 浏览；被阻塞的任务写明对应缺陷，其他任务继续。U1/U2 的观察与任务由真人记录，体验步骤不能用脚本替代。测试组修正错误数据由 T1 交接；软件坏了找 M10；难用问题建体验 Issue，不能丢给文书组修改一句话代替修功能。

### 第五步：用户组交问题 → M10 处置 → 原体验人确认

U1 给 U2 自己的任务/截图/反馈链接，U2 在 `changes/<变更ID>/user-summary.md` 按任务列完成/失败/阻塞、入口卡点、问题 Issue、手册和截图 PR。M10 在每条 Issue 写接受修复、后续处理或不采纳及理由；接受项修后由原体验人重走任务，后续处理给负责人/影响/再检查日期。U2 汇总处置，不替 U1 填“体验已通过”。

### 第六步：T2/U2/M10 交事实 → R1/R2 更新报告

T2 给报告的包是测试汇总、用例与原始日志链接、数据规模、已修/未修、实际指标或未评估原因；U2 给的是手册 PR、截图索引、真实任务观察/限制；M10 给的是代码/契约变更、版本和技术限制。R1 回复“收到哪些证据、要改哪些 REQ/章节、仍缺什么”；R2 据此核对图/链路/方法，R1 写测试/体验结论和总稿，两人各提交自己文件的 PR。

R1 报告中的数字请原测试岗位复核，技术说明请 M10 复核，截图请 U2 复核；这些可以在同一个 PR 留具体评论，不要求所有人同时改报告。没等到结果的段落保留待验证，其他章节可以先合草稿，不能要求所有测试通过后才允许写任何文档。最终“通过”结论必须对应实际证据。

### 第七步：前三组交稳定资料 → D2/D1 最终演示

R1 交最终报告/需求/结论和限制，T2 交已复测主链路/边界/降级的操作配方，U2 交同版本截图/手册/demo 数据计划。D2 回复缺少的场景或数据 ID，D1 核所有数字/截图来源。M10 在 #129 明确“冻结软件 SHA、允许最终演示的范围、仍有限制”；没冻结只能写草稿，不能录最终版。

D2 组织第 1 轮彩排，失败建 Issue 交 M10，测试/原体验人复测，D1/D2 各修自己的 PPT/脚本，再做第 2 轮，之后录真人出镜 MP4。紧急 UI/代码变更影响哪个环节，就补测和重录那个环节；不把旧图静默塞进新版本。

### 第八步：各组 PR → 接收 Review → M10 收口

个人 `work/*` PR 到本组 `team/*`，同组另一人按任务书核对实际文件/数量/内容；跨组接收人只评论或给接收记录，不能直接推别人分支。组联络人汇总自己的组 PR，目标按本轮 notice 写明（当前阶段集成或已收口后的 main），写软件 SHA、材料 commit、结果和缺口。阶段材料可以引用已合并到另一个组分支的原文件链接，不能互相复制后双份维护。

M10 检查核心流程和技术边界，各组确认自己的材料已更新；有失败/阻塞继续开放，不因为到了周末或 PR 合并就关闭 #129。课程提交由指定人实际操作 Blackboard，D1/D2 登记文件/回执；GitHub PR 不能代替学校提交、成员签名或独立验收。

### 大改动后每个岗位具体补什么

- T1：接口字段/权限变了，更新对应 JSON/模拟响应/非法输入/36 条权限例中相关项，跑生成/核对，交 T2 数据影响摘要。
- T2：按钮/状态/主流程变了，更新 S01–S12 和受影响的 60 条业务例，测完整交易冒烟，发新 user-handoff 和测试汇总。
- T3：端口/部署/模型/并发/故障变了，补对应环境/恢复/性能/模型或路由格，保留原失败与新日志；不必每改一句文案都跑 900 请求。
- U1：改了哪些学生操作/文字/布局，就重走相关任务并换对应截图/手册步骤，写旧图属于哪个版本。
- U2：更新管理/部署说明、汇总截图索引、体验处置和 demo 计划，交 R1/D2；不覆盖 U1 原图。
- R2：更新受影响链路、图和技术/智能说明；R1 更新需求追踪、测试数字、限制、总稿并重新导出受影响版本。
- D1/D2：冻结前只改草稿/来源/影响记录；冻结后变更演示路径才重测、修 PPT/讲稿、重录受影响部分。


## 5. 测试功能目录：每个候选版本都要核对覆盖

以下清单根据 `frontend/src/router/index.tsx` 的实际 live 路由、核心验收场景与 OpenAPI 组织。路径里的 `:id`、`:wantedId` 用本轮数据 ID 替换。目录要求检查覆盖，不表示每个列出的动作已在当前候选中实现；不存在的动作登记“需求要求但未实现”或经范围确认“不适用”，不可直接打勾。每轮从实际路由/OpenAPI 补充新增项，确保一条路由或新增接口都有对应用例。

### T01 游客浏览与检索

- 入口：`/`、`/market`、`/product/:id`、`/wanted`、`/wanted/:id`。
- 未登录浏览商品/求购及公开详情，关键词、实际支持的分类/价格等筛选、排序、分页、清空筛选、空结果、返回/刷新、无效/不存在/下架资源。
- 纯浏览不要求登录；收藏、发布、私聊等需登录动作按契约提示并保存返回目标。所有列表从真实 API 获得，不得用兜底商品掩盖接口失败。

### T02 认证、账户与会话恢复

- 入口：`/register`、`/login`、`/profile`。
- 注册字段、邮箱格式/重复、密码校验、正确/错误登录、禁用/失效账户、退出、刷新恢复、过期会话、受保护深链接及登录后的原目标恢复。
- 本人资料可编辑字段、不可编辑字段、公开/私有字段边界；多标签页/服务重启后的会话行为按当前实现验证。

### T03 商品发布、管理与媒体

- 入口：`/publish`、`/product/:id/edit`、`/my-products` 及公开详情。
- 发布、必填/格式/价格边界、超长文本、图片数量/类型/大小/损坏、失败重试/取消、保存后列表/详情一致、编辑/上下架、已售或占用状态的操作限制。
- 文件权限、图片显示和重启后保留；非所有者不能编辑，自己不能购买自己的商品；重复点击不创建重复事实。

### T04 收藏、求购与本人数据

- 入口：`/favorites`、`/wanted/publish`、`/wanted/:id/edit`、`/wanted/:id`。
- 收藏/取消/重复操作、空列表、已售/下架商品表现、账号切换后归属；求购发布/编辑/关闭、预算/类别/地点/有效期等字段按真实契约校验、非所有者拒绝。

### T05 聊天、报价与重连

- 入口：`/chat`、`/chat/:id`，从商品或求购发起联系的实际入口。
- 买卖双方会话、会话归属、空/超长消息、发送成功/失败/重试、历史分页、断线补拉、顺序/重复消息、多会话切换；他人不能读取消息。
- 结构化报价、还价/接受/拒绝/撤回/过期按服务状态机校验；重复、旧状态和无权操作拒绝；不是每个动作都由同一方执行。

### T06 唯一订单与并发边界

- 入口：`/transactions`、`/transactions/:id`。
- 接受有效报价形成唯一有效订单并关联商品/求购/会话；买卖双方可见，第三方不可见。
- 两个买家竞争、重复接受/请求重试、商品占用、非法状态、取消/争议等实际支持动作。确认双方状态一致、数量/事件无重复；并发通过专用测试脚本验证并附原始结果。

### T07 约定、双方完成与持久化

- 入口：`/transactions/:id/meetup` 和订单详情。
- 见面时间/地点校验（含过去时间）、时区、约定版本变更、旧确认失效、双方确认同一版本；单方完成不能当双方完成，双方完成后商品/订单同步。
- 取消/争议/未完成状态限制、重复确认、非参与方拒绝；刷新、退出重登、服务重启后数据和状态保留。

### T08 评价与通知

- 入口：`/transactions/:id/review`、`/notifications`。
- 完成后参与者各自评价、重复/未完成/已取消/他人订单评价拒绝，字段边界与显示范围。
- 通知创建/列表/未读/单条已读/全部已读/跳转目标、重复操作、账号切换、失败重试；全局提醒位置和未读数正确。

### T09 举报、证据与管理员治理

- 入口：`/report`、商品/聊天/订单中的举报入口、`/admin`。
- 根据对象和买卖方身份检查原因、输入校验、附件、提交、查看本人举报与处理状态；举报证据/私聊/约定不泄漏给无权人。
- 管理端当前实际提供的用户、商品、举报列表/筛选/详情/处理/原因/审计；禁用/恢复等动作按契约测试，非管理员拒绝，重复处理及非法状态有确定结果。

### T10 智能搜索与供需匹配

- 入口：`/market` 的实际搜索、`/wanted/:wantedId/matches`。
- 输入、类别/预算/成色/地点等硬约束、空结果、排序/解释、分页、无权/无效 ID、旧版本结果。
- 服务正常、超时、异常、索引未就绪、关闭服务时的真实降级；不把相似度说成成交概率，不把规则/候选标成已经验证的模型。

### T11 价格、信誉和风险提示

- 入口：`/publish/price-advice`、公开详情允许展示的提示与 `/admin` 审核区域。
- 输入边界、区间/解释/版本/来源/免责声明、数据不足与不可用降级、字段权限、规则人工覆盖和审计；卖家自主定价，风险不自动认定欺诈/封禁。
- 功能/规则符合性与独立模型效果分开记录；没有足够真实授权评估数据时，只报告当前基线/降级与 NO_GO，不编造准确率或误差。

### T12 页面状态、布局和可访问性

- 对每条当前 live 路由记录加载、成功、空、失败重试、无权状态中适用的项，不能只测理想数据。
- 桌面 1440×900 与手机 390×844，Chrome/Edge 当前版本；长文本、滚动、侧栏、右上角账号/提醒、弹窗、键盘/焦点/标签、按钮可达性、无未处理白屏。
- 以批准的原界面为基准，接 API 不得把布局简化。截图记录视口和 SHA；生产构建也要检查，不只看开发模式。

### T13 路由别名与错误恢复

- 入口：`/orders`、`/orders/:id`、`/orders/:id/review`、`/profile/transactions` 及未知路径。
- 别名与正式交易页保持权限/行为一致；不存在路径 404、无权 403、无效资源、后端不可达、慢请求、重复点击、深链接、刷新/返回和恢复提示。

### T14 干净环境、安装包与持久化

- 另一台组员电脑或全新 VM 从指定 SHA 或指定包按部署手册安装，不复用 M10 未提交文件/账号库/依赖；记录系统、硬件、依赖、镜像/包哈希、端口、迁移头和命令。
- 空审计库迁移/种子幂等/健康检查、启动/停止/重启、媒体卷、端口占用时提示、升级与回滚路径；EXE 仅在该版本确有可运行包时测试，未交付写未交付。
- 在异机完成注册或专用账户登录、发布/浏览/聊天/报价/订单约定/完成/评价、智能降级。换本机目录不能写成异机通过。

### T15 权限、安全、性能与恢复

- 对象归属、管理权限、令牌/私密响应/日志与媒体 URL、CSRF/CORS 和实际接口测试证据；不在截图/Git 提交凭据。
- 专用数据库/Redis DB14/15/测试媒体卷中执行重复/并发、性能、依赖失败、备份恢复与损坏备份拒绝；记录请求数/并发/数据规模/硬件/命令、p50/p95/p99 和原始输出。
- 区分 PostgreSQL 恢复与 MinIO 媒体恢复的实际范围；没有实测不能写“全部可恢复”。服务失败是否可降级按真实契约验证，不能承诺任何依赖关闭后所有功能都可用。

## 6. 用户组任务包：真人实际操作什么

每轮受影响任务都要重走；发布候选执行全套。角色是当前任务身份，不是给学生账号永久分配买方/卖方。用户组从测试组接收已通过的流程、数据别名和版本；不用查看 token、改库或调用私有接口来完成任务。

### U01 游客发现商品

不开登录会话，在市场寻找符合某类用途和预算的商品，筛选后打开详情，再查看一条求购。预期能找到商品并理解价格/状态；点收藏或联系时才需要登录。记录是否被多余弹窗拦住、是否理解筛选和商品状态、返回是否丢失条件。

### U02 买家登录与咨询

从 U01 的目标商品开始登录，回到原目标，收藏并发起咨询，发送测试消息与合法报价，再查看会话和通知。预期能理解登录要求、找到卖家和报价入口、知道是否发送成功；记录找不到入口、重复发送和错误提示问题。

### U03 卖家发布与管理

用另一账号发布一件自己的测试商品、上传许可图片、编辑信息并在市场找到它，再到“我的商品”确认归属与状态。预期不需要技术人员指点即可完成；记录哪些字段不清楚、图片失败是否能重试、发布后去向是否明确。

### U04 双账号交易到完成评价

买卖双方在隔离会话完成报价处理、查看订单、记录未来的见面约定、分别确认同一版本、模拟交付后双方完成、各评价一次，并查通知。用户必须能区分“约定确认”和“完成交易”；测试商品不涉及真实付款。记录每一步找不到的动作、状态文案歧义、单方/双方状态是否让人误解。修改约定后再检查是否知道需要重新确认。

### U05 求购与智能解释

发布一条明确预算与类别的求购，查看匹配商品并理解原因；另检查价格建议是否只作参考。执行测试组准备好的智能不可用场景，观察是否知道正在降级、还能做什么。不得要求用户组自行训练模型或把分数解读为成功交易概率。

### U06 举报人与管理员

从实际对象入口提交一次模拟举报，找到“我的举报”及处理状态；管理员用另一会话查看并按规则处理，再由举报人回看。检查买卖双方原因选项是否合适、处理结果是否看得懂、私密证据是否越权显示。无关学生不能看举报证据。

### U07 失败恢复与手机体验

在 390×844 手机宽度完成浏览、聊天和通知入口；按测试组的安全场景尝试错误输入、上传失败或会话过期，再按页面提示恢复。检查侧栏/账号/提醒是否错位、按钮是否被遮挡、返回/刷新后是否丢输入。故障注入由测试组安排，不随意停掉共享服务。

### U08 新人按手册启动

用户组把手册交给未实现部署流程的测试组员，在另一台电脑或新 VM 执行 T14；用户组观察哪些步骤缺失并修订说明，M10 修技术问题，原执行人复测。用户组写手册不等于已经通过独立安装验收。

每项任务的交付是任务记录 + 反馈 Issue（如有）+ 版本化截图索引 + 手册修改 PR。任务“完成”不代表所有体验问题已解决；接收/暂缓理由与复测状态分开记录。

## 7. 文书组不能只交几句概括

报告分工的每项任务须交正文源稿、证据索引和 Review，不用“负责架构/汇总报告”一句话结项。统稿与系统设计岗位的逐项任务、文件边界与验收见[详细岗位任务书](../management/nine-member-collaboration-plan.md)。课程报告页数/格式/引用以课程原文件为准，不把 Proposal 的 4–8 页当最终报告要求。

文书、手册、PPT 引用测试结果时都要写测的是哪个 SHA、环境和多少用例；真实 API、契约 fixture、原型 Mock、人工体验与模型评估分别注明。测试失败记录保留，不只挑成功截图。M10 核对技术事实，测试执行人核对数字，统稿人负责全文术语、图表编号和来源一致。
