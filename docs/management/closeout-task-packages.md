# CampusLoop 四组收尾任务包（参考文件细化版）

版本：1.0；编制日期：2026-10-09；适用项目：CampusLoop AI。

## 一、工作安排与使用方式

后续代码实现、接口对接、数据库迁移、合并冲突和功能缺陷由技术负责人统一处理。其余八位成员自行组成四个两人组，承担技术报告、独立测试、操作手册、证据整理和演示材料。每人选定一个岗位，详细个人任务见《CampusLoop 八人自选分组与个人交付任务书》。组内一人提交组包，另一人复核；作者姓名、执行人和提交链接分别记录。

四个组分别为：文档报告组、测试验收组、操作手册与页面证据组、汇报演示组。原“优化组”的交付调整为页面问题清单、手册、截图和演示数据方案；页面问题由技术负责人修复，组员负责复测。

本分配是后续任务的重新安排，不修改成员过去的贡献。八人的姓名由报名表登记，不根据 GitHub 账号推断。M1 为黄麒玮、M10 为陈梓弘；谁参加这八个岗位，以实际报名为准。

## 二、必须统一的项目事实

- 产品是校园二手交易平台。游客可浏览商品和求购；学生账号可在不同订单中作为买方或卖方；管理员负责人工治理。系统没有仓库入库、出库或派发角色。
- 前端使用 React、TypeScript、Vite，源码在 `frontend/src/`。`frontend/index.html` 是入口文件，不能把它当作全部页面源码。
- 后端使用 FastAPI，源码在 `backend/app/`；模型在 `backend/app/models/`，迁移在 `backend/alembic/`，种子在 `backend/scripts/seed.py`。项目没有要求使用 `backend/db.py`、`backend/app.py` 或 SQLite 的 `campus.db`。
- 接口以 `openapi/campusloop.v1.yaml` 为唯一契约，生成客户端在 `frontend/src/sdk/generated/`。技术文档核对契约、模型和实际代码，用户手册核对可运行页面。
- 默认前端地址为 `http://localhost:5173`；后端本地地址调整为 `http://localhost:8001`；后端接口文档通常为 `http://localhost:8001/docs`，以交付版本实际配置为准。Compose 容器内监听 8000，本地映射到 8001；MinIO 的默认 S3 地址为 9000，控制台为 9001。
- 项目不处理真实付款，不做仓储配送，不核验真实学籍；校园认证标识按教学模拟说明。风险规则只提供人工审核线索。
- Phase 2 验可点击 Mock、契约和环境；Phase 3 验真实接口与持久化交易；Phase 4 验智能集成、解释、评估和降级；Phase 5 验发布与提交。截图必须注明阶段和实现状态。

## 四、文档报告组任务包（两人）

组内岗位：A1 需求与报告统稿，A2 设计与实现说明。共同产出英文技术报告、可编辑源稿、引用清单、需求到证据追踪清单。

### 要取得的输入

读取项目范围、当前阶段 Issue、接口契约、系统结构、数据库模型、已合并交付和测试验收组提供的结果。报告中每项“已实现”说明需要代码或测试链接；计划、原型、规则基线和模型实验分别标注。

### 要完成的具体内容

1. Introduction：校园二手交易背景、目标用户、问题、目标、边界和项目价值。
2. Requirements：角色、游客浏览与登录动作、商品/求购、聊天/议价、订单/约定/完成/评价、举报/通知/管理员、智能与降级需求；给出需求 ID 和验收条件。
3. Design：React/FastAPI/PostgreSQL/Redis/对象存储的结构与职责，数据库与资源归属，订单状态与约定版本，REST/实时消息、权限、事务、幂等及智能输出。
4. Implementation：只说明实际代码中的主要实现流程和选择理由；分别说明 Mock、真实持久化、关键词/规则和高级模型的状态。不整段粘贴源码；课程允许的必要伪代码由负责人另行确认。
5. Testing：引用测试组的执行版本、方法、结果、缺陷、复测、并发/恢复/降级证据；未执行项目写清限制。
6. Conclusions：逐项对照目标给出完成、部分完成或未完成，写出真实限制与未来工作。
7. References 与 Contributions：列出外部库、素材、数据、算法和其他实际来源；按课程要求记录 AI 使用与真实成员贡献。

### 文件与验收

交付 `docs/submission/technical-report/` 中各章源稿、`references.md`、`report-evidence-index.md`，以及 `CampusLoop_Technical_Report.docx`、对应 PDF。40–60 页是原任务包的团队建议，最终篇幅、语言和格式以教师正式要求为准；不能把 proposal 的 4–8 页要求套用到最终技术报告。

验收由 A2 复核 A1 的事实、A1 复核 A2 的术语与追踪；B 组复核测试数字；技术负责人核对实现说明。每条关键结论均能找到需求、版本和证据，全文角色、端口、枚举和状态一致。

## 五、测试验收组任务包（两人）

组内岗位：B1 功能与双账号旅程，B2 权限、异常、智能和环境。共同产出可执行用例、缺陷单、实际执行记录、复测记录和测试报告。

### 环境和账号

按输入包启动系统，用 Chrome 与 Edge 或两个隔离浏览器配置分别登录买方、卖方；另备管理员和未登录会话。账号由技术负责人提供，权限与演示数据以版本为准。完整项目可用于运行，报告与截图不得含真实学生隐私、令牌或密码。

Phase 2 前端 Mock 登录可验证原型旅程，但不计入真实认证成功。Phase 3 起用实际接口验证刷新后数据、第二账号可见结果和数据库持久化。

### 必测内容

1. 游客商品与求购浏览、搜索、筛选、排序、分页、详情和返回；收藏、联系、发布、举报与个性化匹配触发登录及来源恢复。
2. 注册/登录/退出/资料与账号异常；普通学生访问管理页和他人私有资源被拒绝。
3. 卖方发布/编辑/上下架，买方发现/收藏/聊天/报价，双方形成订单、约定同一版本、双方完成确认、评价及通知。
4. 求购发布、编辑、关闭、匹配解释；超时或服务不可用时按当前版本降级。
5. 无效字段、图片格式/数量/大小、空结果、发送失败与重试、重复提交、非法状态、旧约定版本、取消或未完成订单评价、非参与方访问和举报证据隐私。
6. 干净启动、依赖健康、迁移/种子验证；性能与恢复测试使用专用测试环境，记录命令、数据规模和原始结果。

### 文件与验收

交付 `docs/collaboration/phase-<n>/testing/` 下 `functional-test-cases.md`、`boundary-test-cases.md`、`execution-log.md`、`defects.md`、`retest-log.md`、`test-summary.md`，及证据索引和必要原始记录。每条用例必须写编号、Issue/需求、前置、账号/角色、数据、步骤、预期、实际、结果、执行人、时间、SHA 和证据路径。

Bug 单写明严重度、复现步骤、预期/实际、环境/SHA、截图或日志、受影响流程。技术负责人修复后，B 组在修复提交复测。缺陷只有复测通过才能关闭。

使用独立演示/测试数据库或命名空间；需要重置时先登记目标与恢复方案。不能清理共享数据库或删除别人的数据。演示物品和账号均为虚构。

验收要求是别人能按步骤得到同样结果。作者的代码测试和 CI 结果可作为输入，B 组独立执行记录另存；未运行、阻塞和不适用不能算通过。

## 八、每阶段一周的交接顺序

每个项目阶段继续占一个项目周。以下 D1–D7 是该阶段周内安排，不另起“五个两周阶段”。具体日历日期和课程截止由团队确定并登记，不能用相对天数代替正式提交日期。

- D1：技术负责人发布本阶段输入；八人完成选组与岗位登记，提交各自文件清单与阻塞。
- D2：A 组交报告框架与需求追踪；B 组交可执行用例；C 组交手册目录/截图计划；D 组交汇报结构和演示脚本草案。
- D3–D4：B 组执行当前可用能力并登记缺陷，C 组实际操作和截图，A 组补设计实现与引用，D 组据已验证功能制作演示。
- D5：技术负责人发布修复版本，B 组复测；C 组更新步骤/截图；A 组更新测试结论；D 组做第一轮彩排。
- D6：四组交完整候选包并交叉复核，统一提交 SHA、需求编号、功能状态和图文引用，关闭可修复材料问题。
- D7：完成复核后的组包、第二轮彩排和阶段交接。存在功能/环境/人工确认阻塞时明确登记，阶段 Issue 按实际门禁处理。

Phase 2 重点是契约/原型与设计材料；Phase 3 把 Mock 记录替换为真实双账号证据；Phase 4 整理智能正常/降级、评估与冻结清单；Phase 5 形成最终报告、手册、回归、恢复、演示和提交包。每轮都保留历史证据，不回写旧日志。

## 九、提交、分支和闭环要求

每人从本轮指定的阶段集成基线创建 `docs/<岗位>-p<阶段>-<主题>` 分支。个人 PR 提交到当前阶段指定的材料汇总分支 `docs/p<阶段>-collaboration`，说明任务编号、文件、版本、验证和接收人；技术负责人建好分支并登记实际链接后使用。汇总材料随对应阶段 PR 进入 `phase<阶段>/integration`；最终材料随阶段收口进入 main。

八人选择岗位后只编辑各自文件。A1 维护报告总稿；A2 提交设计/实现独立章节；B1 维护功能用例、功能执行与核心缺陷；B2 维护边界用例、边界执行与异常缺陷；C1 维护用户手册和截图；C2 维护管理员/部署手册和演示数据；D1 维护 PPT；D2 维护讲稿/视频。共享索引由每组指定的一人汇总。

Issue 依据保持：前端 #18/#24/#29/#34；后端 #21/#25/#30/#35；智能 #22/#26/#31/#36；管理质量 #23/#27/#33/#37。代码项由技术负责人执行；独立验收、报告、手册、汇报与贡献证据由八人提供并映射回相应 Issue。

成果接力：技术负责人交可运行版本 → B 组交测试结果/缺陷复测 → C 组交版本一致的手册/截图 → A 组交证据一致的报告 → D 组交相同版本的汇报/演示 → 团队核对清单并完成阶段收口。

报名、审查与实际操作属于组员任务。任何人不得替另一位成员写“已签字”“已复测”；技术实现完成后仍由相应执行人提交真实记录。
