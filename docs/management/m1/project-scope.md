# CampusLoop AI 项目范围与优先级

> 文档编号：M1-SCOPE-001
> 负责人：M1
> 版本：0.1 候选版
> 依据：项目说明 PDF 1.2、Phase 1 Issues 1-4
> 最后更新：2026-09-19

## 1. 项目定义

CampusLoop AI 是面向大学生的校园二手交易网页平台，通过统一商品市场、交易协作记录和可解释的智能搜索/匹配能力，降低信息分散、供需错位和线下面交协商成本。

平台记录从商品发现到双方确认完成的协作过程，但不处理真实付款、不担保商品质量、不核验真实学籍，也不替代用户完成线下查验。

## 2. 问题背景

1. 商品和求购分散在群聊、校园墙和通用平台，格式不统一且容易过期。
2. 关键词难以理解“预算、用途、成色、地点”等自然语言需求。
3. 求购与商品可能在不同时间出现，用户需要持续重复搜索。
4. 定价缺少统一参照，校园面交时间与地点需要反复协商。
5. 校园并不天然可信，取消、爽约、骚扰、虚假描述和举报需要持续记录与人工治理。

## 3. 目标用户与角色

| 角色 | 核心目标 | 边界 |
|---|---|---|
| 学生用户 | 发布、发现和交易校园闲置物品 | 一个账号可在不同交易中作为买方或卖方 |
| 买方 | 搜索/接收匹配、聊天、报价、确认见面与完成、评价 | 不能购买自己的商品 |
| 卖方 | 管理商品、处理报价、确认见面与完成、评价 | 只能修改本人资源 |
| 管理员 | 处理用户、商品、举报、风险线索和基础统计 | 权限由后端验证，敏感操作必须记录原因和审计日志 |

## 4. 核心价值

- 用统一、可检索、可追踪的市场替代碎片化信息流。
- 用完整交易状态和双方确认减少只靠聊天记录协作的不确定性。
- 用求购、语义检索和可解释匹配连接延迟出现的供需。
- 在任何智能功能不可用时保留基础发布、浏览、关键词搜索和交易能力。
- 用最少必要数据、权限检查和人工审核建立可解释的可信机制。

## 5. 第一阶段成功标准

第一阶段成功不等于系统功能完成。当前阶段达到以下条件才算形成需求候选版：

1. 每项纳入功能都有编号、主责、协作者、依赖、优先级、计划周次和可执行验收条件。
2. MVP 覆盖商品发布、搜索、聊天、议价、订单、见面约定、双方完成确认和评价的完整闭环。
3. 四个小组边界可映射到页面、业务实体、接口/数据能力和测试场景。
4. Core/Stretch 不阻塞 MVP，智能服务均有基线、解释、评估和降级方案。
5. 未确认项有负责人和下一截止时间；文档不把候选方案写成已实现事实。

## 6. MVP 候选范围

| 能力 | 纳入理由 | 最低交付边界 |
|---|---|---|
| 账号与资料 | 所有业务的身份和权限基础 | 注册、登录、退出、模拟认证标识、资料和角色权限 |
| 商品与市场 | 形成供给侧主流程 | 发布、编辑、上下架、逻辑删除、多图、分类、成色、价格、地点、列表和详情 |
| 关键词搜索与筛选 | AI 不可用时仍可发现商品 | 标题/描述/类别/品牌关键词及价格、分类、成色、地点筛选 |
| 收藏 | 支持持续关注商品 | 收藏、取消、列表及已售/下架状态 |
| 聊天与议价 | 交易协作入口 | 双人消息、历史补拉、结构化报价、接受/拒绝/还价/过期 |
| 订单 | 保存交易事实 | 接受报价生成唯一订单、状态事件、事务、并发和幂等约束 |
| 见面约定 | 支持校园线下面交 | 记录双方协商后的时间地点、修改版本和双方确认；不做智能推荐 |
| 双方完成确认 | 防止单方完成 | 同一有效约定下双方分别确认后完成，商品转为已售 |
| 评价 | 建立交易后反馈 | 仅完成订单参与者各评价一次 |
| 举报与通知 | 支持治理和流程提醒 | 举报、证据权限、站内通知、管理员处理和审计 |
| 基础管理后台 | 保证人工治理 | 用户、商品、举报管理和最小统计 |

## 7. Core 候选范围

Core 只在 MVP 稳定后进入集成：

- 求购市场与生命周期。
- AI 语义搜索，必须保留关键词降级。
- 求购-商品供需匹配，先硬约束再软匹配并解释原因。
- 价格建议区间，先规则基线，数据满足条件后再评估回归模型。
- 规则化信誉说明，新用户采用中性起点。
- 基础审计与数据分析，明确时间范围、分母和数据来源。

## 8. Stretch 候选范围

- 风险智能实验，仅向管理员提供人工审核线索。
- 智能商品描述助手。
- 高级推荐和高级数据分析。
- 邮件等额外通知渠道。
- Isolation Forest 等异常检测实验。

Stretch 在第 8 周冻结前仅可在 MVP/Core 稳定、有数据许可且存在可复现评估时纳入。

## 9. 明确排除项

| 排除项 | 理由 |
|---|---|
| 支付宝/微信/银行卡、资金结算或支付担保 | 项目只记录交易协作，不承担金融责任 |
| 真实物流与配送跟踪 | 核心场景为校内线下面交 |
| 真实学校 SSO、真实学籍或身份证认证 | 仅提供教学模拟标识，避免外部系统和敏感身份数据 |
| 智能见面时间/地点推荐 | PDF 1.2 明确仅记录双方私聊协商结果 |
| 跨校交易 | 超出校园边界和十周周期 |
| Arduino、RFID、NFC、摄像头、智能柜等硬件 | 项目为纯软件系统 |
| 区块链与大量微服务/Kubernetes | 不解决当前核心问题且增加交付复杂度 |
| 商业级反欺诈保证 | 风险结果只能作为人工审核线索 |
| AI 自动定价、自动封禁或自动认定欺诈 | 最终价格和治理决定必须由人作出 |

## 10. 范围控制规则

- 第 2 周形成候选范围，第 4 周锁定需求基线，第 8 周停止新增功能。
- 新需求必须提交变更记录，说明价值、工作量、依赖、风险和被替换的工作。
- 如果 MVP 延迟，优先移除 Stretch，再缩减 Core，不删除权限、数据一致性和核心异常测试。
- README、演示和汇报必须同时标明“已实现、原型/Mock、计划、暂缓或排除”。
