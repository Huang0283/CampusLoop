# 五周单周阶段计划与五次汇报检查点

> 文档编号：M1-PLAN-001
> 负责人：M1
> 质量复核：M10
> 版本：1.0
> 最后更新：2026-09-27
> 说明：文件名 `ten-week-plan.md` 为兼容既有 Issue、PR 和证据链接而保留；当前正式执行口径是五个连续阶段，每个阶段严格占一个项目周。教师如调整具体汇报日期，只调整该周内的日程，不自动延长阶段或把验收顺延到下一周。

## 1. 总体执行原则

项目按 Phase 1 至 Phase 5 连续推进，每个阶段只占一周，并在周末形成一个可独立检查、可演示、可回滚、可交接的小闭环。

每周都必须同时回答以下问题：

- 本周接收了上一阶段的哪些文件、提交和结论。
- 四个小组分别完成什么任务，由谁负责。
- 交付物保存在哪里，关联哪个任务编号和提交号。
- 非作者如何运行、检查或演示本周结果。
- 哪些内容通过、失败、延期或正式移出范围。
- 下一阶段由谁接收，接收后必须执行什么动作。

未达到阶段门禁时，不得仅凭截图、口头说明、Mock、未合并分支或“之后再做”把阶段标记为完成。未完成项必须登记：阻塞事项、Owner、依赖人、影响、下一动作和明确截止时间。

## 2. Phase 1：第 1 周——范围、可行性与质量框架

### 本周目标

把项目总设想拆成能够由十名成员执行和验收的候选范围。确定 MVP、Core、Stretch 和 Out，完成页面旅程、领域规则、平台方案、智能功能可行性与质量策略，使第二周可以直接冻结设计和契约，而不是重新猜需求。

### 管理质量组：M1、M10

- M1 拆分需求并分配唯一需求 ID，写清用户、触发条件、成功结果、失败结果、Owner、依赖和计划阶段。
- M1 完成优先级、RACI、替补关系、升级路径、需求追踪和五阶段计划。
- M10 完成测试层级、验收场景、缺陷等级、关闭证据和重新打开条件。
- M1/M10 组织范围评审和第一次汇报彩排，记录参与人、争议、决定、行动项、Owner、截止时间和复核结果。

### 前端体验组：M2、M3、M4

- M2 审计前端工程、路由、权限、公共组件和页面状态，形成页面/路由/角色总表。
- M2 完成登录、注册、资料、导航、布局和设计规范候选。
- M3 完成市场、商品、求购、搜索、筛选、匹配和价格建议的低保真流程与字段清单。
- M4 完成聊天、报价、订单、见面、双方确认、评价、举报、通知的低保真流程、角色动作和异常状态。
- 三人交叉检查页面命名、公共组件边界、角色权限和完整交易旅程，避免重复设计或流程断点。

### 后端与平台组：M5、M6、M9

- M5 定义账号、资料、角色、会话、认证状态、字段可见性和治理权限边界。
- M6 定义商品、求购、消息、报价、订单、见面、评价、举报、通知的实体、状态机、不变量和并发风险。
- M9 完成系统上下文、组件职责、ER 候选、运行平台、端口、环境变量、迁移、CI、日志和备份恢复候选。
- M5/M6/M9 汇总至少十个权限、状态、并发或环境高风险场景，并分配设计 Owner 与测试 Owner。

### 智能功能组：M7、M8

- M7 定义关键词搜索、语义搜索和供需匹配的输入、输出、规则基线、触发方式、解释字段和评估方法。
- M8 盘点价格、信誉和风险所需数据的来源、许可、字段、缺失和敏感性，设计规则基线和人工治理边界。
- M7/M8 为搜索、匹配、价格、信誉和风险分别给出 go、conditional 或 no-go 结论，并写清依赖、降级方案、Owner 和期限。
- 不训练复杂模型，不编造样本规模或指标，不把风险线索写成自动处罚。

### 本周必须交付

- 范围与优先级、需求追踪、RACI、风险与五阶段计划。
- 页面与路由总表、低保真原型、角色动作和异常状态。
- 账号边界、领域实体、状态机、系统上下文、ER 候选和运行方案。
- 智能能力可行性、规则基线、数据许可、评估计划和能力决策。
- 测试策略、核心验收场景、缺陷流程、范围评审和彩排记录。

### 周末退出门禁

- 所有纳入功能均有需求 ID、唯一 Owner、依赖、阶段和验收方式。
- 页面旅程能映射到后端领域和智能输入输出，不存在责任空白。
- 所有个人产物已通过组内 Review，并进入各自小组集成分支。
- 四个小组汇总 PR 已进入 `phase1/integration`。
- M10 已检查可测试性，M1 已确认范围和遗留项。
- 阶段收口 PR 合并到 `main` 后，才可统一关闭四个 Phase 1 Issue。

### 交给第 2 周

冻结候选所需的需求、页面旅程、状态与权限候选、数据可行性、测试场景、开放决策和完整提交号。

## 3. Phase 2：第 2 周——设计基线、契约与统一环境

### 本周目标

把第一周的候选内容转换成互相一致、可以启动、可以生成、可以测试的设计基线。第二周只证明原型、契约、数据库、环境和评估方案一致，不声称真实业务联调完成。

### 管理质量组：M1、M10

- M1 组织需求和设计基线评审，冻结本周允许实现的范围。
- M1 确认需求 ID 与页面、OpenAPI、数据库、智能输出和测试场景的映射。
- M10 建立契约测试、环境冒烟、权限边界和下一周 E2E 场景。
- 对未冻结字段或状态建立变更记录，不允许成员私自在各自分支定义不同版本。

### 前端体验组：M2、M3、M4

- M2 完成可点击应用壳、导航、角色入口、公共状态、组件规范和登录/资料原型。
- M3 完成市场、商品、求购、搜索、匹配和价格建议的可点击原型。
- M4 完成聊天、报价、订单、见面、评价、举报和通知的可点击原型。
- 三人按冻结 OpenAPI 建立页面到接口映射、Mock 替换清单和成功/失败/无权限状态。
- 游客可以浏览公开市场和商品详情；需要身份的发布、收藏、聊天、交易等动作才触发登录引导。

### 后端与平台组：M5、M6、M9

- M5/M6 发布版本化 OpenAPI，包含认证、商品、求购、聊天、报价、订单、见面、评价、举报和通知的成功与错误响应。
- M5/M6 提供最小服务骨架、权限规则、状态转换规则和契约测试样例。
- M9 完成数据库迁移、种子数据、端口和环境变量契约、Compose 或等价启动方式、CI 冒烟检查和服务健康检查。
- 生成并提交与 OpenAPI 版本一致的前端 SDK；禁止手工修改生成目录后不更新源契约。

### 智能功能组：M7、M8

- M7/M8 冻结数据字段、标注规范、训练/验证/测试拆分原则、基线输入输出、评估命令和错误格式。
- 发布搜索、匹配、价格、信誉和风险的版本化服务契约与示例。
- 明确数据不足、模型不可用、超时和版本不匹配时的降级响应。
- 只有满足许可和可复现要求的能力才进入第三或第四阶段。

### 本周必须交付

- 可点击原型、组件规范、路由角色规则和页面/API 映射。
- 通过校验的 OpenAPI、生成 SDK、成功/失败样例和契约测试。
- 数据库迁移、种子数据、统一启动环境、端口说明和健康检查。
- 智能数据、输出、评估、解释和降级契约。
- 需求/设计基线记录、验证记录、Mock 替换计划和阶段交接。

### 周末退出门禁

- 非作者能够按文档启动统一环境并得到健康结果。
- OpenAPI 校验通过，生成 SDK 与契约提交一致。
- 数据库可从空环境迁移并加载测试数据。
- 原型能够展示主路径、失败、空数据和无权限状态。
- M10 确认契约和环境可测试，M1 确认范围冻结。
- 阶段收口 PR 合并到 `main` 后，才可创建第三阶段分支。

### 交给第 3 周

冻结的接口版本、SDK、迁移版本、种子账号、页面/API 映射、智能基线服务契约和可直接执行的验收场景。

## 4. Phase 3：第 3 周——真实 MVP 实现与双账号闭环

### 本周目标

使用真实 API、数据库和消息机制完成可持久化的双账号交易闭环。固定响应、仅内存状态或未标记 Mock 不能关闭真实联调任务。

### 管理质量组：M1、M10

- M1 按冻结范围检查实现，不允许第三周临时扩展功能。
- M10 执行接口、权限、状态机、WebSocket 和浏览器 E2E 测试。
- 缺陷按 P0-P3 处理；P0/P1 必须修复或由 M1 正式移出本阶段范围。

### 前端体验组：M2、M3、M4

- M2 接入真实注册、登录、退出、资料、角色和会话失效接口。
- M3 接入真实市场、商品、求购、搜索、筛选、收藏和发布管理接口。
- M4 接入真实聊天、报价、订单、见面、双方确认、评价、举报和通知接口。
- 所有页面处理加载、空数据、失败、重试、权限拒绝、重复提交和刷新恢复。
- 对 Phase 2 Mock 逐项替换；保留的 Mock 必须标明原因、Owner 和替换期限。

### 后端与平台组：M5、M6、M9

- M5 实现认证、会话、资料、角色、字段可见性和管理员权限。
- M6 实现商品、求购、收藏、消息、报价、订单、见面、完成确认、评价、举报和通知。
- M6 保证状态转换、事务、幂等、唯一约束和并发接受行为可验证。
- M9 提供稳定数据库、缓存/消息、对象存储、迁移、测试数据、日志和可重复启动环境。
- 进程重启后关键业务事实仍可恢复，客户端不得成为订单或权限事实来源。

### 智能功能组：M7、M8

- M7 提供可调用的关键词搜索与规则匹配基线。
- M8 提供可调用的价格规则区间及已批准的信誉/风险规则基线。
- 服务必须符合第二周契约，记录版本，并提供不可用时的确定性降级结果。
- 本周只提供支持 MVP 或第四周集成所需的最小基线，不提前声称模型效果。

### 本周必须交付

- 可启动的前端、后端、数据库和必要服务。
- 真实迁移和种子账号；API、权限、状态和 WebSocket 测试结果。
- 双账号从登录、发布、浏览、聊天、报价、订单、见面、双方确认、评价到举报/通知的 E2E 记录。
- 缺陷清单、修复提交、遗留项和 MVP 版本标签。

### 周末退出门禁

- 两个账号能够通过浏览器完成真实持久化主流程。
- 刷新或重启不会丢失已确认的交易事实。
- 非参与者不能访问私聊、订单或举报证据。
- 过期报价、非法转换、重复提交和并发接受得到一致处理。
- 必做 E2E 步骤不依赖未标记 Mock。
- M10 验收通过且 M1 确认 MVP 范围后，阶段收口 PR 才能合并到 `main`。

### 交给第 4 周

已验收 MVP 标签、真实事件和数据结构、现存缺陷、性能基线、智能服务接入点以及治理和降级测试场景。

## 5. Phase 4：第 4 周——智能集成、治理补齐与功能冻结

### 本周目标

至少两个有数据和评估依据的智能功能接入真实业务，完成基线对比、解释、隐私、治理与降级验证；周末冻结功能，此后不得无审批新增范围。

### 管理质量组：M1、M10

- M1 维护集成范围和冻结清单，区分已实现、实验性、延期和移除内容。
- M10 独立复现指标，并测试权限、隐私、服务不可用、超时和恢复场景。
- 指标、截图、演示和文档必须指向同一数据版本、模型版本和提交号。

### 前端体验组：M2、M3、M4

- M3 接入搜索、匹配和价格建议，展示依据、限制、数据不足和降级提示。
- M2/M4 接入必要的信誉、风险或管理员人工审核页面，不把智能结论展示成事实或自动处罚。
- 智能服务不可用时，公开浏览、发布、聊天和基础交易仍可继续。
- 完成关键页面的权限、错误、空状态、移动端和可访问性检查。

### 后端与平台组：M5、M6、M9

- M5/M6 编排智能请求，保存输入版本、结果版本、解释和状态，但不允许智能输出绕过权限和订单状态机。
- M6 实现任务触发、幂等、去重、结果存储和通知控制。
- M5 保证风险线索只能进入人工审核，申诉和证据可见性符合权限规则。
- M9 记录模型、数据、Worker、缓存和任务队列版本，提供健康、失败和恢复证据。

### 智能功能组：M7、M8

- M7 在同一评估集上比较关键词基线与混合搜索/匹配候选，输出 Precision@K、Recall@K、MRR 和解释示例。
- M8 在可用数据上比较规则基线与价格候选，输出 MAE、MAPE 或区间覆盖率，并明确挂牌价和成交价边界。
- 对信誉和风险仅输出透明证据或人工审核线索，不自动改变用户、订单或处罚事实。
- 无法满足数据许可、样本量或复现要求的能力必须降级或标记 no-go。

### 本周必须交付

- 至少两个真实接入的智能能力及其接口、页面和业务触发证据。
- 基线与候选的运行命令、数据版本、原始指标和结论。
- 解释、限制、隐私、人工治理和降级演示。
- 功能冻结清单、发布候选范围、遗留缺陷及 Owner。

### 周末退出门禁

- 指标可由非作者按提交说明复现。
- 智能结果有解释且不冒充交易事实。
- 智能服务失败不阻塞基础交易闭环。
- 数据来源、许可和隐私状态明确。
- P0/P1 缺陷清零或正式阻塞发布。
- M1 签署冻结清单，M10 完成集成和降级验收，阶段收口 PR 合并到 `main`。

### 交给第 5 周

冻结的发布候选、指标报告、数据/模型版本、已知限制、缺陷优先级、演示范围和最终文档清单。

## 6. Phase 5：第 5 周——稳定化、复现与最终交付

### 本周目标

不再新增功能，只修复批准的缺陷、完成干净部署和回归、验证恢复能力，并提交与最终版本完全一致的系统、报告、手册、演示和贡献证据。

### 管理质量组：M1、M10

- M1 对照需求追踪表核对实现、测试、文档和演示结论，编写最终范围和已知限制。
- M1 汇总技术报告、贡献记录、演示脚本、提交清单和最终汇报材料。
- M10 执行全量回归、权限和安全检查、恢复演练、性能测试和非作者复现。
- M1/M10 只接受当前最终提交对应的证据，不接受旧分支或旧截图替代。

### 前端体验组：M2、M3、M4

- 修复冻结范围内的交互、错误处理、布局、无障碍和浏览器兼容问题。
- 完成用户手册、页面入口、演示账号和主流程说明。
- 对最终 SDK 和接口版本执行构建、Lint、关键页面和 E2E 回归。
- 确保游客浏览和登录后操作边界与最终权限规则一致。

### 后端与平台组：M5、M6、M9

- 修复冻结范围内的权限、事务、并发、恢复和性能缺陷。
- M9 在干净环境验证配置、迁移、种子数据、启动、日志、健康检查、备份和恢复。
- 运行并保存 100 并发用户测试的环境、脚本、原始结果、响应时间、错误率和资源使用情况。
- 检查仓库无密钥、真实隐私数据、临时数据库、日志包或不可复现构建产物。

### 智能功能组：M7、M8

- 固定数据、模型、规则、随机种子、依赖和运行命令。
- 复验最终版本指标、解释和降级，确保论文和演示数字与原始结果一致。
- 编写智能功能使用边界、限制、数据许可和复现说明。
- 不在第五周临时更换模型或新增未经回归的能力。

### 本周必须交付

- 最终源码、配置模板、迁移、种子数据和发布标签。
- CI、全量回归、权限、安全、性能、备份恢复和干净部署证据。
- 技术报告、用户手册、管理员手册、演示脚本、汇报材料和贡献记录。
- 已知问题、延期功能和最终提交清单。

### 周末退出门禁

- 非作者能够从干净环境启动并执行主流程。
- 所有 P0/P1 缺陷关闭，其他缺陷有影响和处理结论。
- 文档、接口、数据、指标、截图和演示均对应最终标签。
- 备份恢复、降级和关键权限场景通过。
- 提交包无缺项、无密钥、无真实隐私数据和无虚假指标。
- M1/M10 签署最终验收，最终标签和提交清单已记录。

## 7. 每周固定节奏

### 周一：输入锁定与任务拆分

- 从上一阶段已验收的 `main` 创建本阶段集成分支。
- 每个任务记录输入版本、Owner、交付路径、Review 人和验收命令。
- 依赖缺失时当天登记阻塞，不允许消费者自行猜测契约。

### 周二至周三：分组执行与上游先行

- 契约或规则提供者先提交可评审产物。
- 消费者只基于已版本化输入开发；临时 Mock 必须明确标记。
- 每日同步完成内容、当天计划、阻塞和接口变化。

### 周四：小组集成

- 个人任务 PR 先合并到小组集成分支。
- 组内负责人检查任务编号、交付路径、验证结果和遗留问题。
- 小组汇总 PR 合并到阶段集成分支，M10 开始独立测试。

### 周五：阶段验收与交接

- M10 记录命令、环境、实际结果、失败日志和缺陷。
- M1 复核范围、延期、移除项和下一阶段接收清单。
- 只有阶段收口 PR 可以把本阶段结果合并到 `main`。
- 下一阶段必须从收口后的 `main` 创建，不能从小组分支继续堆叠。

## 8. 合并和依赖顺序

每周统一使用以下顺序，减少成员之间同时修改共享文件产生的冲突：

- 管理质量组先发布本周范围和验收口径。
- 后端、平台和智能组发布规则、契约或服务。
- 前端组消费已确认输入并完成页面或联调。
- M10 在阶段集成提交上独立验收。
- M1 汇总范围和交接，提交唯一阶段收口 PR。

公共 OpenAPI、SDK、路由表、需求追踪、阶段验收和发布清单必须有唯一 Owner。其他成员通过评论、建议或独立任务文件提供修改，不同时直接重写同一共享文件。

## 9. 延误、变更和失败处理

- 当天发现依赖缺失，当天登记，不等到周五。
- 先移除 Stretch，再缩减 Core；不得删除权限、隐私、事务、恢复或异常测试来伪装按时完成。
- 范围、接口、状态、数据或计划变化必须进入仓库记录，并由受影响负责人确认。
- 周五未完成项必须写明是否阻塞阶段；若阻塞，则阶段 Issue 和 PR 保持开放。
- 只有 M1 可以批准移出范围，M10 必须同步更新验收场景和回归范围。
- 不允许把本周未完成任务自动搬到下一周，同时宣称本周闭环已经完成。

## 10. 总项目闭环

五个阶段按以下证据链形成总闭环：

- Phase 1 决定做什么、谁负责、如何验收。
- Phase 2 把决定转换成一致的原型、接口、数据库、环境和测试契约。
- Phase 3 使用真实实现完成基础交易闭环。
- Phase 4 在真实闭环上接入可评估、可解释、可降级的智能功能并冻结范围。
- Phase 5 对冻结版本完成复现、测试、恢复、文档、演示和提交。

最终所有重要结论都必须能够追溯到需求 ID、实现提交、测试结果、演示步骤和最终标签。
