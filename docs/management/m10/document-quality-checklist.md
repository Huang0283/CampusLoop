# 第一阶段文档质量检查表

> 文档编号：QUALITY-DOC-001  
> 负责人：M10  
> 版本：0.1 候选版  
> 适用阶段：第 1-2 周需求验证  
> 最后更新：2026-09-19

## 1. 使用规则

- 作者提交前自查一次，评审人在 Pull Request 中复查一次。
- `done` 只能用于已有仓库路径、提交、测试输出或演示步骤等可复核证据的事项。
- 尚未实现的功能统一使用“计划”“候选”“待验证”，不得写成已上线、已完成或已达到某指标。
- 检查失败时记录文件、章节、问题、负责人、修复期限和复核结果，不以口头说明关闭。

## 2. 基本信息

- [ ] 标题能准确说明文档用途。
- [ ] 标明负责人、版本、状态和最后更新时间。
- [ ] 标明适用阶段及上游依据。
- [ ] 候选、已评审、已冻结、已废弃等状态清楚。
- [ ] 文件名使用小写英文和连字符，路径归属明确。
- [ ] 文档与 PDF、README 或 Issue 存在差异时，写明采用哪个版本及原因。

## 3. 范围与需求

- [ ] 每项需求有唯一编号。
- [ ] 每项需求有主责、协作者、依赖、优先级、计划周次和状态。
- [ ] 每项需求至少有一条可执行验收条件。
- [ ] MVP、Core、Stretch 和排除项没有混用。
- [ ] Core 与 Stretch 不阻塞 MVP 的完整交易闭环。
- [ ] 不包含真实支付、真实学校 SSO、物流、身份证认证、跨校交易或硬件能力。
- [ ] 见面功能仅记录双方协商结果，不包含智能时间或地点推荐。
- [ ] AI 分数不表述为成交概率，价格建议不表述为自动定价，风险分数不表述为欺诈判定。

## 4. 业务与技术一致性

- [ ] “商品、求购、匹配、报价、订单、见面约定、完成确认、评价、举报、风险线索”术语一致。
- [ ] 前端页面、后端动作、数据实体和测试场景可以相互映射。
- [ ] 状态名称及转换条件在文档间一致。
- [ ] 权限同时说明角色和资源所有权，不以隐藏按钮代替后端授权。
- [ ] PostgreSQL 是交易事实来源，Redis 只保存缓存或临时状态。
- [ ] 智能服务不可用时，发布、浏览、关键词搜索和基础交易仍可继续。
- [ ] 技术栈分清“仓库已存在”“候选采用”和“仅在条件满足后采用”。

## 5. 测试与证据

- [ ] 验收条件包含前置条件、操作、预期结果和证据位置。
- [ ] 正常、失败、无权限、重复提交和并发路径已考虑。
- [ ] 测试数据不包含真实密码、令牌、聊天隐私或举报证据。
- [ ] 性能、覆盖率、准确率和样本量只引用真实运行结果。
- [ ] 截图仅作辅助，不能替代测试日志、命令输出或可复现步骤。
- [ ] 未执行的测试明确标为“待执行”。

## 6. Markdown 与仓库质量

- [ ] 标题层级连续，表格、链接、代码块和 Mermaid 语法可读。
- [ ] 相对链接可从当前文件打开。
- [ ] 中文、英文缩写和数字间距一致。
- [ ] 没有空占位符、模板残留、乱码、密钥或个人敏感信息。
- [ ] README 中的目录、启动命令和当前状态与仓库实际一致。
- [ ] PR 只包含本任务相关文件，并说明验收证据和跨组影响。

## 7. 发布前门禁

以下任一项不满足时不得标记为 `done`：

1. 无负责人或无验收条件。
2. 存在 P0/P1 未关闭缺陷。
3. 文档把计划功能描述为已经实现。
4. 接口、状态、权限或数据口径与受影响小组尚未确认。
5. 包含真实密钥、个人敏感信息或无法说明来源的数据。
6. 只能用截图或口头承诺证明完成。
