# CampusLoop 九人协作与最终交付规划

版本：1.4

日期：2026-10-27

适用对象：CampusLoop 校园二手交易系统

技术负责人：M10 陈梓弘（20253801098）；当前同时承担 M1 管理任务，其他九人自行选择材料岗位。

协作方式：GitHub Issue、分支、Pull Request、可追溯证据

## 文档目的

本文件把剩余九名组员的工作拆成可以独立领取、独立提交和独立验收的任务。九名组员负责测试、技术报告、用户手册、页面证据、演示和提交材料；M10 负责继续优化系统功能、API、前端 UI、真实联调、缺陷修复和最终技术合并。

本文件不预先决定谁加入哪一组。九名组员先按个人兴趣和能力选择下述工作方向及岗位，由组员自行协商形成分组，再在 Issue #129 登记姓名、岗位、组内复核人和分支。每个岗位有明确文件、每周结果、复核人和接收人。个人贡献必须以 GitHub PR、文件版本、测试日志、截图索引、演示记录或其他可核对证据为准。没有实际执行的内容只能写成待办，不能写成已完成。

## 课程交付约束

以下要求来自 `JC2001-GroupProjectDescription-and-Requirements-2026-27(1).pdf`，是本项目协作的硬约束：

- 项目计划书必须提交，但不计分；课程截止时间以 Blackboard 为准，团队不能自行猜测日期。
- 技术报告占总项目成绩的 50%。正文从 Introduction and Project Context 到 Conclusions and Future Work，要求 40 至 60 页；标题页、目录、图表目录、References 和 Appendix A 不计入正文页数。
- 技术报告按 A4、四边 2.54 cm 页边距、单栏、12 pt Arial 或 Times New Roman、1.5 倍行距排版，最终提交单个 PDF；报告不粘贴源代码，源代码放入 PoC 提交包。本内部中文协作规划使用 OceanScope 风格的宋体正文与黑体标题，不作为课程英文报告模板。
- Proof-of-Concept 软件占 30%。提交包必须包含源代码、可运行版本、依赖或支持文件以及 8 至 12 页用户手册 PDF。
- 项目演示占 20%。课程要求一次 15 分钟演示，提交 PowerPoint 和 MP4；录像必须出现演示者本人，不能只录屏或用自动化录像代替真人讲解。
- 课程安排四次 Project Updates，至少提交三次。每次更新要写已完成工作、困难及处理方法、下一步，并且内容必须反映真实进度和与导师的讨论。
- 技术报告 Appendix A 必须附 Group Workload Profile。所有成员应在没有争议时签名；如不同意贡献评价，不应签名并应按课程要求联系课程负责人。贡献百分比必须有可量化证据，不能凭感觉填写。
- 所有外部代码、图、图片、数据、模型、算法和 AI 使用都要按学校要求说明来源和使用方式；不把自动生成内容当作成员独立贡献。

## 九人自选工作方向

以下是四种互相接力的工作方向，不是已经分配完成的组员名单。九名组员可在各方向内自行组队并选择个人岗位；每个方向建议人数只用于平衡工作量，不构成固定名额。若报名人数不平衡，由组员协商调整并在 Issue #129 登记，确保所有岗位都有负责人。

### 文书与技术报告方向（建议 2 人）

把真实实现、需求、设计、测试结果和限制写成可评分的英文技术报告，并维护事实追踪。可选择“需求与报告统稿”及“系统设计与技术证据”两个岗位。成员按自己的选择登记。

### 独立测试与验收方向（建议 3 人）

从非作者视角独立复现功能、权限、异常、环境、性能和恢复。可选择“测试数据与身份权限”“双账号交易与业务状态”“异机部署、性能与恢复”三个测试岗位。测试数据清单、独立评估集和每日简报归测试方向，岗位仍由组员自行认领。技术负责人修复代码，测试执行人保留失败记录并在修复提交上复测。

### 使用说明与页面截图方向（建议 2 人）

让没有参与编码的人能够按说明运行和使用系统。“用户手册”就是安装、启动、登录和完成交易的操作说明；“页面证据”就是指定版本的真实截图及操作记录，例如接受报价后出现哪个订单页面，供报告和演示引用。可选择“学生用户手册与主流程”“管理员/部署说明与页面证据”两个岗位。手册组负责写清步骤与保存截图，测试组负责独立验证这些步骤，M10 负责修复技术问题；不能只交截图而没有说明。

### 最终演示与提交方向（建议 2 人）

在功能和 UI 冻结后制作课程演示。可选择“PPT、课程要求与证据来源”“讲稿、双账号演示、彩排和 MP4”两个岗位。演示成员负责遵守真实评估结论和 NO_GO 限制，不提前把变化中的页面录成最终视频。

### 自选登记规则

九名成员分别选择一个主要方向和个人岗位，在 Issue #129 登记姓名、成员编号、方向、岗位、交付文件、组内复核人和个人分支。登记后如需调整，由本人在 Issue 留言说明原因、已完成材料接收人及新负责人，再更新登记；不得由技术负责人静默代分组。

### 小组长期分支与个人临时分支

以下四条跨阶段长期组分支由 M10 从本轮 main 创建并推送，组员不用再建立；分支存在不代表已分配姓名。各组自行推选材料集成人，在 Issue #129 认领负责人和复核人：

- **文书与技术报告**：长期组分支：`team/reporting`；长期分支负责人：该组自行推选的材料集成人。
- **独立测试与验收**：长期组分支：`team/testing`；长期分支负责人：该组自行推选的材料集成人。
- **使用说明与页面截图（用户体验）**：长期组分支：`team/user-experience`；长期分支负责人：该组自行推选的材料集成人。
- **最终演示与提交**：长期组分支：`team/presentation`；长期分支负责人：该组自行推选的材料集成人。

长期组分支在所有后续阶段复用，不因每周或每次改动重建。成员认领预建的 `work/<方向>/<岗位>` 分支，一人独用；每轮工作经 Review 后 PR 回对应 `team/*`。每轮合并后同步组分支再继续，认领人仍使用的岗位分支不自动删除。小组材料经复核后进入版本通知指定的 `phase<n>/integration`；阶段已收口后的日常材料更新再向 `main` 发汇总 PR。禁止直接推送 `main` 或他人长期组分支。

`main` 必须长期保留，是唯一正式稳定主干。现存 `phase<阶段>/*` 技术集成分支只服务对应阶段的开发、验收和阶段 PR；阶段收口 PR 合并且没有未合并提交、开放 PR 或后续依赖后，可以删除。已合并的个人 `task/*` 临时分支可以在 PR 合并并记录 SHA 后删除。未合并、仍在 Review、有人继续使用或依赖未解决的分支必须保留。不能因为“临时”就删除现有远端分支；先逐条核对 PR、提交和依赖，再清理明确完成的分支。

长期组分支和九条岗位工作分支已预设名称，见后文岗位任务及各组 WORKFLOW.md。组员认领现有岗位分支后直接拉取，不能重新从旧分支建立同名分支。组内姓名由成员协商，不擅自推断 M 编号。

工作量按每周实际用例/材料/执行/复核共同核对，不保证单凭岗位数量就完全相等。数据岗位还承担权限测试与评估数据复核；环境岗位还承担异常/恢复与独立复算。若阻塞导致本周工作失衡，认领人在 Issue 说明可转交的独立用例/文件，由双方明确交接，不重叠编辑共享文件。

认领前所有岗位均为“待认领”，建议人数不代表已经组好队。可兼岗或拆分岗位，但每项文件只能有一个编辑负责人，所有交付均须有人认领。组员同时推选材料集成人，负责登记、共享索引及材料汇总；该职责不自动分配给任何成员。

## 先看懂这些规则，再认领岗位

本版的数量是团队从现在开始执行的最低交付要求，不是课程另加的要求，也不表示仓库已存在这些产物。首次把基础包建好，以后每次大改只补受影响的用例、数据、章节和截图；不要求每天重新造 60 件商品、重写报告或再收一遍同样数据。一次发布验收仍须把完整目录核对一遍。数量达到但覆盖遗漏，仍然不合格。

- **软件版本 SHA**：所测代码的完整提交号；从 M10 通知复制。材料自己的 commit 另记，不能把两者混在一起。
- **虚构静态样例**：写在 JSON/CSV 或图片文件中的测试输入，例如“二手高数教材、售价 25 元”。只交这些文件，尚未证明系统功能正确。
- **真实接口测试**：将上述虚构样例通过被测 API 创建到专用测试库，再在页面操作并核对 API/数据库结果；数据是虚构的，接口和操作是真的。不得把商品硬编码到生产页面充数。
- **一条用例**：一次明确的前置、输入/动作、预期、实际与结论。改标题重复同一操作不能增加数量；同一用例换浏览器是两次执行，不是两个新用例。
- **岗位编号**：R1/R2、T1/T2/T3、U1/U2、D1/D2 是新岗位，不是原 M 编号。九人自行认领，本文不替组员分组。
- **交付文件**：下面列出的具体文件都由对应岗位唯一维护。需要其他人的内容时，对方先提交自己的文件，接收人汇总链接；不同时改一个共享文件。
- **状态**：通过、失败、阻塞、未执行、不适用五类分别记录。需要的功能缺失写失败/阻塞；只有范围明确排除并经 M10 登记，才能写不适用，不能为了凑通过数删用例。

目录中的 `<n>` 换成实际项目阶段，例如阶段五用 `phase-5`；`<变更ID>` 换成 M10 通知的编号，例如 `C20261027-02`。同一阶段内按变更 ID 分轮次，不创造“阶段六”。下列文件名是**要交的产物**，不是表示已经实现的命令或文件；接收前先核对存在与实际执行。

后文简写的 `changes/<变更ID>/文件名` 均位于 `docs/collaboration/phase-<n>/changes/<变更ID>/`；`testing/`、`experience/` 根目录分别是 `docs/collaboration/phase-<n>/testing/`、`docs/collaboration/phase-<n>/experience/`，不是仓库根目录。每轮日志追加变更 ID 和时间，执行 CSV 按运行一行追加，不能覆盖上轮失败/原始证据。

每个岗位都要交自己的 `task-log.md`、本轮 `delivery-checklist.md` 和非作者 Review 链接。交付清单逐个列文件、任务 ID、软件 SHA、实际结果、证据、未完成原因和接收人；缺的文件写待交，不能只发一句“已完成”。测试岗位另交 `daily-report.md`，每个工作日更新一次；严重故障立即报 M10。

## 各组具体交付

岗位先完成“第一次交什么”，再按“每次改动后做什么”持续更新。每组只设一名联络人：文书 R1、测试 T2、用户 U2、演示 D2；可以登记交接后换人。R1/T2/U2/D2 只汇总本组成果，不替另一岗位写原始结果。四组不需要互相找所有组员，对接步骤见后文“对接流程”。

### 文书与技术报告组

长期组分支：`team/reporting`。本组回答“系统做了什么、为什么这样设计、有什么证据和限制”，不改生产代码。测试和体验未结束时可以写草稿，但不能把未验证结论写成已通过。

#### R1 需求、测试结论与报告统稿

岗位分支：`work/reporting/report-editor` → PR 到 `team/reporting`。接收 M10 的版本通知、R2 技术章节、T2 测试汇总和 U2 手册/截图索引。

##### 个人任务

1. **R1-01 需求与范围**：写清校园闲置交易的问题、目标用户、项目目标、不做真实支付/物流/真实学籍认证的边界。把 T01–T15 的每个功能域至少拆成 2 条可检查要求，共至少 30 条；一条写正常行为、一条写失败/权限边界。每条给唯一 REQ 编号、角色、入口、输入、结果、优先级、关联 Issue/代码/用例和当前状态。已有需求编号优先沿用，不另造一套覆盖旧编号。
2. **R1-02 测试与评估章节**：从 T2 的最终汇总抄入真实执行数量并复算总和；说明测试版本、环境、虚构数据规模、通过/失败/阻塞和复测。独立模型效果、功能符合性、自动化与真人体验分开写，引用原始结果；没有合格 L3/未封存评估就如实写限制，不填虚构准确率。
3. **R1-03 报告正文**：本人写 Introduction、Requirements、Testing and Evaluation、Conclusions；R2 的 Design/Implementation/AI 章节通过链接或构建引用进入总稿，不直接编辑 R2 的源文件。总报告按课程要求覆盖背景、需求、设计、实现、测试评估、项目管理/反思、结论和参考文献；每个重要结论都能定位到版本与证据。
4. **R1-04 来源与贡献**：登记所有实际使用的代码/模型/数据/图片/方法和 AI 工具，不为凑数量加文献；给十名成员各留一项真实贡献记录，附 PR/Review/测试或材料链接，未认领写待认领。贡献表由成员确认，不能替人签名。
5. **R1-05 排版与导出**：总报告正文 40–60 页，A4、四边 2.54 cm、12 pt Arial/Times New Roman、1.5 倍行距、单栏；封面、目录、References、Appendix A 不计正文页数。DOCX/PDF 可打开、目录/页码/引用一致；确认学校正式日期、时区与入口，不猜测。

##### 每次改动后做什么，交给谁

收到通知先在 #129 回复涉及的 REQ 和章节；只更新受影响内容，其他章节写已核对无影响。收齐 T2/U2 的实际记录后再更新“已通过”结论，向 R2 发 PR Review，请原测试执行人核对数字、M10 核对技术事实。交 D1 的是报告 PR/版本、可引用结论、证据路径与限制，不能只交 PDF 截图。

R2 从 15 个功能域各抽 1 条 REQ，能顺着 CSV 打开代码/契约、用例和结果；T2 复算数量一致；M10 确认范围与 NO_GO 描述；最终导出符合课程页数和格式。缺证据的条目写待验证，不能因排版完成而判报告完成。

##### 个人任务一：12 个能重走的业务场景

为 P049–P060 各写 1 个场景，动作必须按本轮服务状态机实现，不直接改订单状态：

1. **S01 咨询**：B 联系 A 的商品，建立 1 个会话，双方各发 2 条非空文本。
2. **S02 待处理报价**：B 发有效报价，A 看见待处理；同一请求重试不重复。
3. **S03 还价**：A 对 B 报价还价，双方状态一致；记录原报价与新报价 ID。
4. **S04 拒绝**：A 拒绝报价，不能再接受同一失效报价。
5. **S05 接受与唯一订单**：A 接受 B 报价，商品被占用，只有 1 个有效订单，C 不能再买同件。
6. **S06 见面约定**：双方确认同一版本的未来时间和校内公共地点，刷新后仍在。
7. **S07 单方完成**：一方确认完成后，订单不能提前算双方完成，不能提前评价。

12. **S12 旧版本确认失效**：修改约定得到新版本，旧确认不能误算新版本已确认，双方需按新版本操作。

## 对接流程：谁交什么、发哪里、谁接收

### 公共约定：只需要四个联络人，不要全员互相催

四组联络人为 R1、T2、U2、D2；组内原始任务由实际岗位执行。所有通知在 [Issue #129](https://github.com/Huang0283/CampusLoop/issues/129) 以变更 ID 串起来，文件在各自岗位/组分支提交 PR，缺陷/体验问题另开 Issue 并回链。无需把文件重复复制到四个群；发可打开的 GitHub 链接，不只发本机 `C:\...` 路径或别人打不开的 localhost。

第一次交接接收人先做一次最小操作，再回复“已接收，可开始/部分可开始/缺材料”；不能只点表情。每轮通知由 M10 写本轮预计反馈日期，接收人最迟下一个团队工作日给接收/阻塞反馈，不要求当天完成整组工作；发现越权、数据丢失或核心链路不通立即报告。每周节奏仍是一周一个阶段，正式课程日期未知时保持待确认。

### 第一步：M10 发版本 → T2 分给 T1/T3

M10 在 `docs/collaboration/phase-<n>/changes/<变更ID>/notice.md` 填写软件分支/完整 SHA、UI 与 API 地址、是否已合并、专用环境/数据获取、改前改后、受影响页面/接口/权限/状态、要测的 T 编号/用户 U 任务和预期、已知限制、反馈日期、组汇总 PR 目标；在 #129 发链接并点名实际认领的 T2/R1/U2/D2。

T2 回复软件 SHA/任务范围，把数据和权限交 T1、业务交自己、环境/异常交 T3。T1/T3 在自己的日志认领用例，不能三人改一个文件。若 API 没启动、没有审计库或缺管理员，T2 列“缺什么、由谁补、哪些不能测”交 M10；其他能测的用例先继续。R1/R2/U1/U2/D1/D2 此时可改草稿，不要假写测试结论。

### 第二步：T1 交数据 → T2/T3 接收

T1 发数据 PR/版本、样例统计（8账号/60商品/12求购等）、README、命名空间、生成/复位命令、实际成功/拒绝数、映射清单和已知缺口；凭据私发，不写公开 Issue。

T2 在 business 空间按说明导入，T3 在 environment 空间复核目标和重复导入。两人各回复：实际软件 SHA、数据版本、执行命令、创建数/失败数、是否可开始。文件缺行/引用错误退回 T1；接口不支持或环境权限缺失退回 M10；不把双方都写成“等对方处理”。T1 修后重交同 PR，由原接收人重试；此前失败保留。

先接收基础数据再接收权限/交易前置：T2 不用等 T1 的 36 条全部通过才开始生成场景，T1 的订单/私聊越权用例接收 T2 的配方后补测，分别写两次交接。安装说明亦先由 U2 按统一启动脚本写可执行草稿，T3 边运行边回报缺步，U2 再修订，不要求手册已验收后才允许测试手册。

### 第三步：测试组每天交反馈 → M10 修 → 原执行人复测

T1/T3 将自己的 `daily-report.md` 和脱敏证据交 T2；T2 加本人记录，在 `changes/<变更ID>/testing-summary.md` 汇总五类计数、Issue、严重度、可交用户任务、阻塞、需 M10 帮忙和下一步，每个工作日在 #129 发一次摘要。不是让 M10 到三个分支里猜结果。

每个真实故障单独建 Issue，填软件 SHA、环境/数据、账号别名/对象 ID、最短复现、预期依据、实际结果和脱敏证据。M10 回复“接受并修复/需补证据/暂缓及理由”，修复 PR 用 `Refs #缺陷号`，推送新软件 SHA 和回归范围。原执行人在新 SHA 跑原用例与相邻回归，在缺陷 Issue 写结果；T2 才更新汇总状态。没有原执行人复测，M10 不能替他写“已确认”，PR 合并不自动等于缺陷关闭。

### 第四步：T2 交通过的任务 → U2 分给 U1

T2 发 `business-journeys/user-handoff.md`，逐项写 U01–U08 哪些可做、通过用例/证据、软件 SHA、experience 空间导入入口、角色别名、数据 ID、已知限制。U2 先确认能打开首页、登录专用账号、查看一件指定商品，再在 #129 回复接收结果，并分给 U1 的学生任务与自己的管理/安装任务。

U1 不必等 U06 管理页修好才能体验 U01 浏览；被阻塞的任务写明对应缺陷，其他任务继续。U1/U2 的观察与任务由真人记录，体验步骤不能用脚本替代。测试组修正错误数据由 T1 交接；软件坏了找 M10；难用问题建体验 Issue，不能丢给文书组修改一句话代替修功能。

### 第五步：用户组交问题 → M10 处置 → 原体验人确认

U1 给 U2 自己的任务/截图/反馈链接，U2 在 `changes/<变更ID>/user-summary.md` 按任务列完成/失败/阻塞、入口卡点、问题 Issue、手册和截图 PR。M10 在每条 Issue 写接受修复、后续处理或不采纳及理由；接受项修后由原体验人重走任务，后续处理给负责人/影响/再检查日期。U2 汇总处置，不替 U1 填“体验已通过”。

### 第六步：T2/U2/M10 交事实 → R1/R2 更新报告

T2 给报告的包是测试汇总、用例与原始日志链接、数据规模、已修/未修、实际指标或未评估原因；U2 给的是手册 PR、截图索引、真实任务观察/限制；M10 给的是代码/契约变更、版本和技术限制。R1 回复“收到哪些证据、要改哪些 REQ/章节、仍缺什么”；R2 据此核对图/链路/方法，R1 写测试/体验结论和总稿，两人各提交自己文件的 PR。

R1 报告中的数字请原测试岗位复核，技术说明请 M10 复核，截图请 U2 复核；这些可以在同一个 PR 留具体评论，不要求所有人同时改报告。没等到结果的段落保留待验证，其他章节可以先合草稿，不能要求所有测试通过后才允许写任何文档。最终“通过”结论必须对应实际证据。

### 第七步：前三组交稳定资料 → D2/D1 最终演示

R1 交最终报告/需求/结论和限制，T2 交已复测主链路/边界/降级的操作配方，U2 交同版本截图/手册/demo 数据计划。D2 回复缺少的场景或数据 ID，D1 核所有数字/截图来源。M10 在 #129 明确“冻结软件 SHA、允许最终演示的范围、仍有限制”；没冻结只能写草稿，不能录最终版。

D2 组织第 1 轮彩排，失败建 Issue 交 M10，测试/原体验人复测，D1/D2 各修自己的 PPT/脚本，再做第 2 轮，之后录真人出镜 MP4。紧急 UI/代码变更影响哪个环节，就补测和重录那个环节；不把旧图静默塞进新版本。

### 第八步：各组 PR → 接收 Review → M10 收口

个人 `work/*` PR 到本组 `team/*`，同组另一人按任务书核对实际文件/数量/内容；跨组接收人只评论或给接收记录，不能直接推别人分支。组联络人汇总自己的组 PR，目标按本轮 notice 写明（当前阶段集成或已收口后的 main），写软件 SHA、材料 commit、结果和缺口。阶段材料可以引用已合并到另一个组分支的原文件链接，不能互相复制后双份维护。

M10 检查核心流程和技术边界，各组确认自己的材料已更新；有失败/阻塞继续开放，不因为到了周末或 PR 合并就关闭 #129。课程提交由指定人实际操作 Blackboard，D1/D2 登记文件/回执；GitHub PR 不能代替学校提交、成员签名或独立验收。

## 核心功能测试矩阵（测试组必测）

以下清单根据 `frontend/src/router/index.tsx` 的实际 live 路由、核心验收场景与 OpenAPI 组织。路径里的 `:id`、`:wantedId` 用本轮数据 ID 替换。目录要求检查覆盖，不表示每个列出的动作已在当前候选中实现；不存在的动作登记“需求要求但未实现”或经范围确认“不适用”，不可直接打勾。每轮从实际路由/OpenAPI 补充新增项，确保一条路由或新增接口都有对应用例。

### T01 游客浏览与检索

- 入口：`/`、`/market`、`/product/:id`、`/wanted`、`/wanted/:id`。
- 未登录浏览商品/求购及公开详情，关键词、实际支持的分类/价格等筛选、排序、分页、清空筛选、空结果、返回/刷新、无效/不存在/下架资源。
- 纯浏览不要求登录；收藏、发布、私聊等需登录动作按契约提示并保存返回目标。所有列表从真实 API 获得，不得用兜底商品掩盖接口失败。

### T02 认证、账户与会话恢复

- 入口：`/register`、`/login`、`/profile`。
- 注册字段、邮箱格式/重复、密码校验、正确/错误登录、禁用/失效账户、退出、刷新恢复、过期会话、受保护深链接及登录后的原目标恢复。
- 本人资料可编辑字段、不可编辑字段、公开/私有字段边界；多标签页/服务重启后的会话行为按当前实现验证。

### T03 商品发布、管理与媒体

- 入口：`/publish`、`/product/:id/edit`、`/my-products` 及公开详情。
- 发布、必填/格式/价格边界、超长文本、图片数量/类型/大小/损坏、失败重试/取消、保存后列表/详情一致、编辑/上下架、已售或占用状态的操作限制。
- 文件权限、图片显示和重启后保留；非所有者不能编辑，自己不能购买自己的商品；重复点击不创建重复事实。

### T04 收藏、求购与本人数据

- 入口：`/favorites`、`/wanted/publish`、`/wanted/:id/edit`、`/wanted/:id`。
- 收藏/取消/重复操作、空列表、已售/下架商品表现、账号切换后归属；求购发布/编辑/关闭、预算/类别/地点/有效期等字段按真实契约校验、非所有者拒绝。

### T05 聊天、报价与重连

- 入口：`/chat`、`/chat/:id`，从商品或求购发起联系的实际入口。
- 买卖双方会话、会话归属、空/超长消息、发送成功/失败/重试、历史分页、断线补拉、顺序/重复消息、多会话切换；他人不能读取消息。
- 结构化报价、还价/接受/拒绝/撤回/过期按服务状态机校验；重复、旧状态和无权操作拒绝；不是每个动作都由同一方执行。

### T06 唯一订单与并发边界

- 入口：`/transactions`、`/transactions/:id`。
- 接受有效报价形成唯一有效订单并关联商品/求购/会话；买卖双方可见，第三方不可见。
- 两个买家竞争、重复接受/请求重试、商品占用、非法状态、取消/争议等实际支持动作。确认双方状态一致、数量/事件无重复；并发通过专用测试脚本验证并附原始结果。

### T07 约定、双方完成与持久化

- 入口：`/transactions/:id/meetup` 和订单详情。
- 见面时间/地点校验（含过去时间）、时区、约定版本变更、旧确认失效、双方确认同一版本；单方完成不能当双方完成，双方完成后商品/订单同步。
- 取消/争议/未完成状态限制、重复确认、非参与方拒绝；刷新、退出重登、服务重启后数据和状态保留。

### T08 评价与通知

- 入口：`/transactions/:id/review`、`/notifications`。
- 完成后参与者各自评价、重复/未完成/已取消/他人订单评价拒绝，字段边界与显示范围。
- 通知创建/列表/未读/单条已读/全部已读/跳转目标、重复操作、账号切换、失败重试；全局提醒位置和未读数正确。

### T09 举报、证据与管理员治理

- 入口：`/report`、商品/聊天/订单中的举报入口、`/admin`。
- 根据对象和买卖方身份检查原因、输入校验、附件、提交、查看本人举报与处理状态；举报证据/私聊/约定不泄漏给无权人。
- 管理端当前实际提供的用户、商品、举报列表/筛选/详情/处理/原因/审计；禁用/恢复等动作按契约测试，非管理员拒绝，重复处理及非法状态有确定结果。

### T10 智能搜索与供需匹配

- 入口：`/market` 的实际搜索、`/wanted/:wantedId/matches`。
- 输入、类别/预算/成色/地点等硬约束、空结果、排序/解释、分页、无权/无效 ID、旧版本结果。
- 服务正常、超时、异常、索引未就绪、关闭服务时的真实降级；不把相似度说成成交概率，不把规则/候选标成已经验证的模型。

### T11 价格、信誉和风险提示

- 入口：`/publish/price-advice`、公开详情允许展示的提示与 `/admin` 审核区域。
- 输入边界、区间/解释/版本/来源/免责声明、数据不足与不可用降级、字段权限、规则人工覆盖和审计；卖家自主定价，风险不自动认定欺诈/封禁。
- 功能/规则符合性与独立模型效果分开记录；没有足够真实授权评估数据时，只报告当前基线/降级与 NO_GO，不编造准确率或误差。

### T12 页面状态、布局和可访问性

- 对每条当前 live 路由记录加载、成功、空、失败重试、无权状态中适用的项，不能只测理想数据。
- 桌面 1440×900 与手机 390×844，Chrome/Edge 当前版本；长文本、滚动、侧栏、右上角账号/提醒、弹窗、键盘/焦点/标签、按钮可达性、无未处理白屏。
- 以批准的原界面为基准，接 API 不得把布局简化。截图记录视口和 SHA；生产构建也要检查，不只看开发模式。

### T13 路由别名与错误恢复

- 入口：`/orders`、`/orders/:id`、`/orders/:id/review`、`/profile/transactions` 及未知路径。
- 别名与正式交易页保持权限/行为一致；不存在路径 404、无权 403、无效资源、后端不可达、慢请求、重复点击、深链接、刷新/返回和恢复提示。

### T14 干净环境、安装包与持久化

- 另一台组员电脑或全新 VM 从指定 SHA 或指定包按部署手册安装，不复用 M10 未提交文件/账号库/依赖；记录系统、硬件、依赖、镜像/包哈希、端口、迁移头和命令。
- 空审计库迁移/种子幂等/健康检查、启动/停止/重启、媒体卷、端口占用时提示、升级与回滚路径；EXE 仅在该版本确有可运行包时测试，未交付写未交付。
- 在异机完成注册或专用账户登录、发布/浏览/聊天/报价/订单约定/完成/评价、智能降级。换本机目录不能写成异机通过。

### T15 权限、安全、性能与恢复

- 对象归属、管理权限、令牌/私密响应/日志与媒体 URL、CSRF/CORS 和实际接口测试证据；不在截图/Git 提交凭据。
- 专用数据库/Redis DB14/15/测试媒体卷中执行重复/并发、性能、依赖失败、备份恢复与损坏备份拒绝；记录请求数/并发/数据规模/硬件/命令、p50/p95/p99 和原始输出。
- 区分 PostgreSQL 恢复与 MinIO 媒体恢复的实际范围；没有实测不能写“全部可恢复”。服务失败是否可降级按真实契约验证，不能承诺任何依赖关闭后所有功能都可用。

## 分支与 GitHub 协作

M10 技术任务通过技术任务 PR 进入当前阶段集成，不由材料组修改生产代码。四条 `team/*` 是长期组分支；九条 `work/<方向>/<岗位>` 是每个岗位认领后一人使用的工作分支，已由 M10 建立。岗位分支 PR 指向本组 `team/*`，组汇总 PR 指向本轮版本通知指定的集成目标；禁止直接 push main、共享组分支或他人岗位分支。

岗位分支可在每轮 PR merge 后继续复用：拉取自己的远端并 merge 本组最新分支，不 rebase/force-push 共享历史。PR 合并时不自动删除这九条仍有人使用的岗位分支；若一项工作已结束且不再复用，再创建新的短期任务分支。长期/岗位分支用 merge 方式保持祖先关系；不要对持续复用的 head 使用 squash 后继续堆提交。

文件边界、拉取/push/PR/Review/冲突处理见各组 WORKFLOW.md。一个文件只有一个编辑负责人；Review 用评论/建议而非直接改他人分支；跨组文件经对方接收后在对方 PR 修改。软件完整 SHA 与材料提交分开登记，材料合并不代表软件基线已经验证。

## 时间与提交节奏

每阶段仍按一周推进，不固定第几天或几点完成哪一项。每周由 M10 发布验收 SHA、变更范围和优先级，各方向认领本周交付；周内持续测试、修复和同步材料，周末复核交付、复测和阻塞。未通过的事项保持开放，不因到周末而自动视为完成。

测试组每个工作日向 M10 简报一次；其他方向随大改动更新材料，并在本周交付前提交个人 PR、证据和任务日志。最终演示与录像放在功能/UI 冻结和验收之后。

已核对三个课程文件：Proposal_Template.pdf 只有 Deadline 填写栏；课程要求 PDF 要求以 Blackboard Course Assessment 的截止时间为准，没有具体日历日期；Group workload profile 随 coursework 提交，也没有独立截止日期。材料集成人取得真实日期后在 Issue #129 登记截止时间、时区、提交入口、课程提交人与团队内部交付日期；未知时标为待确认，不把每周安排当作学校截止日期。

每周提交指源文件、测试/数据清单、证据和个人 PR 进入对应材料分支并接受复核，不只是发聊天截图。课程最终提交由团队确认的一名成员依教师要求在 Blackboard 完成，并保存提交回执；GitHub push 不等于已向学校提交。

## 完成标准

本协作计划只有同时满足以下条件才算完成：

1. M10 的软件候选 SHA 在另一位成员电脑或全新虚拟机上按手册启动，核心旅程和失败边界可复现，保留独立执行记录。
2. 测试组维护数据清单和独立评估边界，完成独立功能、权限、异常、环境和非功能测试，每日向 M10 汇报，失败项已修复或明确阻塞。
3. 文书组完成 40 至 60 页技术报告正文及引用、贡献和证据追踪。
4. 手册组完成 8 至 12 页用户手册和管理员/部署/故障文档，非作者可按步骤运行。
5. 功能与 UI 已冻结，演示组在同一 SHA 上完成两轮彩排、15 分钟演示材料和真人出镜 MP4。
6. 软件、报告、手册、PPT、视频和 Group Workload Profile 的版本、术语、数字和限制一致。
7. 所有外部来源、AI 使用、隐私数据、许可证和未完成项已披露；材料集成人、M10 和课程要求的 Review/签收真实完成。

没有证据的项目保持“待完成”或“阻塞”，不通过口头确认关闭 Issue。
